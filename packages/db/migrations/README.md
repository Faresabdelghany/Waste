# Migrations

Plain SQL files, applied in journal order by `src/migrate.ts` (`pnpm db:migrate`), never by `drizzle-kit push`. Two kinds of statement live here, and the rule for how they share a file is the point of this document.

## Who writes what

**drizzle-kit writes** what it has a builder for: `CREATE TABLE` with its columns, defaults, primary and foreign keys, unique constraints, indexes and `CHECK` constraints (including `validPeriod` and `validGeometry`), and the `ALTER TABLE` statements of a later change to those. `pnpm db:generate` diffs `src/schema/index.ts` against `meta/<last>_snapshot.json` and writes the next file, its snapshot and the journal entry. It never reads a `.sql` file back and never looks at a database, so what is appended to its file is invisible to it.

**Hand-written statements** are everything the database needs that Drizzle cannot express. The foundation (`0001_foundation.sql`: extensions, functions, the API role, grants) was written by hand as a whole. From the first domain table on, every table needs three kinds of statement beside what drizzle-kit generated, and a helper in `src/sql/` spells each so no two tables spell it differently:

| Statement | Helper | When |
|---|---|---|
| Row-level security enabled and forced, one policy over `company_id` for `wms_api` | `tenantFence(table)` | Every table (every table carries `company_id`) |
| The `BEFORE UPDATE` trigger on `wms.touch_updated_at()` | `touchUpdatedAt(table)` | Every table that spread `timestamps` |
| `REVOKE UPDATE, DELETE ... FROM wms_api` | `appendOnly(table)` | Every table that spread `recorded` instead of `timestamps` — a ledger, appended and never rewritten (Issue #101); the gate reads `recorded_at` as the mark, and the helper refuses a table that also carries `updated_at`. The owner keeps both rights, for tests and for erasure |
| The `btree_gist` exclusion constraint over the business key and the validity range | `excludeOverlapping(table, [keyColumns])` | Every table that spread `validity` (which must also carry the `validPeriod` check); `company_id` leads the key, and every key column is `NOT NULL`, since a null never equals anything in an exclusion constraint |
| The `btree_gist` exclusion constraint over a key and the `tstzrange` of a reservation, with a predicate | `excludeOverlappingWindow(table, [keyColumns], { live? })` | Every table that spread `window` and carries the `orderedWindow` check — a reservation on a clock, not an effective-dated row — at least once; named by its key (`vehicle_allocation_vehicle_no_overlap`), so one table may carry several; a nullable key column is allowed, and the helper itself keeps its nulls out of the index (`"<column>" is not null` in the predicate), while `live: { column, not }` says which rows count (`"status" <> 'released'`). Both exclusion helpers resolve their key through `src/sql/key.ts` — the table's own columns, none of the range, `company_id` leading once — so the two cannot drift on what a key is |

Drizzle can describe policies (`pgPolicy`) and RLS; they are not used, so each of these statements has one owner and one spelling.

### A ledger: appended, never rewritten

A ledger (Issue #101, ADR-0003: `stock_movement`, `vehicle_allocation_event`; Issue #104, ADR-0004: `proof_of_service`, `unload`, `driver_command`; Issue #109, ADR-0005: `ticket_event`, a Ticket's history — its status changes, assignments and comments — the fifth ledger keyed by the server after Resources' two and Execution's `proof_of_service` and `unload`, and the sixth in all, the receipt being the client's; Issue #112: `billing_run_exclusion`, `invoice`, `invoice_line`, `settlement_event` and `weight_review`, the seventh to eleventh — an Invoice is a ledger because "invoice number and original issued content are immutable", a credit note being an Invoice of `kind = credit-note` naming the one it credits and "sent" the export's own row, and a weight review one row per decision on an Unload with a correction naming the new Unload row it wrote) spreads `recorded` — one `recorded_at` — instead of `timestamps`, so it has no `updated_at`, no trigger, and nothing to keep honest; its file carries `appendOnly(table)` where another table's carries `touchUpdatedAt(table)`. That is the one rule the gate reads: a table with `recorded_at` is a ledger (and a table with neither stamp is neither kind, which the gate refuses rather than guesses about). The default privileges of `0001_foundation` granted the API role every right on every future table of `wms`; the revoke takes UPDATE and DELETE back for the ledger, so a row nobody can change through the API is still a row the owner can remove by hand. What a ledger says about the present is a query, never a table of its own: the Container Asset State is `src/query/asset-state.ts`, the latest movement of a container in recording order — a `LATERAL` lookup per row, `where company_id = ? and container_id = <the row's> order by id desc limit 1`, one backward probe into `stock_movement_container_id_idx` (`(company_id, container_id, id)`, ascending: drizzle-kit's `DESC` is `DESC NULLS LAST`, which `ORDER BY id DESC` does not match), never a fold of the whole ledger — turned onto the glossary's four states by `@waste/domain/resources/asset-state`. A test's `dropTenant` cannot delete a ledger's rows as `wms_api`; it needs the owner. Nor can the API role row-lock one: `SELECT … FOR UPDATE` asks `UPDATE` privilege of the table, which the revoke took away (42501), so a rule the API holds over a ledger row is held under the lock of the `timestamps` row it hangs off — a credit note under the billing run that issued the invoice, a weight review under the unload's route (Issue #112) — and never on the ledger row itself, which in any case never changes.

A ledger of one table's history has kinds with shapes, like the proof ledger: `ticket_event_kind_shape` is one `CASE` over the kind built from the domain's `TICKET_EVENT_SHAPES` (`@waste/domain/resolution/event-shapes`), so a `created` row says nothing but the status and the assignee, an `assigned` or `status-changed` row may carry a note, a `status-changed` row carries a resolution exactly when its status is `completed`, and a `comment` carries a body, may carry an attachment's key and may be the customer's to read; the case's row is a snapshot the ledger repeats. Two partial unique indexes beside it are the outbox consumer's idempotency keys (Issue #109 §3): `ticket_source_event_id_idx` over `(company_id, source_event_id) where source_event_id is not null` on `ticket` and `ticket_event_source_event_id_idx` likewise on the history, so a `pickup-failed` delivered twice is one ticket and a `command-rejected` folded twice is one comment, the second attempt a 23505 the consumer reads back. `source_event_id` is a soft uuid and not a key into `outbox_event`, for the reason `aggregate_id` is: the outbox row outlives nothing and joins nothing, and a key from here would make it join something and never be pruned.

### A generated column as an exclusion key

An exclusion constraint's key column may not be nullable — a null never equals anything, so rows with one would overlap freely — and `subscription.location_id` (Issue #78) was the first answer: a `generated always as (coalesce(property_id, shared_collection_point_id)) stored` column that makes a one-of-two place one `NOT NULL` value the key can hold. `price_list_row.condition_key` (Issue #112) is the same device over five nullable conditions: `coalesce(planning_area_id::text, '') || '/' || coalesce(customer_kind, '') || '/' || …`, stored, so `price_list_row_no_overlap` over `(company_id, price_list_id, product_id, condition_key)` holds one row of a list, a product and one condition set in force at a time — a scheduled price change is the next row of the same set, and a default row and a zone row of one product coexist, the key telling them apart. Like `location_id` it is the database's device and never on the wire; a value written for it is refused by Postgres (428C9), and the API never names it.

### A period that is the record: the settlement

A Settlement settles an assignment over a period, so its period *is* the `validity` set (Issue #112, ADR-0005): `settlement_no_overlap` over `(company_id, service_area_assignment_id)` holds one settlement of an assignment over a period without a helper of its own, and the one thing a settlement adds to the set is `settlement_period_closed`, `valid_to is not null` — a settlement without an end is not a period. It is the one effective-dated table whose end is required; the wire says the same (`Settlement.validTo` is not nullable). Its period is not held inside its assignment's, since a correction that lands in the month after an award ended is settled then (§7.16), and it carries a status beside the period because open, calculated and closed are what the period cannot say — the stamps held to it by `settlement_stamps_shape`, the Vehicle Allocation's pattern of a row the database holds and a ledger (`settlement_event`) nobody rewrites.

### A reservation on a clock

A Vehicle Allocation reserves a vehicle from an instant to an instant — two routes a day on one vehicle is ordinary and a reservation without an end is not a plan — so it is not effective dating: it spreads `window` (`planned_from`, `planned_to`, both `timestamptz NOT NULL`) with `orderedWindow(columns)` beside them (`<table>_window`, `planned_to > planned_from`, strict for the same reason `validPeriod` is), and its file carries one `excludeOverlappingWindow` per key — over the vehicle, over the driver, over the trailer — each with `{ live: { column: status, not: "released" } }`, which frees a released row, and with the nulls of a nullable key kept out of the index by the helper. A table that copies the window columns as a snapshot (`vehicle_allocation_event`) spreads `window` without the check, and the gate asks nothing of it.

### A ledger keyed by the client: the command receipt

`driver_command` (Issue #104, ADR-0004) is a ledger whose id is the client's, not the database's: a driver's device mints a UUIDv7 for every command it queues, and that id is the receipt's primary key, the idempotency key the applier reads first, and the id of the row the command made — a session, a proof, an unload — in that row's own table. A command's id already present is a replay the API answers with the stored outcome, never a 409, and two uploads of one batch overlapping meet the receipt's primary key (23505 `driver_command_pkey`), which is how the race is decided. The receipt is also where a rejected command is kept — its `body` verbatim and the `problem` the applier answered, the two `jsonb` columns of the context beside the outbox's `payload`, each kept for another reader and never queried by column — so nothing a device said is silently dropped. Being a ledger, it spreads `recorded` and its file carries `appendOnly`, like the two ledgers beside it, `proof_of_service` and `unload`.

A ledger row's reference may be null where the row records a refusal that named nothing the writer reaches. `driver_command.route_id` is nullable: a command rejected because no such route is assigned to the driver — another company's, another project's, or none — has no route the composite key could check, so the receipt is written with `route_id` null in the driver's own project (`project_id` stays `NOT NULL`, so the row is the project's like every Execution row and the driver key stays checked), the device's claimed id kept in `body` beside the body it sent, and the inline check `driver_command_route_shape` holds such a row to a rejection naming no session and no pickup — Postgres leaves a composite key with a null member unchecked (`MATCH SIMPLE`), so the shape check is what says which rows may take that form. The other nullable references of the ledgers beside it say something else: `proof_of_service.pickup_id` null is a proof standing on the route alone (`proof_of_service_pickup_shape` says which kinds may), and a null `session_id` on a proof or an unload is a row the office recorded (`_session_shape`) — a fact about the row, never a row the writer could not see.

### A reference through another column

A reference usually reaches its row by id alone. Where a row belongs to a parent the referencing row also names — the Stock Movement ledger names a placement *of the container it moves* — the key carries that column on both sides, so the two cannot disagree: `projectReference(t, [t.containerId, t.placementId], containerServicePlacement, [containerServicePlacement.containerId, containerServicePlacement.id])` is `(company_id, project_id, container_id, placement_id) → container_service_placement (company_id, project_id, container_id, id)`, and the placement carries `projectKey(t, t.containerId)`, `unique (company_id, project_id, container_id, id)`, named `<table>_<through>_project_key`. Container A cannot be recorded as issued into container B's placement, whatever the API does (23503). Execution (Issue #104) uses the same shape for a route's children: `pickup` and `session` carry `projectKey(t, t.routeId)`, and a proof, an unload or a receipt names a pickup or a session *of the route it names* — `projectReference(t, [t.routeId, t.pickupId], pickup, [pickup.routeId, pickup.id])` — so a proof cannot be recorded against another route's stop.

## Keys: a reference carries the tenant

An intra-tenant reference is a **composite foreign key that includes `company_id`**: `(company_id, project_id) → project (company_id, id)`, `(company_id, role_id) → role (company_id, id)`, and so on. A row therefore cannot reference another company's record, whatever the API does, and the database refuses the attempt with 23503. Every table referenced this way carries `unique (company_id, id)` for the key to point at. Only `company_id → company (id)` itself is a plain key, and `company` is its own tenant (`company_id = id`, the `company_self` check), so the fence applies to it like to every other table.

drizzle-kit writes these (they are foreign keys and unique constraints), but its default names would not do: `<table>_<columns>_<foreign table>_<foreign columns>_fk` overruns 63 bytes on a composite key, and Postgres truncates an identifier silently. So every key is named explicitly through `src/names.ts` by the helpers in `src/schema/references.ts`: `companyReference(t, company)` for the plain key, `tenantReference(t, [t.roleId], role)` for a composite one (`<table>_<columns>_fk`), `tenantKey(t)` for the `unique (company_id, id)` a reference points at (`<table>_tenant_key`), `tenantUnique(t, ...columns)` and `uniqueOn(...columns)` for business keys (`<table>_<columns>_key`, Postgres's own suffix, the tenant column left out of the name — and where listing the columns would pass 63 bytes, the key is spelled inline with `unique(tableObjectName(...))` and named for what it holds instead, as `shared_collection_point_member_membership_key` is), and `tenantIndex(t, ...columns)` for a referencing column set no unique constraint leads with (`<table>_<columns>_idx`; Postgres indexes only the referenced side of a foreign key). A check over a text column is `oneOf(column, values)` or `lowercase(column)` from `src/schema/checks.ts`; a count is `positive(column)` (null passes, since nothing recorded is not zero) and a one-of-two column pair `exactlyOne(t, label, [a, b])` (`(a is not null)::int + (b is not null)::int = 1`, named `<table>_<label>_exactly_one`). Each is named `<table>_<column>_<rule>`, or `<table>_<label>_<rule>` where the rule is about several columns at once. A rule one table alone has is an inline `check(tableObjectName(t.id.table, "<label>", "<helper>"), sql\`...\`)` named for itself — `depot_provider_shape`, `stock_movement_kind_shape`, which is a `CASE` over the kind spelling the pairs the domain's `MOVEMENT_SHAPES` allows, so the two are held together by a test and not by a helper. A check that compares a nullable column with a literal spells the comparison `is not distinct from`: `ticket_recollection_shape` is `recollection_route_id is null or resolution is not distinct from 'recollected'` (Issue #109), because `null = 'recollected'` is null and a null check passes, so an open ticket with no resolution could otherwise carry the route it may only carry once a re-collection was arranged. A name past 63 bytes is refused when the table is defined, with the fix in the message.

### A closed vocabulary that is a set is an array with a subset check

Where a row holds several values of one closed list — the days a Route Scheme serves, the days a Project rests on — the column is a `text[]` and not a child table, since a weekday is a vocabulary token and not a row anyone references (Issue #97). Postgres has no `in` for an array, so `subsetOf(column, values)` is `oneOf`'s counterpart: `CHECK (column <@ ARRAY['monday', …]::text[])`, named `<table>_<column>_subset_of`, holding every element to the list. An empty array is a subset of anything and passes it, so `nonEmpty(column)` — `CHECK (cardinality(column) > 0)`, `<table>_<column>_non_empty` — is the separate rule for the column where an empty set would mean a scheme that never runs; a group's `days` may be empty (a group that no longer runs) and carries the first check alone. Both read the same tuple of `@waste/domain/planning/vocabulary` that the contracts read into their `z.enum`, and, like `oneOf`, spell the values into the migration as literals, so adding a day is a migration. Neither refuses an element twice (`'{monday,monday}'` is a subset of the seven) or bounds the set: the database holds subset-ness and non-emptiness, and distinctness and size are the contracts' rule (`ServiceDays`, and `WEEKEND_MAX` for a project's weekend), since the API is the only writer. Where a bound is the table's own rule — a project's weekend leaves a working day — it is an inline check beside `subsetOf` (`project_weekend_not_every_day`, `cardinality(weekend) < 7`), the way `service_frequency_shape` is a table's own.

### And a project-scoped reference carries the project

Where **both** tables are project-scoped the key carries `project_id` as well: `(company_id, project_id, property_id) → property (company_id, project_id, id)`, so a subscription cannot name a property of another project any more than of another company, and a placement cannot name another project's container. That is `projectReference(t, [t.propertyId], property)`, named `<table>_<columns>_fk` like the tenant's, and the referenced table carries `unique (company_id, project_id, id)` for it: `projectKey(t)`, named `<table>_project_key`. Both leave `company_id` and `project_id` out of the name, since every key of a project-scoped table begins with them.

A reference from a project-scoped table to a company-wide one — an agreement's customer, a placement's waste fraction, a product's container type — stays a `tenantReference`: the target has no project to agree on. A table nothing references needs no key of its own (`property_party`, `vehicle_allocation_event`), and `projectKey` is what a table gets when something will point at it — `container_service_placement` got its in `0007_resources`, the day the Stock Movement ledger pointed at it, through an `ALTER TABLE … ADD CONSTRAINT` in the new file and a `DROP INDEX` of the index on its project the key now leads with. One thing to know about that order: drizzle-kit writes a created table's foreign keys before an altered table's new unique constraint, and Postgres wants the key before the reference, so the one `ADD CONSTRAINT` was moved up in the file by hand; the rendering test compares a file's generated head as a set, so the move is allowed, and the file says why in a comment.

## Layout: the same file, below drizzle-kit's statements

A table's hand-written statements go into **the migration file that creates the table**, after drizzle-kit's statements, each preceded by its own `--> statement-breakpoint` line (the migrator splits the file on that marker and runs each piece as its own statement, all in one transaction). Not into a paired `--custom` file: the table and its fence are one change and land in one journal entry, so no database is ever left with the table applied and the fence not, and a reader finds the whole table in one place.

The recipe for a new table:

1. Define it in `src/schema/<context>.ts` from the column sets in `src/schema/columns.ts` (`id`, `tenant` or `projectScoped`, `timestamps` — or `recorded` for a ledger — `validity` with `validPeriod(columns)` in the extra config, `window` with `orderedWindow(columns)` for a reservation) and the key helpers in `src/schema/references.ts` (every reference to another table of the tenant a `tenantReference`, `tenantKey` where a reference will point at it), export it from `src/schema/index.ts`.
2. `pnpm db:generate` writes `NNNN_<name>.sql`.
3. Append the hand-written statements to that file: `tenantFence`, `touchUpdatedAt` where there is `updated_at` and `appendOnly` where there is not, `excludeOverlapping` where there is validity, `excludeOverlappingWindow` where there is a window with its check. Copy the helper output verbatim.
4. `pnpm --filter @waste/db test`. The gate in `src/__tests__/hand-written.test.ts` reads every migration the way the migrator does (split at the breakpoints, comments dropped, whitespace collapsed), finds the file whose statements create each table of the schema, and fails with the missing statements printed verbatim when the file lacks one; paste what it prints. A statement wrapped over several lines counts; one commented out, or sharing a breakpoint piece with another, does not.
5. `pnpm db:migrate` locally; CI applies the same to its stack.
6. `pnpm db:fingerprint --write` against that local database (Issue #152), and commit `meta/_fingerprint.txt` with the migration: the complete fingerprint of a database these files build — every object the migrations own, one line each, environment-specific values normalised (`src/fingerprint.ts` says which). `src/__tests__/fingerprint.test.ts` migrates a fresh database and holds it to the committed file, so a migration added or changed without a regenerated fingerprint fails the merge, naming the lines; the Pilot's release compares the Pilot with the same file after it migrates. The file is `_`-prefixed on purpose: drizzle-kit parses every other file of `meta/` as a snapshot, and `journal.test.ts` holds `meta/` to that. Review its diff like the migration's: a line that changed and should not have is the finding.

What the file looks like once complete (a specimen; the constraint's key is the table's own):

```sql
CREATE TABLE "wms"."agreement" (
	"id" uuid PRIMARY KEY DEFAULT wms.uuidv7() NOT NULL,
	"company_id" uuid NOT NULL,
	"created_at" timestamp with time zone DEFAULT now() NOT NULL,
	"updated_at" timestamp with time zone DEFAULT now() NOT NULL,
	"valid_from" date NOT NULL,
	"valid_to" date,
	"container_id" uuid NOT NULL,
	CONSTRAINT "agreement_validity" CHECK ("wms"."agreement"."valid_to" is null or "wms"."agreement"."valid_to" > "wms"."agreement"."valid_from")
);
--> statement-breakpoint
ALTER TABLE "wms"."agreement" ADD CONSTRAINT "agreement_no_overlap" EXCLUDE USING gist ("company_id" WITH =, "container_id" WITH =, daterange("valid_from", "valid_to", '[)') WITH &&);
--> statement-breakpoint
ALTER TABLE "wms"."agreement" ENABLE ROW LEVEL SECURITY, FORCE ROW LEVEL SECURITY;
--> statement-breakpoint
CREATE POLICY "agreement_tenant_fence" ON "wms"."agreement" AS PERMISSIVE FOR ALL TO wms_api USING ("company_id" = (select wms.current_company_id())) WITH CHECK ("company_id" = (select wms.current_company_id()));
--> statement-breakpoint
CREATE TRIGGER "agreement_touch_updated_at" BEFORE UPDATE ON "wms"."agreement" FOR EACH ROW EXECUTE FUNCTION wms.touch_updated_at();
```

A ledger's file carries `REVOKE UPDATE, DELETE ON "wms"."stock_movement" FROM wms_api;` in the trigger's place (the section above).

### A column added to a table already applied

The recipe's step 2 covers it: change the table in its schema module, and `pnpm db:generate` diffs the schema against the last snapshot and writes the `ALTER TABLE … ADD COLUMN` and `ADD CONSTRAINT` statements into the new file, beside whatever else that file creates — `0006_planning.sql` gave `project` its `weekend` and `holiday_list` this way (Issue #97), in the file that creates the nine Planning tables, and `0008_execution.sql` gave `company` its route-number counter, `next_route_number integer not null default 1000` (Issue #104), the first `ALTER TABLE company`, whose `organisation-access-rendering.test.ts` mapping is `CHANGED_LATER`; `0009_resolution.sql` gave it the ticket-number counter beside it, `next_ticket_number integer not null default 1000` (Issue #109), the second, under the same mapping; `0010_finance.sql` the invoice-number counter, `next_invoice_number integer not null default 1000` (Issue #112), the third — one number per document, an invoice or a credit note, one series with two prefixes on the wire, taken one at a time under the company's row lock, which a billing run holds for the rest of its transaction so a run of a thousand invoices numbers them unbroken and a run that fails rolls its numbers back with its rows. The same file (0009) carries the first check replaced because its vocabulary grew: `outbox_event`'s two `one_of` checks are `DROP CONSTRAINT`ed and `ADD CONSTRAINT`ed in their new spelling, with Resolution's three kinds and its `ticket` aggregate — drizzle-kit writes the pair whenever a check's text changes, and the earlier file's rendering test maps the table's current spelling onto what its file says (`CHANGED_IN_0009` in `execution-rendering.test.ts`) while the new file's pins the replacements through `statementsBetween`; 0010 replaces them once more, with Finance's `invoice-issued` and `settlement-closed` and its `invoice` and `settlement`, so `execution-rendering.test.ts` maps today's spelling back one file at a time (`CHANGED_IN_0010`, then `CHANGED_IN_0009`) and `resolution-rendering.test.ts` diffs 0009's replacements from 0008's spelling to 0009's rather than to today's. 0010 also gave `product` its invoicing columns — `invoice_name`, `invoice_code` under the partial unique `product_invoice_code_idx`, `vat_percent` under `product_vat_percent_range` — `agreement` the `price_list_id` it is priced under with its key and index, and `unload` the `unload_project_key` the weight review points at, the day something pointed at it, exactly as the placement got its in 0007: drizzle-kit wrote the key below the foreign keys, and it was moved above the two that point at it, with a comment saying why. The file that created the table is not touched (an applied file is never edited), and it needs no new hand-written statement: the fence and the trigger are the table's, not the column's, and stand as 0002 wrote them. What does move is the rendering test that pins the earlier file: it compares the schema as drizzle-kit generates it *now* against what the earlier file says, so it carries the table's spelling as of that file and maps the current one onto it (`CHANGED_LATER` in `organisation-access-rendering.test.ts`), the way it already left out the index 0005 added; the new file's own rendering test pins the `ALTER TABLE` statements through `statementsBetween` (`src/__tests__/specimen.ts`), the table as it was against the table as it is. `0012_generation.sql` (Issue #97 part B) is the plainest case of the recipe: the two Generation tables, `generation_run` and `generation_match`, and beside them `route` gaining `generation_run_id` — the run that last wrote it, nullable since a route the fixtures or the office wrote names none — with its key into the run and its index, three statements drizzle-kit wrote in the order Postgres wants them (the run's table before the key that points at it), nothing moved by hand; `generation-rendering.test.ts` pins the three through `statementsBetween` over the route as 0008 left it, and `execution-rendering.test.ts` maps today's `route` back onto 0008's (`CHANGED_IN_0012`) and leaves the key and the index out (`ADDED_IN_0012`), the way `registry-rendering.test.ts` holds 0004 to its day. The two tables are ordinary: current state with the trigger, neither a ledger nor effective-dated, so their hand-written statements are the fence and the trigger and nothing else — a stamp of what a rule group matched is a row a run writes once and a read compares two of, not a history nobody may rewrite, since a run that failed is rolled back with its stamp.

### A column dropped from a table already applied

The first was `collection_group.rule_vehicle_type` in `0007_resources` (Issue #101): the vehicle-type token of 0006 gave way to `rule_vehicle_type_id`, a key into Resources' `vehicle_type`, and drizzle-kit wrote the `DROP COLUMN`, the `DROP CONSTRAINT` of the token's `one_of` check and of the shape check that named it, and the shape check `ADD`ed again in its new spelling. **A dropped column is guarded, not backfilled**: no database held a token when 0007 was written (0006 was unmerged and the seed writes no groups), so the file carries a hand-written `DO $$ … RAISE EXCEPTION … $$` before the `DROP COLUMN` that fails the migration when any row still holds one — a database with data refuses to lose it, and whoever has such a database maps each token onto a `vehicle_type` row first. The rule from here on: a column is dropped behind a guard that proves it empty, or behind a backfill that carries its values across, never bare. The rendering test pins the guard's presence and its place before the drop. Two more things about it. drizzle-kit — the CLI and `drizzle-kit/api` alike — asks on a TTY whether the added column is the dropped one renamed whenever a table both gains and loses a column in one diff; the answer is no, and where no TTY is at hand the diff is made in two steps, the columns added and then the token dropped, whose union is what the CLI writes for "create column" (the rendering test does the same, with the table at the step between spelled out beside the table as of 0006). And the earlier file's rendering test maps the table's current spelling onto what its file says (`CHANGED_IN_0007` in `planning-rendering.test.ts`) and leaves out the keys and indexes the new file added (`ADDED_IN_0007`), while the new file's test pins the `ALTER TABLE` statements themselves; a statement the new file dropped that the old one created goes back in for the comparison (`DROPPED_IN_0007` in `registry-rendering.test.ts`, the placement's project index).

Anything else the database needs that is not a table's goes below the tables' statements in the same file, as `0002_organisation_access.sql` carries the access token hook and its grants below the eight tables' fences and triggers, and as `0008_execution.sql` carries the third role and the publication below the seven Execution tables' (Issue #104, ADR-0004): `wms_sync`, the role the PowerSync service connects as — `REPLICATION` to open a logical replication slot, `BYPASSRLS` because forced row-level security would filter the initial snapshot for a role without it and the service reads every tenant by construction, `NOLOGIN` until `pnpm db:bootstrap` gives it a login from `SYNC_DATABASE_URL`, `USAGE` on `wms`, one `GRANT SELECT` per synced table and no other right, granted to the owner so a test can `SET LOCAL ROLE` to it, its statements tolerating the concurrent-creation race as `wms_api`'s do — and `CREATE PUBLICATION powersync FOR TABLE …` over exactly the tables the sync rules read (`SYNCED_TABLES` in `src/sql/publication.ts`, the one spelling the file is copied from and the rendering test holds it to; `user_account` is among them because every parameter query joins it to resolve the driver from the token's subject, and the rules' column lists keep its e-mail off every device). The gate in `src/__tests__/hand-written.test.ts` knows nothing of the role or the publication: they are nobody's table, like the hook, and what a table owes is what the gate reads. A table added to the sync rules is added to `SYNCED_TABLES` first, and its grant and its place in the publication go into the file that adds it (`ALTER PUBLICATION powersync ADD TABLE …`), never into 0008. A function that changes is replaced whole, in a new file, with `CREATE OR REPLACE FUNCTION` and its definition restated in full (`SECURITY DEFINER` and `SET search_path` are part of it), as `0005_hook_email.sql` replaces the hook below the index drizzle-kit wrote; the owner and the privileges survive the replacement, so the grants and revokes of the earlier files stand and are not repeated. drizzle-kit itself writes `--> statement-breakpoint` at the end of an `ALTER TABLE` or `CREATE INDEX` line; the migrator, and the gate, split on the marker wherever it stands. A file with nothing of a table's in it is hand-written whole, as `0001_foundation.sql` was and as `0011_worker.sql` is (Issue #97 part B, ADR-0007): `pnpm --filter @waste/db exec drizzle-kit generate --custom --name worker` made the empty file and its journal entry (and a snapshot identical to the last but for its ids, which is what drizzle-kit writes for a custom file), and the file's statements were copied from `src/sql/pgboss.ts`, the one spelling `worker-rendering.test.ts` holds it to — the fourth role, `wms_worker`, `BYPASSRLS` for the one kind of statement that reads across tenants, `SELECT` on every `wms` table present and future through a default privilege and no write right on any, `NOLOGIN` until `pnpm db:bootstrap` gives it a login from `WORKER_DATABASE_URL`, the API role's `search_path`, granted to the owner, its statements tolerating the race as the others' do; then pg-boss's own schema, `pgboss`, as `getConstructionPlans("pgboss")` of the pinned pg-boss writes it, installed by the owner because both processes run pg-boss with `migrate: false` and a role that owns nothing may not install it — the plan comes wrapped in pg-boss's own `BEGIN` … `COMMIT` with an advisory lock, which `pgbossStatementsOf` drops, since the migrator holds one transaction for the whole file and a `COMMIT` inside it would commit the journal's half-written state, and splits the rest at the top-level semicolons, dollar-quoted bodies whole; then `USAGE`, table and function rights on the schema for `wms_api` and `wms_worker`, present objects and future ones, and `CREATE` for neither, so partitioned queues and pg-boss's persisted statistics, which make tables as the caller, stay off. `pnpm --filter @waste/db pgboss-plan` prints the plan in that shape. pg-boss's `start()` refuses a `pgboss.version` other than the one the library expects, so a pg-boss upgrade that moves its schema version is a new file carrying `getMigrationPlans(PGBOSS_SCHEMA, PGBOSS_SCHEMA_VERSION)` through the same splitter, with `PGBOSS_SCHEMA_VERSION` moved beside it; the rendering test fails the merge when the pin and the dependency disagree, before the worker's start does.

## The Pilot

The hosted environment, the Pilot, is migrated through one door (Issue #152, decided in #133): the protected workflow `.github/workflows/pilot-database.yml`, whose `release` runs the journal check, an encrypted backup, `pnpm db:migrate` — the same migrator as everywhere else, every pending file in one transaction — and the journal check and the fingerprint again, under the `pilot` environment's owner URL, which lives nowhere else. The procedures, from a release to a restore, are `supabase/README.md`. The Supabase MCP replay of the earlier weeks is retired: it typed journal rows by hand and held no lock, and nothing here is ever applied that way again. The Pilot recorded `0000`–`0009` in that era, byte-equal to `main`'s files; `0010_finance`, `0011_worker` and `0012_generation` are applied by the first protected release, a database-only one. A hosted role's login is the `grant-logins` operation's, from the environment's app-role URLs — never bootstrap's, whose plans refuse any host but this machine's.

One thing 0011 owes a later file (found in the worker review of 2026-09-26, no number reserved yet): `src/sql/pgboss.ts` grants `wms_api` `SELECT, INSERT, UPDATE, DELETE` on every `pgboss.*` table where a `send` needs `INSERT` on `pgboss.job` and `SELECT` on `pgboss.queue` alone, so the API role can read every tenant's `pgboss.job.data` — the `RelayedEvent`s of every company, with no RLS on that schema — and the narrowing is a `REVOKE … FROM wms_api` plus the narrow grants in a new migration, never an edit of 0011.

## A merged migration is never edited

**A migration may be amended while it is inside an unmerged pull request and has only run on disposable CI databases. Once merged to `main` it is never edited: a correction is a new numbered migration, whether or not the Pilot has applied the original.** A change to an applied table is a new file — `pnpm db:generate` for what drizzle-kit can express, `pnpm --filter @waste/db exec drizzle-kit generate --custom` for an empty file to hand-write into — and the journal is append-only and monotonic (`src/__tests__/journal.test.ts` refuses a file the journal does not list and an entry whose `when` is not later than the one before).

drizzle-orm's migrator applies what is later than the newest row of its journal and never compares hashes, so on its own it would carry on over an edited file. The **journal check** (`src/journal-check.ts`) is what enforces the rule: `migrateDatabase` takes its advisory lock, runs the check and only then applies anything, and `pnpm db:check` asks the same standalone. It refuses an applied row whose `when` maps to no migration, to several, or to one another row already recorded; a hash that is not its file's sha256; a migration the migrator would skip for good; and a folder that disagrees with its own journal. Pending files pass. The fingerprint carries the journal's rows too, so an edited merged file also fails `fingerprint.test.ts`.

**A persistent local database with an old hash is reset, never accepted.** The shared local stack of the weeks before the check recorded files that were edited afterwards, and its journal is refused now; reset it: `pnpm db:stop --no-backup`, `pnpm db:start`, `pnpm db:migrate`, `pnpm db:bootstrap`, `pnpm db:seed` (`db:stop` alone keeps the volume). Never write a hash into a journal by hand, locally or anywhere.

### Correcting a migration

A merged migration that fails on the Pilot after a green CI run is environmental, and there are two corrections:

- **A precondition the Pilot's data does not meet** is mended by a repair module and then `release` runs again. A repair is `scripts/repairs/<issue>-<slug>.ts`, exporting `issue`, `description`, `precondition`, `apply` and `postcondition` (`src/pilot/repair.ts`), and one line in the allow-list, `scripts/repairs/index.ts`, importing it by its literal path, reviewed together. The `repair` operation resolves the id through that list alone, takes the migration lock and runs precondition → apply → postcondition in one owner transaction, rolling back when the apply or the postcondition fails, and logs the outcome and no row: needed → applied and verified; already applied → verified, nothing written; neither → refused without writing. A repair that has run is never deleted: once its postcondition holds and the migration that needed it is applied and verified, its line leaves the allow-list and the file moves to `scripts/repairs/applied/` with the issue and the release run that applied it, unchanged from then on.
- **A file the Pilot itself refuses** is the narrow exception for a merged migration the Pilot never recorded. Prove its hash was recorded by no environment that is not disposable — the Pilot's `check` shows its journal, and no other environment outlives a pull request — then revert the whole artefact on `main` in a new reviewed commit (the SQL file, its journal entry, its snapshot and the fingerprint), reissue the change under a new number, and reset every disposable database that recorded it. Never edit the merged file in place and never forge a journal row. Once any environment that is not disposable records the hash, correction is forward only.

Unqualified names in a generated file (`geometry(Point, 4326)`) resolve through the search path the migrator pins, `wms, extensions`; hand-written statements qualify what they name.
