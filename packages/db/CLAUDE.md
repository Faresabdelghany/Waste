# packages/db

Drizzle over postgres.js, server-only. `src/schema/` is the schema (`pgSchema("wms")`), `migrations/` the SQL the migrator applies, `src/seed/` the demo tenant, and `src/commands/` the write statements the API and the worker share.

Read `migrations/README.md` before adding a table, a column or a migration. It is the rulebook: who writes which statement, how keys carry the tenant, the file layout, and why a merged migration is never edited.

- There are two URLs. `DATABASE_ADMIN_URL` is the owner, for migrations, bootstrap and tests; `DATABASE_URL` is the API's role, `wms_api`. Migrations always run as the owner, because default privileges bind to the role that grants them. `wms_worker` reads across companies for the worker's sweeps, and `wms_sync` replicates for PowerSync. `wms_public` (ADR-0010) logs in as nobody: `wms_api` SETs it for a public request's transaction (`withPublishedProject`, `src/public-door.ts`), and its columns and policies are `src/sql/public-door.ts`'s, which `public-door.test.ts` holds the database to.
- Every table spreads the column sets in `src/schema/columns.ts` and carries its hand-written statements: the tenant fence (RLS), and either the `updated_at` trigger or, for a ledger (`recorded_at`), the revoke. `src/__tests__/hand-written.test.ts` fails with any missing statement printed verbatim; paste it below drizzle-kit's statements in the migration that created the table.
- Every table is classified for the audit trail in `src/sql/audit-trail.ts`: AUDITED, its trigger (`auditTrail(entry)`) in the migration that creates it and a set naming its parent, or EXEMPT with why; `audit-trail.test.ts` fails a table in neither. The trigger function reads the actor and the reason from `wms.user_account_id` and `wms.change_reason`, which `actAs` (`src/tenant.ts`) sets. `audit_event` is a ledger whose tenant key cascades, the schema's one cascade, and the reset to the seed sweeps it last. `AUDITED` is `[...AUDITED_AT_0019, ...<FEATURE>_AUDITED]`: 0019's rendering test reads the frozen list, each later migration writes its own triggers and its rendering test pins them, and a list is named after its feature, never its migration's number.
- A status or kind is text with a CHECK over the domain's tuple (`oneOf` in `src/schema/checks.ts`), which a new value changes in one constraint.
- A reference carries the tenant, and between project-scoped tables the project too, through `src/schema/references.ts`.
- Every object name goes through `src/names.ts`, which refuses a name longer than Postgres's 63 bytes where Postgres would truncate it silently.
- A statement Drizzle cannot build is a pure function in `src/sql/` with a test over its text.
- `withCompany(db, companyId, fn)` (`src/tenant.ts`) takes the pool and refuses a transaction, since the setting it makes would outlive a savepoint's release.
- Through the raw `sql` face, timestamps come back as Postgres text and a `Date` parameter is refused.
- A statement both processes run throws `Refused` (`src/commands/shared.ts`); each process turns it into its own answer.
- `src/jobs.ts` is the one spelling of enqueueing a pg-boss job inside a transaction: the Drizzle adapter, `createJobSender` (a pg-boss instance never started, over a pool, for the API), `sendGenerateRoutes` over `src/commands/generation.ts`'s queue and payload, `succeedInTransaction` (a running job completed and its successor sent under the same key, in one transaction), and `jobHeld`, the one question asked of pg-boss's job table outside pg-boss, by id or by singleton key. pg-boss is a runtime dependency for it, pinned exactly like the worker's.
- A message is queued only through `queueMessage` (`src/commands/messaging.ts`, #291 C15): the office's `POST /messages` and every later sender (invoice delivery, reminders, service notices) write the delivery log's row and its `messaging.send` job there, in one transaction, with the text rendered and the address copied. Consent is never judged at the queue: the worker's send judges it against the customer as they stand then. A sender on an outbox event names it (`sourceEventId`), so a customer is queued its message once per event; a Staff Notice (O16 of #290) is queued only through `queueStaffMessage` beside it, once per outbox event and user account.
- A Plan is asked for only through `ensurePlan` (`src/commands/plans.ts`): the office's requests `interactive`, generation's and the nightly sweep's `batch` (#172). Every sender's Plans then meet in one fingerprint cache; a second writer of `plan` rows would pay the provider twice for one answer.
- A photo's or a signature's bytes live in the private `proofs` Storage bucket (migration 0018), under the key the command names. Only the API signs for them (`src/storage.ts`), with `SUPABASE_SERVICE_ROLE_KEY`, server-side and never the web's. The worker's purge removes objects past `PROOF_RETENTION_DAYS` unless an open ticket names the stop, or the route for a route's own proof.
- `pnpm db:seed` writes on fixed UUIDv7 ids (`DEMO_IDS`, `src/seed/demo.ts`), so a test can name a seeded row without looking it up, and an upsert that would change nothing writes nothing. Its User Accounts are also the Pilot's, whose Logins carry the same reserved `.example` addresses, so an address changed here needs the owner to rename that Login on the Pilot. It writes configuration and identity only (#143): a reset leaves the tenant configured, never run. A set the API replaces whole under ids it mints — a calendar's holidays, a group's picks — goes through `replaceSets` (`src/seed/upsert.ts`), keyed by its content, so the next run survives the first edit made through the product. A system role's name and description are the tenant's once seeded, written on insert alone; its key, scope and grants are put back on every run, and the API refuses a change to the scope or the grants.
- The tests run against a real Postgres. The rendering tests pin DDL without one; the rest create a fresh database per file or share the local one, and `src/__tests__/specimen.ts` runs a specimen table inside a transaction that always rolls back.
- The reset to the seed (`src/reset-to-seed.ts`) sweeps every table of the schema in its foreign-key order except the eight in `KEPT_TABLES`, Organisation & Access, so a new table is swept without asking. A new table that belongs with the accounts, which a reset must keep, goes into `KEPT_TABLES`.
