# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The monorepo of a new WasteHero operations platform (waste/recycling logistics): the web app in `apps/web` (Next.js App Router, TypeScript, Tailwind CSS v4, shadcn/ui) and the beginnings of its backend in `apps/api`. The web app started as a small portfolio "project dashboard" template (see README.md) and has grown into a full multi-workspace prototype. It still runs on fixture data in `lib/data/` plus client-side stores persisted to localStorage and has no sign-in of its own (the `/login` account picker is a fixture until Issue 5); `apps/api` verifies Supabase access tokens and answers the Organisation & Access resources — company, projects, service providers, users, roles and their grants — beside its two probes and its OpenAPI document, over the eight tables of that context in `packages/db` (Issue #70) on the database foundation of Issue #64. The backend it will get is described in `docs/architecture/backend-architecture.md` and decided in `docs/adr/`.

## Commands

- `pnpm dev` — both servers through turbo: the web app at http://localhost:3000 and the API (`apps/api`, `tsx watch`) at http://127.0.0.1:3001; the API needs `DATABASE_URL` (see `pnpm db:start`) and `SUPABASE_URL` (the Supabase project whose Auth signs the tokens it verifies) and refuses to start without either. `pnpm --filter @waste/web dev` or `--filter @waste/api dev` runs one of them. The web script pins `-p 3000`, so a busy 3000 fails loudly instead of Next sliding onto 3001 (its fallback when no port is given) and colliding with the API. turbo runs tasks in strict env mode: `HOST`, `PORT`, `DATABASE_URL` and `SUPABASE_URL` reach the API from the shell only because `turbo.json` lists them on `@waste/api#dev` (which restates `cache: false` and `persistent: true`, since a package task does not inherit them from the root `dev` task); any new variable the API reads has to be added there too. The root `.env` reaches it without turbo: the API's `dev`, `start` and `test` scripts pass `--env-file-if-exists=../../.env` (after `watch` in the dev script: before it, tsx takes `watch` for the script path), and a variable set in the shell wins over the file.
- `pnpm build` — production build of the web app through turbo; `pnpm --filter @waste/web start` serves it. The API has no build step: it runs its TypeScript source through tsx (`pnpm --filter @waste/api start`), see Workspace packages below.
- `pnpm typecheck` — type check with TypeScript 7's native `tsc` (the `@typescript/native` alias). The `typescript` package itself is TypeScript 6 (`@typescript/typescript6`), kept because ESLint's TypeScript parser needs the JavaScript compiler API that 7 no longer ships; `tsc6` runs it for parity. Both aliases are declared at the root and in every workspace package (`apps/web`, `apps/api`, `packages/domain`, `packages/contracts`, `packages/tooling`, `packages/db`). `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm build` does NOT catch type errors; run the type check explicitly.
- `pnpm lint` — ESLint 9 with the Next rule set, one flat config at the repository root (`eslint.config.mjs`), run per package through turbo. Errors fail CI; warnings do not in `apps/web`, but the shared packages and `apps/api` run `eslint . --max-warnings 0`, so there a warning fails too. Every rule that is switched off or downgraded there carries the reason in a comment.
- `pnpm test` — unit tests on Node's built-in runner through tsx, one suite per package via turbo: `apps/web` (`lib/**/__tests__/*.test.ts`, 12 files, 67 tests), `packages/domain` (`src/**/*.test.ts`, 33 files, 234 tests, 6 of them the purity gate), `packages/contracts` (12 files, 97 tests, 6 the purity gate), `packages/tooling` (3 files, 58 tests: the gate's own specimens, the database-under-test rule, and the web database-fence specimen, which drives ESLint's Node API with `apps/web` and `apps/api` as cwd) and `apps/api` (`src/**/*.test.ts`, 16 files, 236 tests; the listen tests bind real ports, and the script sets `--test-timeout` so a leaked server fails the run instead of hanging CI; the readiness tests that need a database and the six route suites (`me`, `company`, `projects`, `service-providers`, `users`, `roles`, each minting its own tenants so files isolate on the shared local database) use `DATABASE_URL`, the API's own role, and skip with a visible reason when it is unset or fail when `REQUIRE_DATABASE` is set — one proof in `me.test.ts` takes `DATABASE_ADMIN_URL` as well, since only a role that bypasses RLS can show the principal lookup binding the claim to the tenant by itself; the rule is `@waste/tooling/database-under-test`, spelled once for `packages/db` and the API, each wrapping it in its own `src/__tests__/database.ts`, the API's adding `ownerUnderTest` for that one URL, loopback only; `turbo.json` declares `DATABASE_ADMIN_URL`, `DATABASE_URL`, `SUPABASE_URL` and `REQUIRE_DATABASE` on `@waste/api#test` with `cache: false`, and CI sets `SUPABASE_URL` to a placeholder, since these tests sign their own tokens against a key set they generate and never fetch one) and `packages/db` (`src/**/*.test.ts`, 20 files, 144 tests; the journal, bootstrap-plan, database-guard, EWKB, geometry-rendering, column-sets-rendering, organisation-access-rendering, statuses and hand-written tests need no database, the rest run against a real Postgres: they skip with a visible reason when `DATABASE_ADMIN_URL` is unset and fail instead when `REQUIRE_DATABASE` is set, which CI sets, so CI can never pass by skipping; the package's test, migrate, bootstrap and seed scripts pass `--env-file-if-exists=../../.env` (Node 22.9+, hence `engines` at the root), so the root `.env` reaches them without turbo, and `turbo.json` declares the three variables on `@waste/db#test` with `cache: false`, since a test against an external database has no cacheable inputs) as of 2026-09-24.
- `pnpm db:start` / `pnpm db:stop` — the local database: the Supabase CLI (a root devDependency, pinned; its binary arrives as a platform optional dependency, no install script) starts one Postgres 17 + PostGIS container, `supabase_db_waste`, on Docker, from `supabase/config.toml` (`project_id = "waste"`, `[db] major_version = 17`, the CLI's own migrations and `seed.sql` disabled: Drizzle owns both; `[auth] enable_signup = false` and `[auth.hook.custom_access_token]` naming `pg-functions://postgres/public/custom_access_token_hook`, neither of which `db start` reads: they are in the file because the decisions belong in the repository and `supabase config push` applies them to the hosted project). It is the database container only, no Auth or Studio; the same image as the hosted project. Port 54322; the URLs are in `.env.example`, copied to `.env` (gitignored; Node reads it through `--env-file-if-exists`). `pnpm db:migrate` applies `packages/db/migrations` through `packages/db/src/migrate.ts` (an advisory lock with a 60 s timeout serialises two migrators on one database; a transaction-pooler URL, port 6543, is refused because the lock needs one backend; its connections carry `search_path = wms, extensions` as a startup parameter, so an unqualified name in a generated migration resolves the way it does for the API role), `pnpm db:generate` runs `drizzle-kit generate` (never `push`: it would fight the hand-written statements), and `pnpm db:bootstrap` gives the API role `wms_api` (`API_ROLE` in `packages/db/src/roles.ts`) its local login with the password `DATABASE_URL` carries; the plan refuses a non-loopback admin host and a `DATABASE_URL` that logs in as anyone else, because on a hosted project that statement is run by hand with a real password. The database tests refuse non-loopback URLs too: they migrate, create and drop databases and reset the API role's password. `pnpm db:seed` writes the demo company through `packages/db/src/seed/demo.ts` as the owner (`DATABASE_ADMIN_URL`): WasteHero Denmark, its three projects, the two service providers, the eleven system roles with their 540 grant rows, and the two invited accounts (Olivia Larsen, the primary administrator with every project; Lars Mikkelsen with one Service Provider Access for NordRen), on ids spelled out as fixed UUIDv7 constants (a millisecond of 2026-09-24, the version and variant nibbles, then a digit per kind of record and an ordinal), so the local database and the hosted project hold the same tenant and a test can name a row without looking it up. It is idempotent — every upsert skips the write when the stored row already says what the run proposes, so a second run does not even move `updated_at` through the touch trigger — it runs against any host, loopback or hosted, unlike bootstrap, and it never touches an account's `auth_user_id` or `deactivated_at`, which belong to the access token hook and the API. CI runs it after `pnpm db:bootstrap`, which is also the step that would catch a seed that writes twice. `supabase stop` stops only this project's containers.
- `pnpm test:e2e` — Playwright against an already running dev server at http://localhost:3000 (no managed webServer; start `pnpm dev` yourself). `pnpm typecheck:e2e` type-checks the e2e folder, which the root tsconfig excludes.

pnpm is the package manager (pnpm-lock.yaml). If the volta pnpm shim fails ("Could not find executable"), `npm run <script>` works against the existing node_modules.

## Architecture

### Workspace shell — the core pattern

Nearly every top-level route in `app/` (`/operate`, `/plan`, `/fleet`, `/customers`, `/resources`, `/commercial`, `/improve`, `/configure`, `/control-center`, `/route-studio`, `/service-providers`, plus aliases like `/routes` and `/tickets`) is a thin server component that renders `WorkspacePageShell` (`components/wastehero/workspace-page-shell.tsx`) with a `workspaceId` and optional `initialModuleId`. Navigation inside a workspace is driven by `?module=` and `?record=` search params; some pages redirect specific module params to dedicated routes (e.g. `/?module=driver-app` → `/driver`).

The shell machinery lives in `components/wastehero/`:
- `business-workspace.tsx` — the generic module list/table/detail rendering used by every workspace
- `business-record-form-dialog.tsx` — create/edit dialogs generated from form schemas
- `restricted-workspace-shell.tsx` — separate restricted shells for the driver, portal, service provider, and control-center personas (`/driver`, `/portal`, `/service-provider-workspace`, `/control-center`)
- `map-planning/` — the Plan workspace's page since 2026-09-16 (`plan.map-planning`, the only Plan module): a MapLibre map of the container registry with clustering, a toolbar search (address, container id, planning area), filters, a collection window, rectangle/polygon selection that stays on the map and can be edited by dragging its handles, a Selected area panel (properties, collection points, containers, assumed/collected weight, volume, active agreements, containers by fraction from `@waste/domain/map-planning/statistics`; the Service Areas covering the selection from `@waste/domain/map-planning/coverage` — by planning area, or by a stored polygon; the dated Routes touching it by status, drawable stop-to-stop with "See on map", from `@waste/domain/map-planning/routes`; a Containers list by address), two-way hover highlight (a panel row highlights its markers or route line and a marker or line highlights its rows — one `Highlight` state in the view), named saved selections (shape + filters + window, browser-stored via `saved-selections.ts`), a Layers control (four keyless base maps; planning-area outlines derived as the convex hull of each area's located containers; a Routes layer drawing every drawable route in the collection window from `routesInWindow`, coloured by status bucket — awaiting amber, in progress blue, completed emerald — each line clickable for a route card; drawn Service Areas from `@waste/domain/map-planning/service-areas`; a Coverage gaps toggle from `@waste/domain/map-planning/coverage-gaps` — Available containers whose agreement is not ended/paused/future that no Validated/Scheduled/Effective scheme lists, red-ringed with cluster badges; a Route Schemes section where ticking two compares them via `@waste/domain/map-planning/scheme-compare` — A violet, B cyan, both rose, orphans inside the hull of both red-ringed, a strip at the top with the counts), and two hand-offs: the Guided Setup wizard and the Service Area create dialog (the domain's `serviceAreaSeedFromSelection` proposes a typed seed — project, planning-area ids, boundary line, polygon — and `serviceAreaFormValues` in `lib/data/service-areas.ts` maps it onto the form's field ids for BusinessWorkspace's `RelatedCreateTarget`, whose `extraValues` store the drawn polygon under `submittedValues.boundaryPolygon` — only map-created service areas carry one; the domain never writes a form id, since the schema is web-only and the dialog drops undeclared ids, and `lib/data/__tests__/service-area-seed.test.ts` holds the mapping against the schema). No zoom floor. Routes follow the roads: `road-geometry.ts` asks the keyless public OSRM demo server (car profile, no SLA; prototype only — the target system uses self-hosted Valhalla, see ADR-0002 and `docs/architecture/backend-architecture.md`) for the road through a route's stops in overlapping chunks, splits it into one leg per pair of stops, simplifies it, and caches it in memory and under `wastehero-map-road-geometry-v1`; `use-road-geometries.ts` fetches a few at a time and remembers refusals for the session; the map draws the road as an SVG path in world pixels at zoom 16 inside one translate-and-scale group (so the map is north-up and flat — rotation and pitch are disabled and must stay so), with a pending or refused road drawn straight and dashed. Route stops are records (order, kind, label, planned clock from the Scheduled fact, actual from Completed-at) — a pickup at no container is placed by its address only when the street is in the gazetteer, never hashed; the gazetteer is the web's (`FIXTURE_GAZETTEER` in `lib/data/street-gazetteer.ts`, mirroring the registry's seeded streets and explicit container fixtures) and is passed into every domain call that places a record — `containerLocation`, `containerPoints`, `planningAreaLayers`, `serviceAreasForSelection`, `routesInSelection`, `routesInWindow`, `compareSchemes` — because the domain cannot see the registry (Issue #58); `lib/data/__tests__/street-gazetteer.test.ts` holds table and registry together (no placed fixture container is hashed; the drawable fixture route days are exactly RC-1042, RC-1048, RC-1044); `playback.ts` drives the replay (playback bar, vehicle marker, travelled path bright). The planning questions asked of the records (what a selection contains, which service areas and routes touch it, coverage gaps, scheme comparison, positions derived from fixture addresses and never stored) are answered by `@waste/domain/map-planning/*` (see Workspace packages below); the map-view mechanics stay in `lib/map-planning/` (base maps, marker colours, clustering, number formatting, toolbar search, playback, road geometry, saved selections) and are pure too, just not domain. Fixture route days have a gazetteer stop or two, so the Routes layer lists them; E2E stubs OSRM per test and seeds a generated-shaped route through the record store. MapLibre's tile worker is served by `app/maplibre/[version]/[asset]/route.ts` because Turbopack breaks its module-worker URL — keep `setWorkerUrl` pointed there. Camera moves fall back to instant jumps until a style has loaded, because MapLibre runs no animation frames without one.

### Workspace packages (`packages/`)

- `packages/domain` (`@waste/domain`) — the pure planning logic of ADR-0002. `lib/route-schemes` moved here 2026-09-17 (Issue #45, slice 3) as `src/route-schemes/`, with `record-visibility`, `service-frequencies`, `business-filters`, `record-values` (`EMPTY_FACT`, `cleanFact`, `typedString`, `uniform` — one rule for facts and typed values, blank or the placeholder is absent; the readers Issue #58 enumerated moved here, and the ones with a different contract say so in the header) and `text` (`count`, one place to spell a count — the caller spells an irregular plural) beside it, and the thirteen pure `lib/map-planning` modules followed as `src/map-planning/` (slice 4); import them as `@waste/domain/route-schemes/<module>`, `@waste/domain/map-planning/<module>` and `@waste/domain/<helper>`. The package ships TypeScript source (`exports` maps `./*` to `./src/*.ts`; Turbopack and tsx read it directly, there is no build step) and depends on nothing. The purity gate from `@waste/tooling` keeps it that way (see below): `src/__tests__/purity.test.ts` is the one call that registers it, with no package allowed in shipping code and only `@waste/tooling` allowed in tests. `src/prototype-record.ts` holds the transitional `BusinessRecord` type, which `lib/data/business-modules` re-exports so web imports did not change; do not grow it into a registry. Issue #70 (2026-09-24) added `src/access/` and `src/ids.ts`, pure like everything else here. `access/modules.ts` is the permission vocabulary: `MODULE_KEYS`, the fifty `workspace.module` keys of the prototype's permission matrix in sidebar order (the standalone Control Center workspace is left out, since Configure already carries `configure.control-center`), `WORKSPACE_KEYS` and `modulesOf` derived from them, and `ACTIONS` (`view`, `edit`, `create`, `delete`); the list lives here and not in the database, where `role_grant.module_key` is text, so adding a module is a code change and never a migration. `access/grants.ts` holds `Grant` and the one spelling of the rule that edit, create and delete imply view: `normaliseGrants`, which the seed, the API's request path and `PUT /roles/:id/grants` all write through, so a grant set is the same whichever door it came through; `mergeGrants` beside it only tidies (one entry per module, actions in `ACTIONS` order, sorted, an empty grant dropped), so a charter can be read as written and a test can hold every charter already normalised. `access/system-roles.ts` is `SYSTEM_ROLE_KEYS` and `SYSTEM_ROLES`, the eleven seeded roles with their copy and 540 default grant rows between them, moved out of `apps/web/lib/data/role-permissions.ts`. `src/ids.ts` is `mintId(unixMillis, randomBytes)` and `nextId(previous, unixMillis, randomBytes)`, UUIDv7 laid out as RFC 9562 §5.7 says with §6.2's monotonic-random rule — two ids minted in the same millisecond count up over the 74 random bits, carrying past the variant and version bits and into the clock when the field is full — written lowercase, so the string order is the mint order and a cursor over `id` is a cursor over time; `apps/api/src/ids.ts` is the only place that supplies `Date.now` and `crypto.getRandomValues`. The `__tests__` directories are hidden from consumers by `null` exports.
- `packages/contracts` (`@waste/contracts`) — the wire primitives shared by `apps/web` and `apps/api` (Issue #45, slice 5, 2026-09-17), on zod 4; `zod` was its only dependency until `permissions.ts` reached for the domain's vocabulary (Issue #70), and `apps/web` dropped its unused zod 3 the same day, so the web app meets zod only through these schemas. Modules, imported as `@waste/contracts/<module>`: `ids` (`Id`, a UUID version 7 normalised to lowercase — minted by the server for web writes and by the driver's device for offline commands per ADR-0004; no generator here), `dates` (`IsoDate` calendar day, `IsoDateTime` RFC 3339 with seconds and a UTC offset; a wall-clock time without an offset is rejected), `geojson` (`Longitude`, `Latitude`, `Position` = `[lng, lat, alt?]`, `Point`, `LinearRing` of four or more positions closing on the first with three distinct, `Polygon` with an outer ring and holes; unknown members such as `bbox` are dropped on parse; the prototype's unclosed `{ lng, lat }[]` boundaries are not this shape yet — where they become a ring is decided with the tables that store them, build-order step 3 of `docs/architecture/backend-architecture.md`), `pagination` (`PageRequest` with `limit` a whole number or a string of decimal digits, 1..200, default 50, empty or null meaning not given, nothing else coerced, and an opaque optional `cursor`; `Page(item)` = `{ items, nextCursor }` with `null` on the last page), `health` (`HealthResponse`, the body of the API's `GET /healthz`: `status: "ok"` and the server's clock as an `IsoDateTime`; `ReadyResponse`, `UnavailableResponse` and the discriminated union `ReadinessResponse` over them, the two bodies of `GET /readyz`). Issue #70 added six more: `permissions` (`ModuleKey = z.enum(MODULE_KEYS)`, `Action = z.enum(ACTIONS)` and `Grant = { moduleKey, actions }` — the domain's vocabulary turned into the check the API boundary runs, so an unknown key never reaches `role_grant`), `problem` (`Problem`, RFC 9457 `{ type, title, status, detail?, errors? }` with `errors` a list of `{ path, message }`, plus `ProblemFieldError`, `PROBLEM_MEDIA_TYPE` = `application/problem+json` and `BLANK_PROBLEM_TYPE` = `about:blank`, every problem being the generic one for its status until a client needs to tell two apart), `me` (`Me`: the caller's `user` with a `status` of literally `active`, `company`, `role` with its normalised `grants`, `projects` and `serviceProvider` or null), `organisation` (`CompanyStatus`, `ProjectStatus`, `Company`, `CompanyPatch`, `Project`, `ProjectCreate`, `ProjectPatch`, `ServiceProvider`, `ServiceProviderCreate`, `ServiceProviderPatch`), `access` (`UserStatus` — `invited`, `active`, `deactivated`, derived and never stored — `User`, `UserInvite`, `UserPatch`, `Role`, `RoleCreate`, `RolePatch`, `RoleGrants`) and `text` (`Label`, the one spelling of a piece of text a person typed — present, not whitespace only, at most 200 characters, and stored exactly as it arrived, since trimming would answer something the body did not say; `organisation`, `access` and `me` all take it from there, so a resource and the summary of it in `Me` cannot drift apart). Three shape rules run through `organisation` and `access`: a resource carries what the server owns (its `Id`, its `IsoDateTime` stamps) and a write body only what a caller may say, every write body being a `z.strictObject`, so a member the server owns is refused by name instead of dropped; a patch is every field optional with a `.refine` for "give at least one", whose issue path is `""`, the body as a whole, and the access shape is held to one way of reaching something: `UserInvite` to exactly one of `allProjects: true`, `projectIds` and `serviceProviderId`, `UserPatch` to at most one, since a patch that names none of the three leaves the account's access alone; and a coded field is checked by shape, not against a registry it would have to ship — country `/^[A-Z]{2}$/`, currency `/^[A-Z]{3}$/`, language a BCP 47 tag, timezone an IANA name, `contactEmail` `z.email()`. Schemas are written `import * as z from "zod"` so a bundler can drop what a consumer does not use. Same source-shipping layout and `tsconfig.json`/`tsconfig.test.json` split as domain, same purity gate with `allowedImports: ["@waste/domain/access/modules", "zod"]` (exact specifiers, so `zod/v3` and `zod/mini` are refused, and any further reach into the domain is a deliberate new line there; the gate also insists that `dependencies` be exactly the packages of that list, which is why `@waste/domain` is a dependency and not a devDependency — the innermost ring depends on nothing, so the direction is sound). Organisation & Access is the first context with module schemas; the rest derive from their form schemas when their tables are designed, from build-order step 3 on. `apps/web/lib/map-planning/road-geometry.ts` types OSRM coordinates as the contracts `Position` through a type-only import and checks the shape structurally: a runtime zod import would land about 90 KB gzipped in the client bundle of every workspace route, so the web app has no runtime consumer of the schemas until a real one exists.
- `packages/db` (`@waste/db`) — the database foundation of Issue #64 (2026-09-18, slice 1): server-only, consumed by `apps/api` and later the worker, never by `apps/web` (ADR-0001: `eslint.config.mjs` refuses `@waste/db`, `drizzle-orm` and `postgres` under `apps/web/**` with the ADR as the message, and `packages/tooling/src/__tests__/database-fence.test.ts` is the specimen proving the rule fires there, a type-only import included, and not under `apps/api`). Drizzle 0.45 on postgres.js (`prepare: false`, `casing: "snake_case"`), drizzle-kit for `generate` only (`drizzle.config.ts` carries exactly what `generate` reads: dialect, schema, out, casing; the journal's name lives in `src/migrate.ts`). The two faces of `createDb` share Drizzle's codecs: through the raw `sql` face, temporal values arrive as Postgres text and a Date parameter is not accepted (pinned by a test). `src/schema/wms.ts` is `pgSchema("wms")`, the domain schema that Supabase never exposes and never grants to `anon`, `authenticated` or `service_role`; `src/client.ts` `createDb(url, { max, onnotice, searchPath, connectTimeoutSeconds, backoffSeconds })` → `{ db, sql, close }` (Drizzle over the pool, postgres.js itself for statements Drizzle has no builder for, idempotent close with a 5 s end timeout; `searchPath` goes out as a startup parameter, which outranks the role's setting and which Supabase's poolers forward in session mode; `connectTimeoutSeconds` is postgres.js's `connect_timeout`, default 30, and `backoffSeconds` a fixed wait before the dial after a failure where postgres.js's own backoff grows towards 20 s across the pool's connections, both there for the API's probe pool); `src/casing.ts` `CASING` (`snake_case`), the one spelling drizzle-kit, the client, the specimen tests and any code that names a database object share; `src/migrate.ts` `migrateDatabase(url, { onnotice })` applies `migrations/` through drizzle-orm's migrator into the `drizzle.__drizzle_migrations` journal under `pg_advisory_lock` (60 s `lock_timeout`, the unlock result checked, transaction-pooler URLs refused); the migrator applies by journal `when` and never compares hashes, so `src/__tests__/journal.test.ts` refuses a non-monotonic journal or an unlisted file and the hash test proves a fresh database records each file's sha256; `src/bootstrap.ts` `grantLogin(adminUrl, { role, password })` runs `ALTER ROLE ... LOGIN PASSWORD` with the password passed as a parameter into a transaction-local setting and spliced by `format(%L)` inside the database. Migrations: `0000_wms` (generated: `CREATE SCHEMA "wms"`) and `0001_foundation` (hand-written, one statement per `--> statement-breakpoint`): extensions `postgis` and `btree_gist` in `extensions`; `wms.uuidv7()` in pure SQL (Postgres 17 has no native one; 18 does) and `wms.current_company_id()` (`current_setting('wms.company_id', true)`, blank is null, the tenant fence's input) as SQL-standard `BEGIN ATOMIC` bodies with no `SET search_path`, so the planner inlines them (a test reads the plan; a SQL function with a SET clause never inlines, and these run per row), `wms.touch_updated_at()` in plpgsql; a guard that fails the migration when PostGIS or btree_gist already lives outside `extensions`, because `CREATE EXTENSION IF NOT EXISTS ... WITH SCHEMA` is a silent notice then; the API role `wms_api` created `NOLOGIN` with `USAGE` on `wms` and `extensions`, default `SELECT, INSERT, UPDATE, DELETE` on future `wms` tables and `USAGE, SELECT` on sequences (defaults bind to the grantor, which is why migrations always run as the owner), `search_path = wms, extensions`, no `BYPASSRLS`, owner of nothing, granted to the owner so a test can `SET LOCAL ROLE wms_api` inside the transaction that created its specimen table (role settings apply at login, so such a test sets `search_path` itself); the role statements tolerate the concurrent-creation race, since roles are cluster-wide and the migrator's lock is per database; `REVOKE ALL ON SCHEMA wms FROM PUBLIC`. Two connection strings: `DATABASE_ADMIN_URL` (owner: migrations, bootstrap, tests) and `DATABASE_URL` (`wms_api`: the API). Geometry (slice 2, 2026-09-18): `src/schema/geometry.ts` exports `geometry.point()` and `geometry.polygon()`, Drizzle custom types typed as the contracts' `Point` and `Polygon` (`@waste/contracts/geojson`, a type-only import, so `@waste/db` depends on `@waste/contracts` but never runs zod), `geometry(Point, 4326)` / `geometry(Polygon, 4326)` in the database. Writes go through `extensions.st_geomfromgeojson` as one GeoJSON parameter, which reads a crs-less GeoJSON as SRID 4326 (no `ST_SetSRID`: a mislabelled geometry is refused by the type modifier, SQLSTATE 22023, like a wrong shape or a third dimension, the columns being flat); before serialising, a non-finite ordinate is refused and a trailing undefined altitude dropped, since JSON would make either null and PostGIS 0. ### The API (`apps/api`)

`apps/api` (`@waste/api`) is the Hono API of ADR-0001, the only web boundary to domain data, scaffolded 2026-09-17 (Issue #45, slice 6), connected to the database 2026-09-24 (Issue #64, slice 4), and given its authentication, its error shape and the Organisation & Access resources the same day (Issue #70, slices 3 to 5). `GET /healthz` answers the contracts `HealthResponse` (liveness: the process answers, with its clock); `GET /readyz` answers `ReadinessResponse` (readiness: `checkDatabase` in `src/readiness.ts` runs `select 1` through a pool's raw `sql` face bounded by `DATABASE_CHECK_TIMEOUT_MS`, 2 s, under every common balancer's probe timeout; a probe the bound overtook is left to settle, never cancelled, because postgres.js's cancel strands a connection whose startup query it was and, for a sent query, dials a cancel connection whose dropped promise would be an unhandled rejection when the stalled database refuses it, killing the process; instead the probe runs on its own pool, `probePoolOptions(timeoutMs)` = `{ max: 1, connectTimeoutSeconds: timeoutMs / 1000, backoffSeconds: 1 }`, so probes never take a request's connection, a hung dial ends with the bound rather than after 30 s, and a database that comes back is seen within a second where postgres.js's own backoff would grow towards 20 s; 200 `ReadyResponse` `{ status: "ok", checks: { database: "ok" } }` or 503 `UnavailableResponse` `{ status: "unavailable", checks: { database: "unreachable" } }`, the two members of the contracts' discriminated union, so a body whose status disagrees with its check does not parse; a refused connection answers in milliseconds, a hung one at the bound, and `/healthz` keeps answering either way); `GET /openapi.json` is generated at request time by hono-openapi from the `describeRoute` description beside each route, so a described route is always in the published contract: the generator's static-file heuristic (drop a path whose last segment has a dot) is switched off, and only described routes appear, a described OPTIONS handler being the one thing it leaves out (a test validates the document against the OpenAPI 3.1 schema through `@seriousme/openapi-schema-validator`). The generator's own 400 envelope for validated routes is switched off too, because a 400 is a problem like every other error and the route that validates describes it. The document carries `components.securitySchemes.bearerAuth` (`type: http`, `scheme: bearer`, `bearerFormat: JWT`) and every route but the probes declares it: a test walks the document and counts 22 secured operations over its 15 paths, `/healthz` and `/readyz` the only open ones (`/openapi.json` is undescribed, so it is not a path of its own document). `src/env.ts` reads the process environment once at startup through a zod schema: `HOST` (default `127.0.0.1`; a container sets `0.0.0.0`; an IP address or host name, no brackets, scheme or IPv6 zone id, because a zone id has no URL spelling), `PORT` (default 3001), `DATABASE_URL` (required, no default: a `postgresql://` or `postgres://` URL with a host, the `wms_api` role's connection string, checked for shape only, since whether it answers is `/readyz`'s question on every probe; the transaction pooler is not refused here, unlike in the migrator, because `prepare: false` keeps the client valid behind it) and `SUPABASE_URL` (required, no default: the origin of the Supabase project whose Auth signs the tokens — `http` or `https`, a host, and nothing else, a trailing slash refused rather than stripped so the one spelling in `.env` is the one the issuer is compared against, and a path, query, fragment or credentials refused too), an empty variable counting as unset (applied once for every variable, so a new field is a plain schema with a default, or without one when the process cannot run without it) and every other variable dropped; a bad or missing value stops the process with the variable named. `src/app.ts` builds the app (`createApp({ probe, pool, verifier, now, databaseTimeoutMs, log })`: `probe` and `pool` are both a `Database` from `@waste/db/client`, the first what `/readyz` probes and the second what every authenticated request opens its transaction on, and the app connects on neither by itself, so a test hands a route that asks nothing of the database pools that go nowhere; `verifier` is injected too, so a test verifies against a key set it generated and the app never reads `SUPABASE_URL`; the clock is injected so tests pin it, the bound is interpolated into `/readyz`'s OpenAPI description so the document states the one in force, and `log` is where a 500's cause goes, `console.error` unless a test wants to look), `src/listen.ts` binds it on Node's own http server through node-server's request listener with the global `Request`/`Response` override off (`port: 0` gives an ephemeral port; the returned `close()` is idempotent, releases the port at once, drops idle keep-alive connections, waits up to `SHUTDOWN_GRACE_MS` (5 s) for requests in flight and then cuts the rest, so a stalled client cannot hold the process past its host's deadline), and `src/server.ts` is the composition root, the one file without tests: it opens the probe pool with `createDb(env.DATABASE_URL, probePoolOptions(DATABASE_CHECK_TIMEOUT_MS))` and the request pool with `createDb(env.DATABASE_URL)` before binding (postgres.js dials on the first query, so the process starts with the database down and `/readyz` says so) and builds the verifier over `createRemoteJWKSet` of the project's key set, and it shuts down on SIGINT and SIGTERM through `process.on`, so a signal delivered twice (a terminal Ctrl-C plus tsx's relay of it) joins the one shutdown instead of killing the process mid-drain: the listener drains and the probe pool closes together (a probe is not a request, and 503 is the right answer to one arriving mid-shutdown, so the two 5 s ceilings overlap instead of adding up), the request pool closes after the listener, so a request in flight keeps the connection its transaction runs on until it has answered; every failure is printed and any failure exits 1. Authentication and the request path (slice 3). A route takes `Authorization: Bearer <Supabase access token>`; `src/auth/verify.ts` verifies it with `jose` — `jwtVerify` against the project's key set, `issuer` `${SUPABASE_URL}/auth/v1`, `audience` `authenticated`, algorithms `ES256`, `RS256` and `EdDSA` only, so a token signed with a shared secret is refused before any key is looked up. `server.ts` builds the key set with `createRemoteJWKSet` (jose caches it, refetches on a `kid` it has not seen and rate-limits that refetch, which is what Supabase's edge cache and rotation guidance need, where Hono's own `jwk` middleware refetches per request) and a test with `createLocalJWKSet`, both behind the injected `Verifier`, which answers verified claims or a refusal with a reason and a sentence for the problem body, never the token itself; a key set that cannot be fetched is thrown, since it says nothing about the token, and becomes the server's 500. `src/auth/principal.ts` is the guard each authenticated route puts before its handler, never on a wildcard, so the probes and the document need no token and an unknown path stays a 404: it reads `sub` and `app_metadata.company_id`, opens `withCompany(companyId)` on the request pool, and `resolvePrincipal` looks the account (active, bound to that login), its role and normalised grants, its projects (all of the company's when `all_projects`, else its Project Access rows) and its Service Provider up inside it — every lookup carrying an explicit `company_id = companyId`, so the API binds the claim to the tenant itself and the fence is the second stop, not the only one (ADR-0001). The handler receives that same transaction as `tx` on the context and opens none of its own; after `next()` the middleware discards it (a private `Discard` thrown out of `withCompany`) when the context carries an error or the response is 400 or worse, so a failed request leaves nothing behind whether the handler threw a problem or returned one. Nothing is cached, so a revoked grant or a deactivated account is refused on the very next call. `src/auth/require.ts` `requireGrant(moduleKey, action)` reads the resolved grant set and nothing else; its arguments are the domain's literal types, so a typo in a route is a compile error rather than a route nobody can reach. `src/problem.ts` is the error shape the #45 and #64 scaffolds deferred: RFC 9457 Problem Details in the contracts' `Problem`. A handler throws `problem(status, { detail, errors, headers })`; `errorHandler` turns a `ProblemError` into its own response, one of Hono's `HTTPException`s into a problem of its status, SQLSTATE 23505 into a 409 naming the constraint, and anything else into a 500 with no detail and a projection of the error logged (`loggable`: name, message, SQLSTATE, constraint and stack, and the same of its cause — never postgres.js's statement or the `parameters` it bound, which on a failed `POST /users` would be the invitee's address and name). `notFound` answers an unknown path as a problem too; `validate(target, schema)` is hono-openapi's validator with `validationHook`, which turns zod's issues into a 400 listing `errors: [{ path, message }]`, the path dotted into the target (`projectIds.1`) and empty for the target as a whole; `describeProblem` is the OpenAPI response object for one. A 401 carries `WWW-Authenticate` in RFC 6750's three spellings — `Bearer` when no header was sent, `Bearer error="invalid_request"` when the header is not one Bearer token, `Bearer error="invalid_token"` when a token was presented and refused — while a valid token with no company claim is a 403 saying the token names no company, and an unknown `sub`, a `sub` that is not a UUID at all, a deactivated account and a company the account is not in are the one other 403, "No active account in this company is bound to this login" — same status either way, since a better token would not help. The routes. `GET /me` (slice 3) answers the contracts' `Me`, the Principal on the wire, and needs no grant. Ids for web writes are minted by the server: `src/ids.ts` is the impure half of `@waste/domain/ids`, holding the last id so a burst inside one millisecond counts up instead of scattering, and a route writes `id: newId()` into the insert. Lists answer the contracts' `Page(item)` through `src/pagination.ts`: rows ordered by `id` ascending, which for a UUIDv7 is the order they were made in, the cursor base64url of the last item's id, a cursor that is not one of ours a 400 naming `cursor`, and `fetchLimit`/`pageOf` asking for one row more than the page to learn whether there is a next one — no offsets, which drift under inserts, and no total, which a list view does not need. Test helpers: `src/__tests__/unreachable.ts` gives `REFUSED_URL` (loopback port 1, which needs root to bind and nothing binds, so a dial is refused at once and no just-released port can be taken by a sibling process) and a silent server (accepts, never answers; a test ends such a pool with `sql.end({ timeout: 0 })` before closing the server, since `close()` would wait out its 5 s grace on a connection that is hung by construction and a socket dropped first would make postgres.js reconnect); `tokens.ts` mints an ES256 key pair and signs Supabase-shaped tokens against it (`signingKeys`, `signToken`, and `neverVerifies` for an app whose routes under test present none); `tenant.ts` seeds a whole company under `withCompany` as `wms_api` — three projects, two providers, three roles and five accounts, every e-mail on a random `.example` domain — and drops it again, so files isolate by tenant on the shared database; `calls.ts` `callingAs(app, keys, account, companyId)` is one account's way of calling the API, a fresh token per call, so a test can also call with a claim naming a company the account is not in; `read-problem.ts` asserts the problem media type and parses the body with the contracts' `Problem`; and `database.ts` adds `ownerUnderTest` beside `databaseUnderTest`. The package runs its TypeScript source through tsx (`dev` is `tsx watch`, `start` is `tsx`, so tsx is a runtime dependency) and has no build step: the workspace packages ship source, so a Node build would have to bundle them, and that is decided together with hosting. Runtime dependencies: `@waste/contracts`, `@waste/db`, `@waste/domain` (the vocabulary and the grant rule), `drizzle-orm` (the API writes its own queries; pinned to `packages/db`'s range so one instance resolves), `hono`, `@hono/node-server`, `hono-openapi`, `jose`, `zod`, `tsx`.

### Data registries (`lib/data/`)

- `business-modules.ts` (~4200 lines) — the central registry: workspaces → modules → fixture records, plus the fixture company, project, and service provider IDs used for per-record scoping (`FIXTURE_COMPANY_ID`, `FIXTURE_PROJECT_IDS`, `FIXTURE_SERVICE_PROVIDER_IDS`).
- `business-domain.ts` — machine-readable map of every UI surface to canonical business modules M01–M24 (owners, personas, dependencies, boundaries). Consult it before moving features between workspaces — it defines canonical ownership and known boundary corrections. `settingsModuleDomains` lists the modules that keep real business records but are managed from Settings (registered under the `configure` workspace, e.g. `configure.areas` — Areas & Zones, moved from Plan 2026-09-03); the schema registry's lockstep gate counts their keys as expected, and `lib/data/planning-areas.ts` is the only place that knows where planning areas live.
- `business-form-types.ts` + `business-form-schemas*.ts` — form field schemas per module, split across files by domain area.
- `role-permissions.ts` — the Settings permission matrix. The catalogue of rows is still derived from `businessWorkspaces`, but the seeded defaults are imported from `@waste/domain/access/system-roles` (Issue #70) and keyed `role-<key>` instead of being spelled here; `ROLE_PERMISSION_ACTIONS`, `rolePermissionSections`, `isRoleAccessMap`, `defaultAccessForRole` and `effectiveRoleAccess` kept their signatures. `lib/data/__tests__/permission-catalogue.test.ts` holds the web's `workspace.module` keys and the domain's `MODULE_KEYS` equal in both directions, so a module added to a workspace fails a test until the vocabulary names it. This and that test are all #70 changed in the web: the `/login` picker, `demo-accounts.ts`, the organisation store and every persona stay on fixtures until Issue 5.
- `legacy-ids.ts` — old → new id maps and `migrateLegacy*` helpers from the 2026-09-02 terminology rename plus the 2026-09-03 Areas & Zones move (`plan.areas` → `configure.areas`; see Client-side state below). The only place the retired ids are defined; the stores import it and carry only their own `LEGACY_*` display-string maps and legacy shape guards (the full list of sanctioned exceptions is under Client-side state).
- `projects.ts`, `clients.ts`, `project-details.ts`, `sidebar.ts` — fixture data for the legacy dashboard surfaces.

### Client-side state

`app/layout.tsx` wires the global providers: `BusinessRecordStoreProvider` (merges fixture records with user-created records per `workspace.module`, persisted to localStorage under `wastehero-business-records-v1`), `OrganizationStoreProvider` and `AssetManagementStoreProvider` (settings state), plus theme providers. All persistence is browser-local.

**Terminology rename (2026-09-02): Contractor → Service provider, Contract area → Service area.** The rename changed the workspace id (`contractors` → `service-providers`), module ids (`contract-areas` → `service-areas`, `contractor-workspace` → `service-provider-workspace`, `contractor-prices` → `service-provider-prices`), record-id prefixes, enum literals, and routes (`/contractors` → `/service-providers`, `/contractor-workspace/*` → `/service-provider-workspace/*`). Fixtures and code use the new ids only, but browser-local state and bookmarks written before the rename still carry the old ones, so: stores that persist ids must run loaded state through `migrateLegacyState` (or `migrateLegacyRecordBuckets` for record buckets) from `lib/data/legacy-ids.ts`; `business-workspace.tsx` normalises `?module=`/`?record=` params through `migrateLegacyModuleId`/`migrateLegacyId`; and `next.config.mjs` redirects the old routes. Do not reintroduce the old terms anywhere else — the only sanctioned exceptions are: `lib/data/legacy-ids.ts` (the sole definition of the retired ids); the redirect sources in `next.config.mjs`; the store-local `LEGACY_*` maps and shape guards that feed the migrate helpers (`LEGACY_ROLE_NAMES`/`LEGACY_ROLE_SCOPES` in `components/settings/organization-store.tsx`, `LEGACY_SCOPE_KEYS` in `components/wastehero/active-routes-store.tsx`, `LEGACY_RECORD_KEY_RENAMES` in `components/wastehero/business-record-store.tsx`); the legacy `wastehero-contractor-active-routes-v1` storage key that `active-routes-store.tsx` keeps for backward-compatible reads; and explicit historical notes that say the term was renamed. Do not strip those maps — the stores need them to migrate persisted state.

**Collection Calendars move (2026-09-16): `plan.calendars` → `configure.calendars`.** When Plan became Map Planning, Collection Calendars re-homed to Settings → Operations → Collection calendars (pane `collection-calendars`, rendered by `components/settings/collection-calendars-settings.tsx`); record ids did not change and generation, the wizard, and Plan Ahead still read the records. Resolve the location through `COLLECTION_CALENDARS_MODULE` in `lib/data/collection-calendars.ts` — never hard-code the pair. Persisted state follows through `lib/data/legacy-ids.ts` exactly like the Areas move below (`LEGACY_MODULE_KEYS`, `migrateLegacyState`, `hasLegacyIds`, and `migrateLegacyHref` sending `/plan?module=calendars[&record=…]` to `/settings?pane=collection-calendars[&record=…]`).

**Areas & Zones move (2026-09-03): `plan.areas` → `configure.areas`.** The module left the Plan workspace for Settings → Operations → Areas & Zones; record ids did not change. Persisted state follows through the same `lib/data/legacy-ids.ts` seam: the `LEGACY_MODULE_KEYS` entry moves the record-store bucket and role-access keys, `migrateLegacyState` rewrites stored `relationRefs` whose `workspaceId`/`moduleId` pair names the old home, `hasLegacyIds` detects both shapes, and `migrateLegacyHref` sends `/plan?module=areas[&record=…]` to `/settings?pane=areas[&record=…]` (`app/plan/page.tsx` redirects server-side). Never hard-code the pair again — resolve it through `PLANNING_AREAS_MODULE` in `lib/data/planning-areas.ts`.

### Legacy vs canonical surfaces

The original portfolio dashboard still exists alongside the WasteHero prototype: `/projects/[id]`, `/clients`, `/tasks`, `/performance`, and components like `projects-content.tsx` and `project-timeline.tsx`. These are legacy — notably, the records under `/projects/:id` are Routes in domain terms, not Projects. In WasteHero language a "Project" is an operating scope (municipality, contract, region), never a route.

### Domain language

`CONTEXT.md` is the canonical glossary. Every term lists _Avoid_ synonyms — use the exact terms in UI copy and identifiers (e.g. Agreement vs Subscription, Route Scheme vs Route, Warehouse vs Depot, Ticket vs Alert).

### Next.js configuration (`apps/web/next.config.mjs`, 2026-09-17)

- **React Compiler** is on through Turbopack's Rust port (`reactCompiler`, `experimental.turbopackRustReactCompiler`). Components that break the hooks rules are skipped by the compiler, so the `react-hooks/*` lint warnings mark code the compiler cannot optimise.
- **Cache Components and Partial Prefetching** are on (`cacheComponents`, `partialPrefetching`). Every `page.tsx` and the root layout export `instant = false` (added by the `cache-components-instant-false` codemod), so routes may still block on request data; removing an opt-out means making that route's dynamic parts stream behind Suspense. Both workspace shells wrap `BusinessWorkspace` in `<Suspense>` because it reads `useSearchParams`, which is request data under this model. Routes stay mounted across client navigations (React `<Activity>`), so component state persists when the user navigates back.
- **`experimental.useOffline`** keeps failed navigations and Server Actions pending until the connection returns instead of throwing.
- `next dev` maintains `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` (managed block pointing at the bundled Next docs); they are committed on purpose.
