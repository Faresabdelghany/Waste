# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The monorepo of a new waste and recycling operations platform, working name Waste (the `@waste/*` namespace): the web app in `apps/web` (Next.js App Router, TypeScript, Tailwind CSS v4, shadcn/ui) and the beginnings of its backend in `apps/api`. The web app started as a small portfolio "project dashboard" template (see README.md) and has grown into a full multi-workspace prototype. It still runs on fixture data in `lib/data/` plus client-side stores persisted to localStorage; since Issue #81 (2026-09-25) the record store behind every workspace has a server-backed half, switched module by module onto `apps/api`, and `/login` signs a real account in through Supabase Auth beside the fixture account picker — four modules read the API when a person is signed in and an API is configured (Company & Projects, Users & Roles, Service Providers, Contacts & Companies), every other module and every persona stays on fixtures, see Client-side state; `apps/api` verifies Supabase access tokens and answers the Organisation & Access resources — company, projects, service providers, users, roles and their grants (Issue #70) — the Registry's — the catalogue, customers and their properties, agreements and subscriptions, containers and their effective-dated service placements (Issue #78) — Planning's — planning areas and their effective-dated boundaries, collection calendars and their holidays, route schemes with their collection groups and each group's stop matching rule or picked containers, and the pure occurrence preview (Issue #97, part A; the generation worker is part B and waits for a host) — and Resources' — vehicle types with their container-type compatibility, warehouses, depots and unloading stations, vehicles with their compartments and drivers, the container's lifecycle commands over the append-only Stock Movement ledger with the Container Asset State read off it, and vehicle allocations with their appended events (Issue #101) — and Execution's — the dated routes (the day's work, one per collection group per operating date, `planned → ready → active → completed | cancelled`) with their pickups, the pickups' outcomes and proofs of service, the driver's sessions, the unloads, the driver's device-minted idempotent commands with their receipts, and the outbox the other contexts will hear from (Issue #104, part A; the PowerSync sync rules are part B and the relay part C) — and Resolution's — the tickets, each the case that owns a request, a deviation or a complaint, with its appended history of status changes, assignments and comments and the alerts linked to it, opened by the office or, once the outbox has a consumer, from an execution event (Issue #109, part A; the consumer on the worker is part B and waits for a host) — beside its two probes and its OpenAPI document, over the fifty-five tables of those six contexts in `packages/db` on the database foundation of Issue #64. The backend it will get is described in `docs/architecture/backend-architecture.md` and decided in `docs/adr/`.

## Commands

- `pnpm dev` — both servers through turbo: the web app at http://localhost:3000 and the API (`apps/api`, `tsx watch`) at http://127.0.0.1:3001; the API needs `DATABASE_URL` (see `pnpm db:start`) and `SUPABASE_URL` (the Supabase project whose Auth signs the tokens it verifies) and refuses to start without either. `pnpm --filter @waste/web dev` or `--filter @waste/api dev` runs one of them. The web script pins `-p 3000`, so a busy 3000 fails loudly instead of Next sliding onto 3001 (its fallback when no port is given) and colliding with the API. turbo runs tasks in strict env mode: `HOST`, `PORT`, `DATABASE_URL` and `SUPABASE_URL` reach the API from the shell only because `turbo.json` lists them on `@waste/api#dev` (which restates `cache: false` and `persistent: true`, since a package task does not inherit them from the root `dev` task); any new variable the API reads has to be added there too. The root `.env` reaches it without turbo: the API's `dev`, `start` and `test` scripts pass `--env-file-if-exists=../../.env` (after `watch` in the dev script: before it, tsx takes `watch` for the script path), and a variable set in the shell wins over the file.
- `pnpm build` — production build of the web app through turbo; `pnpm --filter @waste/web start` serves it. The API has no build step: it runs its TypeScript source through tsx (`pnpm --filter @waste/api start`), see Workspace packages below.
- `docker build -f apps/api/Dockerfile .` — the API's container image (2026-09-25), built from the repository root because the API runs the TypeScript source of `@waste/contracts`, `@waste/db` and `@waste/domain` beside it: a `node:22-alpine` build stage installs the API's workspace closure with the pnpm `packageManager` pins and `pnpm --filter @waste/api deploy --prod` lays the package, its production dependencies and those three packages' `src/` out as one directory, which a second `node:22-alpine` stage runs as the unprivileged `node` user through tsx (`node_modules/.bin/tsx src/server.ts`, the `start` script without its `--env-file`, since a container's environment comes from its host) with `HOST=0.0.0.0` and `PORT=3001` as defaults, `EXPOSE 3001` and a `HEALTHCHECK` on `/healthz`; the root `.dockerignore` keeps `.env`, `node_modules`, the web app, the tests and the DAWA snapshot out of the context, CI's `Build API image` job builds it on every run with buildx layer caching and asserts `/healthz` 200 and `/readyz` 503 against a database nobody answers on, and where the container runs is still undecided — the host is chosen with the worker's, see `docs/architecture/backend-architecture.md`.
- `pnpm typecheck` — type check with TypeScript 7's native `tsc` (the `@typescript/native` alias). Errors fail CI; warnings do not in `apps/web`, but the shared packages and `apps/api` run `eslint . --max-warnings 0`, so there a warning fails too. Every rule that is switched off or downgraded there carries the reason in a comment.

## Architecture

### Workspace shell — the core pattern

Nearly every top-level route in `app/` (`/operate`, `/plan`, `/fleet`, `/customers`, `/resources`, `/commercial`, `/improve`, `/configure`, `/control-center`, `/route-studio`, `/service-providers`, plus aliases like `/routes` and `/tickets`) is a thin server component that renders `WorkspacePageShell` (`components/waste/workspace-page-shell.tsx`) with a `workspaceId` and optional `initialModuleId`. Navigation inside a workspace is driven by `?module=` and `?record=` search params; some pages redirect specific module params to dedicated routes (e.g. `/?module=driver-app` → `/driver`).

The shell machinery lives in `components/waste/`:
- `business-workspace.tsx` — the generic module list/table/detail rendering used by every workspace
- `business-record-form-dialog.tsx` — create/edit dialogs generated from form schemas
- `restricted-workspace-shell.tsx` — separate restricted shells for the driver, portal, service provider, and control-center personas (`/driver`, `/portal`, `/service-provider-workspace`, `/control-center`)
- `lib/data/project-scope.ts` — the workspace project scope (Issue #44, 2026-09-24). A `ProjectScope` is one `configure.organization` project record's id (`project-…`, the one rule the web reads a project record by) or `"all"`, never a name of its own: the hard-coded `"copenhagen" | "harbor"` union is gone, so a project the fixture list never knew — Cairo Operations (`project-cairo`) or one created in the browser — scopes exactly like the others. `BusinessWorkspace` derives `projectRecords` from the organisation module through `projectRecordsOf` (soft-deleted left out) and runs every scope question through the module: `isInProjectScope` filters the record list (a record of one project shows only in that project's scope and leaks into no other — Cairo's calendars used to leak into Copenhagen because the union did not know the id; a record with no project, or several, shows everywhere), `pinnedProjectId` drives the `projectId` relation options, the form's initial project and the "outside the current workspace scope" check, `selectedProjectIds` stamps a created record (the chosen project wins, else the pinned one, else every project record), and `projectScopeLabel` reads a scope's label from the project record's name, the id when no record names it. `DEFAULT_PROJECT_SCOPE` still pins the default (`FIXTURE_PROJECT_IDS.copenhagen`); the restricted shells pin theirs through `fixedProjectScope`; the header dropdown stays removed and the sidebar label and Settings "Default project" stay the entry points. `lib/data/__tests__/project-scope.test.ts` holds the rules and holds the fixture organisation records to `FIXTURE_PROJECT_IDS`.
- `map-planning/` — the Plan workspace's page since 2026-09-16 (`plan.map-planning`, the only Plan module): a MapLibre map of the container registry with clustering, a toolbar search (address, container id, planning area), filters, a collection window, rectangle/polygon selection that stays on the map and can be edited by dragging its handles, a Selected area panel (properties, collection points, containers, assumed/collected weight, volume, active agreements, containers by fraction from `@waste/domain/map-planning/statistics`; the Service Areas covering the selection from `@waste/domain/map-planning/coverage` — by planning area, or by a stored polygon; the dated Routes touching it by status, drawable stop-to-stop with "See on map", from `@waste/domain/map-planning/routes`; a Containers list by address), two-way hover highlight (a panel row highlights its markers or route line and a marker or line highlights its rows — one `Highlight` state in the view), named saved selections (shape + filters + window, browser-stored via `saved-selections.ts`), a Layers control (four keyless base maps; planning-area outlines derived as the convex hull of each area's located containers; a Routes layer drawing every drawable route in the collection window from `routesInWindow`, coloured by status bucket — awaiting amber, in progress blue, completed emerald — each line clickable for a route card; drawn Service Areas from `@waste/domain/map-planning/service-areas`; a Coverage gaps toggle from `@waste/domain/map-planning/coverage-gaps` — Available containers whose agreement is not ended/paused/future that no Validated/Scheduled/Effective scheme lists, red-ringed with cluster badges; a Route Schemes section where ticking two compares them via `@waste/domain/map-planning/scheme-compare` — A violet, B cyan, both rose, orphans inside the hull of both red-ringed, a strip at the top with the counts), and two hand-offs: the Guided Setup wizard and the Service Area create dialog (the domain's `serviceAreaSeedFromSelection` proposes a typed seed — project, planning-area ids, boundary line, polygon — and `serviceAreaFormValues` in `lib/data/service-areas.ts` maps it onto the form's field ids for BusinessWorkspace's `RelatedCreateTarget`, whose `extraValues` store the drawn polygon under `submittedValues.boundaryPolygon` — only map-created service areas carry one; the domain never writes a form id, since the schema is web-only and the dialog drops undeclared ids, and `lib/data/__tests__/service-area-seed.test.ts` holds the mapping against the schema). No zoom floor. Routes follow the roads: `road-geometry.ts` asks the keyless public OSRM demo server (car profile, no SLA; prototype only — the target system uses self-hosted Valhalla, see ADR-0002 and `docs/architecture/backend-architecture.md`) for the road through a route's stops in overlapping chunks, splits it into one leg per pair of stops, simplifies it, and caches it in memory and under `waste-map-road-geometry-v1`; `use-road-geometries.ts` fetches a few at a time and remembers refusals for the session; the map draws the road as an SVG path in world pixels at zoom 16 inside one translate-and-scale group (so the map is north-up and flat — rotation and pitch are disabled and must stay so), with a pending or refused road drawn straight and dashed. Route stops are records (order, kind, label, planned clock from the Scheduled fact, actual from Completed-at) — a pickup at no container is placed by its address only when the street is in the gazetteer, never hashed; the gazetteer is the web's (`FIXTURE_GAZETTEER` in `lib/data/street-gazetteer.ts`, mirroring the registry's seeded streets and explicit container fixtures) and is passed into every domain call that places a record — `containerLocation`, `containerPoints`, `planningAreaLayers`, `serviceAreasForSelection`, `routesInSelection`, `routesInWindow`, `compareSchemes` — because the domain cannot see the registry (Issue #58); `lib/data/__tests__/street-gazetteer.test.ts` holds table and registry together (no placed fixture container is hashed; the drawable fixture route days are exactly RC-1042, RC-1048, RC-1044); `playback.ts` drives the replay (playback bar, vehicle marker, travelled path bright). The planning questions asked of the records (what a selection contains, which service areas and routes touch it, coverage gaps, scheme comparison, positions derived from fixture addresses and never stored) are answered by `@waste/domain/map-planning/*` (see Workspace packages below); the map-view mechanics stay in `lib/map-planning/` (base maps, marker colours, clustering, number formatting, toolbar search, playback, road geometry, saved selections) and are pure too, just not domain. Fixture route days have a gazetteer stop or two, so the Routes layer lists them; E2E stubs OSRM per test and seeds a generated-shaped route through the record store. MapLibre's tile worker is served by `app/maplibre/[version]/[asset]/route.ts` because Turbopack breaks its module-worker URL — keep `setWorkerUrl` pointed there. Camera moves fall back to instant jumps until a style has loaded, because MapLibre runs no animation frames without one.

### Workspace packages (`packages/`)

- `packages/domain` (`@waste/domain`) — the pure planning logic of ADR-0002. `lib/route-schemes` moved here 2026-09-17 (Issue #45, slice 3) as `src/route-schemes/`, with `record-visibility`, `service-frequencies`, `business-filters`, `record-values` (`EMPTY_FACT`, `cleanFact`, `typedString`, `uniform` — one rule for facts and typed values, blank or the placeholder is absent; the readers Issue #58 enumerated moved here, and the ones with a different contract say so in the header) and `text` (`count`, one place to spell a count — the caller spells an irregular plural) beside it, and the thirteen pure `lib/map-planning` modules followed as `src/map-planning/` (slice 4); import them as `@waste/domain/route-schemes/<module>`, `@waste/domain/map-planning/<module>` and `@waste/domain/<helper>`. The package ships TypeScript source (`exports` maps `./*` to `./src/*.ts`; Turbopack and tsx read it directly, there is no build step) and depends on nothing. The purity gate from `@waste/tooling` keeps it that way (see below): `src/__tests__/purity.test.ts` is the one call that registers it, with no package allowed in shipping code and only `@waste/tooling` allowed in tests. `src/prototype-record.ts` holds the transitional `BusinessRecord` type, which `lib/data/business-modules` re-exports so web imports did not change; do not grow it into a registry. `route-schemes/scope.ts` is the scheme's service type vocabulary (Issue #42, 2026-09-24): `SCHEME_SERVICE_TYPES` — the prototype's Container, Underground and Kerbside collection, then Crane collection (Igloo · 2,500 L and Underground · 5,000 L, the Glass crane's work) and Tank emptying (Wastewater tank · 3,000 L, the vacuum tanker's) — and `SERVICE_TYPE_CONTAINER_TYPES`, the one mapping the group editor offers from and `checkCollectionGroups` refuses outside; a container type may sit in several (240 L, Underground · 5,000 L), and `scope.test.ts` holds every type in `CONTAINER_TYPE_VOCABULARY` to at least one service type, so a new container type fails a test until a service type collects it. `route-schemes/quick-create.ts` is the quick form's side of the two create paths (Issue #43, 2026-09-24): the `route-studio.schemes` schema picks one Waste fraction and a required Service type on its first section, as Guided Setup does on step 1, and the container types it offers follow the service type through `allowedContainerTypes` (the schema's `optionsBy`, the dialog's one dependent-options mechanism); ### Client-side state

`app/layout.tsx` wires the global providers: `ApiSessionProvider` (the API session, below), `BusinessRecordStoreProvider` (merges fixture records with user-created records per `workspace.module`, persisted to localStorage under `waste-business-records-v1`, one of the keys `lib/storage-keys.ts` spells — and, for a switched module, reads the server instead, below), `OrganizationStoreProvider` and `AssetManagementStoreProvider` (settings state), plus theme providers. Persistence is browser-local for everything the server does not yet own.

**The server-backed record store (Issue #81, 2026-09-25): build-order step 4, the adapter seam and the first modules switched.** The record store's two verbs, `getRecords` and `upsertRecord`, kept their signatures and every caller, and grew a second half behind them: `components/waste/business-record-store.tsx` holds, beside the browser's buckets, one `ModuleState` per switched `workspace.module` (`lib/api/records/server-records.ts`: `idle` → `loading` → `ready` with the server's rows as prototype records, or `failed` with the problem), and `getRecords` answers a switched module the server's rows once they are here and its fixtures until then — never a mixture with the browser's bucket, whose records were made against a store that no longer decides — while every module not switched reads and writes the browser's own path exactly as before. Which modules are switched is one list, `SERVER_MODULES` in `lib/api/records/modules.ts`, in load order, since a later module's mapping resolves the earlier ones' rows: `configure.organization` (the company row from `GET /company`, then `/projects`), `service-providers.service-providers` (`/service-providers`), `configure.access` (`/roles`, then `/users`, each user's role, projects and provider read through the resolver) and `customers.contacts` (`/customers`, the Registry's first). Switching a module is adding it there and, where the wire does not carry what the prototype's form says, a mapping under `lib/api/records/`. The seam has four parts. `lib/api/client.ts` is the one way the web reaches the API — the bearer token in `Authorization`, `listAll` walking a `Page`'s cursor to the end at the API's maximum page size (the store holds a module whole and filters in the browser, as the prototype always has; a module too large for that is the point at which a server-side list arrives), `create` handing back the 201's body with its `Location` (#74, the first client), every non-2xx body thrown as `ApiProblem` over the RFC 9457 problem (`lib/api/problem.ts`, read structurally: the contracts' `Problem` is a type-only import, because the store sits in the root layout and a runtime zod import would land in every route's bundle), and a failed fetch a problem of status 0 so nothing mistakes it for the API's answer. `lib/api/records/adapter.ts` is the vocabulary: a `ResourceAdapter` per wire resource (`owns`, `list`, `toRecord`, `toCreateBody`, `toPatchBody`, `create`, `update`), a `ServerModule` composing them, and two rules every mapping keeps — ids and fields. Ids: the prototype's ids stay the web's handles. A seeded row is the fixture record the seed derived it from (`packages/db/src/seed`, by name), so a resource whose name is a fixture's takes that fixture's id — `project-copenhagen` stays `project-copenhagen`, `company-osterbro-housing` stays, a seeded role is `role-<key>` as `lib/data/role-permissions.ts` keys the charter defaults — and a resource no fixture names is `<prefix>-<uuid>`, the shape `lib/data/project-scope.ts` already reads a project record by; the server's id is kept beside the record in the module's `serverIds`, never on it, and a write looks it up by the web id. A record the workspace has just made keeps the id it minted for the session (`withCreated`: the address bar and the selection already carry it) and takes the adapter's id on the next load. Fields: what the wire carries comes from the wire on every read; what it does not — a fixture's owner, value, description, related chips, transitions — is inherited from the matched fixture and is empty for a resource with none, so a change the workspace makes to a fact that is only presentation has nowhere to go and is not kept. The mappings (`lib/api/records/organisation.ts`, `registry.ts`) put the typed form payload on `submittedValues` under the module's form field ids, so the edit dialog seeds from a server record as from a fixture one, and a project's `weekend` and `holidayList` land there exactly as the Holiday lists pane writes them, so `resolveProjectCalendar` reads a server project unchanged and the pane's save becomes `PATCH /projects/:id`. A write is optimistic and reconciled: `upsertRecord` puts the record in the module at once, `writeRecord` sends a `POST` when the module holds no server id for it and a `PATCH` of what moved otherwise (`patchOf`: each wire field where `after` differs from `before`, `null` where the form emptied a nullable one) or nothing when nothing moved, the API's answer mapped replaces the row, and a refusal — the API's 400 naming a field, its 409 in its own sentence, or a `LocalRefusal` the mapping raised before the API saw it, in the same shape — puts the row back and is told to the person as a toast in the API's words. A controlled action that moves a record's status becomes a status patch where the wire has the word (`active`, `inactive`, `onboarding`) and says nothing where it has none (the lifecycle's Suspended, Archived, Merged); the API has no delete, so a soft delete of a switched module's record is refused with a sentence. The session: `components/waste/api-session-store.tsx` keeps the Supabase session (`lib/api/auth.ts`, the token endpoint spoken directly — `grant_type=password` and `refresh_token` under the project's publishable key, no client library, since two calls weigh less than one) under `waste.api-session.v1` (listed in `STORAGE_KEYS_WITHOUT_A_LEGACY_NAME`, the first key born after the rename), refreshes it a minute before expiry, and hands the store an `ApiClient` or null; null — the adapter off, nobody signed in, the token expired — is every module on fixtures. Configuration is `lib/api/config.ts` over three public variables (`apps/web/.env.example`): `NEXT_PUBLIC_WASTE_API_URL` turns the adapter on, `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` turn password sign-in on at `/login`, beside the fixture picker, which stays; and since the API has no CORS yet, `next.config.mjs` rewrites `/waste-api/:path*` to `WASTE_API_ORIGIN` (declared on `@waste/web#dev` and `#build` in `turbo.json`), so the browser calls its own origin and reads `Location` without CORS exposing it — when the API's CORS lands, the public URL becomes the API's origin and the rewrite goes. Still on fixtures: every module not in `SERVER_MODULES` (the Registry's other nine, Planning, Resources, Execution, Resolution, everything without an API), the organisation store's own tenant graph (`components/settings/organization-store.tsx`, which Settings → Company & Projects reads; the switched organisation module feeds the workspace, the Holiday lists pane and every relation option), `demo-accounts.ts` and every persona; a fixture record's `companyId` is still `FIXTURE_COMPANY_ID`, which is why the server's company row takes that id whatever it is named.

### Legacy vs canonical surfaces

The original portfolio dashboard still exists alongside the Waste prototype: `/projects/[id]`, `/clients`, `/tasks`, `/performance`, and components like `projects-content.tsx` and `project-timeline.tsx`. ### Next.js configuration (`apps/web/next.config.mjs`, 2026-09-17)

- **React Compiler** is on through Turbopack's Rust port (`reactCompiler`, `experimental.turbopackRustReactCompiler`). Components that break the hooks rules are skipped by the compiler, so the `react-hooks/*` lint warnings mark code the compiler cannot optimise.
- **Cache Components and Partial Prefetching** are on (`cacheComponents`, `partialPrefetching`). Every `page.tsx` and the root layout export `instant = false` (added by the `cache-components-instant-false` codemod), so routes may still block on request data; removing an opt-out means making that route's dynamic parts stream behind Suspense. Routes stay mounted across client navigations (React `<Activity>`), so component state persists when the user navigates back.
- **`experimental.useOffline`** keeps failed navigations and Server Actions pending until the connection returns instead of throwing.
- `next dev` maintains `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` (managed block pointing at the bundled Next docs); they are committed on purpose.
