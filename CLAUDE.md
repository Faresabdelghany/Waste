# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The monorepo of a new waste and recycling operations platform, working name Waste (the `@waste/*` namespace): the web app in `apps/web` (Next.js App Router, TypeScript, Tailwind CSS v4, shadcn/ui) and the beginnings of its backend in `apps/api`. The web app started as a small portfolio "project dashboard" template (see README.md) and has grown into a full multi-workspace prototype. It still runs on fixture data in `lib/data/` plus client-side stores persisted to localStorage and has no sign-in of its own (the `/login` account picker is a fixture until Issue 5); `apps/api` verifies Supabase access tokens and answers the Organisation & Access resources — company, projects, service providers, users, roles and their grants (Issue #70) — the Registry's — the catalogue, customers and their properties, agreements and subscriptions, containers and their effective-dated service placements (Issue #78) — and Planning's — planning areas and their effective-dated boundaries, collection calendars and their holidays, route schemes with their collection groups and each group's stop matching rule or picked containers, and the pure occurrence preview (Issue #97, part A; the generation worker is part B and waits for a host) — beside its two probes and its OpenAPI document, over the thirty-two tables of those three contexts in `packages/db` on the database foundation of Issue #64. The backend it will get is described in `docs/architecture/backend-architecture.md` and decided in `docs/adr/`.

## Commands

- `pnpm dev` — both servers through turbo: the web app at http://localhost:3000 and the API (`apps/api`, `tsx watch`) at http://127.0.0.1:3001; the API needs `DATABASE_URL` (see `pnpm db:start`) and `SUPABASE_URL` (the Supabase project whose Auth signs the tokens it verifies) and refuses to start without either. `pnpm --filter @waste/web dev` or `--filter @waste/api dev` runs one of them. The web script pins `-p 3000`, so a busy 3000 fails loudly instead of Next sliding onto 3001 (its fallback when no port is given) and colliding with the API. turbo runs tasks in strict env mode: `HOST`, `PORT`, `DATABASE_URL` and `SUPABASE_URL` reach the API from the shell only because `turbo.json` lists them on `@waste/api#dev` (which restates `cache: false` and `persistent: true`, since a package task does not inherit them from the root `dev` task); any new variable the API reads has to be added there too. The root `.env` reaches it without turbo: the API's `dev`, `start` and `test` scripts pass `--env-file-if-exists=../../.env` (after `watch` in the dev script: before it, tsx takes `watch` for the script path), and a variable set in the shell wins over the file.
- `pnpm build` — production build of the web app through turbo; `pnpm --filter @waste/web start` serves it. The API has no build step: it runs its TypeScript source through tsx (`pnpm --filter @waste/api start`), see Workspace packages below.
- `docker build -f apps/api/Dockerfile .` — the API's container image (2026-09-25), built from the repository root because the API runs the TypeScript source of `@waste/contracts`, `@waste/db` and `@waste/domain` beside it: a `node:22-alpine` build stage installs the API's workspace closure with the pnpm `packageManager` pins and `pnpm --filter @waste/api deploy --prod` lays the package, its production dependencies and those three packages' `src/` out as one directory, which a second `node:22-alpine` stage runs as the unprivileged `node` user through tsx (`node_modules/.bin/tsx src/server.ts`, the `start` script without its `--env-file`, since a container's environment comes from its host) with `HOST=0.0.0.0` and `PORT=3001` as defaults, `EXPOSE 3001` and a `HEALTHCHECK` on `/healthz`; the root `.dockerignore` keeps `.env`, `node_modules`, the web app, the tests and the DAWA snapshot out of the context, CI's `Build API image` job builds it on every run with buildx layer caching and asserts `/healthz` 200 and `/readyz` 503 against a database nobody answers on, and where the container runs is still undecided — the host is chosen with the worker's, see `docs/architecture/backend-architecture.md`.
- `pnpm typecheck` — type check with TypeScript 7's native `tsc` (the `@typescript/native` alias). The `typescript` package itself is TypeScript 6 (`@typescript/typescript6`), kept because ESLint's TypeScript parser needs the JavaScript compiler API that 7 no longer ships; `tsc6` runs it for parity. Both aliases are declared at the root and in every workspace package (`apps/web`, `apps/api`, `packages/domain`, `packages/contracts`, `packages/tooling`, `packages/db`). `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm build` does NOT catch type errors; run the type check explicitly.
- `pnpm lint` — ESLint 9 with the Next rule set, one flat config at the repository root (`eslint.config.mjs`), run per package through turbo. Errors fail CI; warnings do not in `apps/web`, but the shared packages and `apps/api` run `eslint . --max-warnings 0`, so there a warning fails too. Every rule that is switched off or downgraded there carries the reason in a comment.
- `pnpm test` — unit tests on Node's built-in runner through tsx, one suite per package via turbo: `apps/web` (`lib/**/__tests__/*.test.ts`, 21 files, 174 tests), `packages/domain` (`src/**/*.test.ts`, 39 files, 319 tests, 6 of them the purity gate), `packages/contracts` (21 files, 253 tests, 6 the purity gate), `packages/tooling` (3 files, 58 tests: the gate's own specimens, the database-under-test rule, and the web database-fence specimen, which drives ESLint's Node API with `apps/web` and `apps/api` as cwd) and `apps/api` (`src/**/*.test.ts`, 30 files, 582 tests; the listen tests bind real ports, and the script sets `--test-timeout` so a leaked server fails the run instead of hanging CI; the readiness tests that need a database and the eighteen route suites (`me`, `company`, `projects`, `service-providers`, `users`, `roles`, the Registry's `catalogue`, `products`, `customers`, `properties`, `property-groups`, `shared-collection-points`, `agreements`, `containers`, and Planning's `planning-areas`, `collection-calendars`, `route-schemes`, `collection-groups`, each minting its own tenants so files isolate on the shared local database) use `DATABASE_URL`, the API's own role, and skip with a visible reason when it is unset or fail when `REQUIRE_DATABASE` is set — one proof in `me.test.ts` takes `DATABASE_ADMIN_URL` as well, since only a role that bypasses RLS can show the principal lookup binding the claim to the tenant by itself; the rule is `@waste/tooling/database-under-test`, spelled once for `packages/db` and the API, each wrapping it in its own `src/__tests__/database.ts`, the API's adding `ownerUnderTest` for that one URL, loopback only; `turbo.json` declares `DATABASE_ADMIN_URL`, `DATABASE_URL`, `SUPABASE_URL` and `REQUIRE_DATABASE` on `@waste/api#test` with `cache: false`, and CI sets `SUPABASE_URL` to a placeholder, since these tests sign their own tokens against a key set they generate and never fetch one) and `packages/db` (`src/**/*.test.ts`, 24 files, 192 tests; the journal, bootstrap-plan, database-guard, EWKB, geometry-rendering, column-sets-rendering, organisation-access-rendering, registry-rendering, statuses and hand-written tests need no database, the rest run against a real Postgres: they skip with a visible reason when `DATABASE_ADMIN_URL` is unset and fail instead when `REQUIRE_DATABASE` is set, which CI sets, so CI can never pass by skipping; the package's test, migrate, bootstrap and seed scripts pass `--env-file-if-exists=../../.env` (Node 22.9+, hence `engines` at the root), so the root `.env` reaches them without turbo, and `turbo.json` declares the three variables on `@waste/db#test` with `cache: false`, since a test against an external database has no cacheable inputs) as of 2026-09-24.
- `pnpm db:start` / `pnpm db:stop` — the local database: the Supabase CLI (a root devDependency, pinned; its binary arrives as a platform optional dependency, no install script) starts one Postgres 17 + PostGIS container, `supabase_db_waste`, on Docker, from `supabase/config.toml` (`project_id = "waste"`, `[db] major_version = 17`, the CLI's own migrations and `seed.sql` disabled: Drizzle owns both; `[auth] enable_signup = false` and `[auth.hook.custom_access_token]` naming `pg-functions://postgres/public/custom_access_token_hook`, neither of which `db start` reads: they are in the file because the decisions belong in the repository and `supabase config push` applies them to the hosted project). It is the database container only, no Auth or Studio; the same image as the hosted project. Port 54322; the URLs are in `.env.example`, copied to `.env` (gitignored; Node reads it through `--env-file-if-exists`). `pnpm db:migrate` applies `packages/db/migrations` through `packages/db/src/migrate.ts` (an advisory lock with a 60 s timeout serialises two migrators on one database; a transaction-pooler URL, port 6543, is refused because the lock needs one backend; its connections carry `search_path = wms, extensions` as a startup parameter, so an unqualified name in a generated migration resolves the way it does for the API role), `pnpm db:generate` runs `drizzle-kit generate` (never `push`: it would fight the hand-written statements), and `pnpm db:bootstrap` gives the API role `wms_api` (`API_ROLE` in `packages/db/src/roles.ts`) its local login with the password `DATABASE_URL` carries; the plan refuses a non-loopback admin host and a `DATABASE_URL` that logs in as anyone else, because on a hosted project that statement is run by hand with a real password. The database tests refuse non-loopback URLs too: they migrate, create and drop databases and reset the API role's password. `pnpm db:seed` writes the demo company through `packages/db/src/seed/demo.ts` as the owner (`DATABASE_ADMIN_URL`): Kystbyen Renovation, its three projects, the two service providers, the eleven system roles with their 540 grant rows, and the two invited accounts (Fares Abdelghany, the primary administrator with every project; Lars Mikkelsen with one Service Provider Access for NordRen), on ids spelled out as fixed UUIDv7 constants (a millisecond of 2026-09-24, the version and variant nibbles, then a digit per kind of record and an ordinal), so the local database and the hosted project hold the same tenant and a test can name a row without looking it up. It is idempotent — every upsert skips the write when the stored row already says what the run proposes, so a second run does not even move `updated_at` through the touch trigger — it runs against any host, loopback or hosted, unlike bootstrap, and it never touches an account's `auth_user_id` or `deactivated_at`, which belong to the access token hook and the API. CI runs it after `pnpm db:bootstrap`, which is also the step that would catch a seed that writes twice. Since 2026-09-25 the same run writes the Registry too, in the same transaction, through `packages/db/src/seed/registry.ts`: 9 waste fractions, 7 container types, 8 service frequencies (four cadences in each of Copenhagen Central and Harbor Commercial), 14 products (the seven fixture products in both), 19 customers, 53 properties with 113 parties, 2 property groups with 9 members, 2 shared collection points with 6 members, 53 agreements with 38 subscriptions, and 107 containers with 56 placements — 496 rows, derived from the web prototype's fixtures (the explicit records of `apps/web/lib/data/business-modules.ts` copied as literals, its fifty generated properties and hundred generated containers rebuilt from the same tables and arithmetic, and a property located where the map places it through `knownAddressLocation` over a literal copy of `FIXTURE_GAZETTEER`), never imported, since `packages/db` may not depend on the web. The ids continue the scheme (`packages/db/src/seed/ids.ts`, kinds `007` to `015`) and `DEMO_IDS.registry` keys every row by the prototype's own record id, agreement number or membership, so an adapter can map one onto the other. A container is placed only where a fixture product collects its fraction (residual, paper and cardboard, glass), so BIN-82014 and every organic, plastic or metal container stand unplaced; the header of `registry.ts` states that rule and every other reading of a fixture value, and the upsert itself is spelled once in `packages/db/src/seed/upsert.ts` for all twenty-three tables, with no deletes. `supabase stop` stops only this project's containers.
- `pnpm test:e2e` — Playwright against an already running dev server at http://localhost:3000 (no managed webServer; start `pnpm dev` yourself). `pnpm typecheck:e2e` type-checks the e2e folder, which the root tsconfig excludes. In CI the `e2e` job of `.github/workflows/ci.yml` builds the web app, serves that build on 3000 through the `webServer` block `apps/web/playwright.config.ts` enables only when `CI` is `true` or `1` and the base URL is loopback (so `PLAYWRIGHT_BASE_URL=https://<preview>` would run the suite against a deployment and start nothing), and runs the suite with two retries, `maxFailures: 10`, a 15-minute `globalTimeout` and the github reporter; `turbo.json` declares `CI` and `PLAYWRIGHT_BASE_URL` on `test:e2e`, since strict env mode drops the second (it passes `CI` through by itself, vendor detected or not, but the switch should not rest on a default nobody wrote down); locally nothing changes: no managed server, no retries.

pnpm is the package manager (pnpm-lock.yaml). If the volta pnpm shim fails ("Could not find executable"), `npm run <script>` works against the existing node_modules.

## Architecture

### Workspace shell — the core pattern

Nearly every top-level route in `app/` (`/operate`, `/plan`, `/fleet`, `/customers`, `/resources`, `/commercial`, `/improve`, `/configure`, `/control-center`, `/route-studio`, `/service-providers`, plus aliases like `/routes` and `/tickets`) is a thin server component that renders `WorkspacePageShell` (`components/waste/workspace-page-shell.tsx`) with a `workspaceId` and optional `initialModuleId`. Navigation inside a workspace is driven by `?module=` and `?record=` search params; some pages redirect specific module params to dedicated routes (e.g. `/?module=driver-app` → `/driver`).

The shell machinery lives in `components/waste/`:
- `business-workspace.tsx` — the generic module list/table/detail rendering used by every workspace
- `business-record-form-dialog.tsx` — create/edit dialogs generated from form schemas
- `restricted-workspace-shell.tsx` — separate restricted shells for the driver, portal, service provider, and control-center personas (`/driver`, `/portal`, `/service-provider-workspace`, `/control-center`)
- `lib/data/project-scope.ts` — the workspace project scope (Issue #44, 2026-09-24). A `ProjectScope` is one `configure.organization` project record's id (`project-…`, the one rule the web reads a project record by) or `"all"`, never a name of its own: the hard-coded `"copenhagen" | "harbor"` union is gone, so a project the fixture list never knew — Cairo Operations (`project-cairo`) or one created in the browser — scopes exactly like the others. `BusinessWorkspace` derives `projectRecords` from the organisation module through `projectRecordsOf` (soft-deleted left out) and runs every scope question through the module: `isInProjectScope` filters the record list (a record of one project shows only in that project's scope and leaks into no other — Cairo's calendars used to leak into Copenhagen because the union did not know the id; a record with no project, or several, shows everywhere), `pinnedProjectId` drives the `projectId` relation options, the form's initial project and the "outside the current workspace scope" check, `selectedProjectIds` stamps a created record (the chosen project wins, else the pinned one, else every project record), and `projectScopeLabel` reads a scope's label from the project record's name, the id when no record names it. `DEFAULT_PROJECT_SCOPE` still pins the default (`FIXTURE_PROJECT_IDS.copenhagen`); the restricted shells pin theirs through `fixedProjectScope`; the header dropdown stays removed and the sidebar label and Settings "Default project" stay the entry points. `lib/data/__tests__/project-scope.test.ts` holds the rules and holds the fixture organisation records to `FIXTURE_PROJECT_IDS`.
- `map-planning/` — the Plan workspace's page since 2026-09-16 (`plan.map-planning`, the only Plan module): a MapLibre map of the container registry with clustering, a toolbar search (address, container id, planning area), filters, a collection window, rectangle/polygon selection that stays on the map and can be edited by dragging its handles, a Selected area panel (properties, collection points, containers, assumed/collected weight, volume, active agreements, containers by fraction from `@waste/domain/map-planning/statistics`; the Service Areas covering the selection from `@waste/domain/map-planning/coverage` — by planning area, or by a stored polygon; the dated Routes touching it by status, drawable stop-to-stop with "See on map", from `@waste/domain/map-planning/routes`; a Containers list by address), two-way hover highlight (a panel row highlights its markers or route line and a marker or line highlights its rows — one `Highlight` state in the view), named saved selections (shape + filters + window, browser-stored via `saved-selections.ts`), a Layers control (four keyless base maps; planning-area outlines derived as the convex hull of each area's located containers; a Routes layer drawing every drawable route in the collection window from `routesInWindow`, coloured by status bucket — awaiting amber, in progress blue, completed emerald — each line clickable for a route card; drawn Service Areas from `@waste/domain/map-planning/service-areas`; a Coverage gaps toggle from `@waste/domain/map-planning/coverage-gaps` — Available containers whose agreement is not ended/paused/future that no Validated/Scheduled/Effective scheme lists, red-ringed with cluster badges; a Route Schemes section where ticking two compares them via `@waste/domain/map-planning/scheme-compare` — A violet, B cyan, both rose, orphans inside the hull of both red-ringed, a strip at the top with the counts), and two hand-offs: the Guided Setup wizard and the Service Area create dialog (the domain's `serviceAreaSeedFromSelection` proposes a typed seed — project, planning-area ids, boundary line, polygon — and `serviceAreaFormValues` in `lib/data/service-areas.ts` maps it onto the form's field ids for BusinessWorkspace's `RelatedCreateTarget`, whose `extraValues` store the drawn polygon under `submittedValues.boundaryPolygon` — only map-created service areas carry one; the domain never writes a form id, since the schema is web-only and the dialog drops undeclared ids, and `lib/data/__tests__/service-area-seed.test.ts` holds the mapping against the schema). No zoom floor. Routes follow the roads: `road-geometry.ts` asks the keyless public OSRM demo server (car profile, no SLA; prototype only — the target system uses self-hosted Valhalla, see ADR-0002 and `docs/architecture/backend-architecture.md`) for the road through a route's stops in overlapping chunks, splits it into one leg per pair of stops, simplifies it, and caches it in memory and under `waste-map-road-geometry-v1`; `use-road-geometries.ts` fetches a few at a time and remembers refusals for the session; the map draws the road as an SVG path in world pixels at zoom 16 inside one translate-and-scale group (so the map is north-up and flat — rotation and pitch are disabled and must stay so), with a pending or refused road drawn straight and dashed. Route stops are records (order, kind, label, planned clock from the Scheduled fact, actual from Completed-at) — a pickup at no container is placed by its address only when the street is in the gazetteer, never hashed; the gazetteer is the web's (`FIXTURE_GAZETTEER` in `lib/data/street-gazetteer.ts`, mirroring the registry's seeded streets and explicit container fixtures) and is passed into every domain call that places a record — `containerLocation`, `containerPoints`, `planningAreaLayers`, `serviceAreasForSelection`, `routesInSelection`, `routesInWindow`, `compareSchemes` — because the domain cannot see the registry (Issue #58); `lib/data/__tests__/street-gazetteer.test.ts` holds table and registry together (no placed fixture container is hashed; the drawable fixture route days are exactly RC-1042, RC-1048, RC-1044); `playback.ts` drives the replay (playback bar, vehicle marker, travelled path bright). The planning questions asked of the records (what a selection contains, which service areas and routes touch it, coverage gaps, scheme comparison, positions derived from fixture addresses and never stored) are answered by `@waste/domain/map-planning/*` (see Workspace packages below); the map-view mechanics stay in `lib/map-planning/` (base maps, marker colours, clustering, number formatting, toolbar search, playback, road geometry, saved selections) and are pure too, just not domain. Fixture route days have a gazetteer stop or two, so the Routes layer lists them; E2E stubs OSRM per test and seeds a generated-shaped route through the record store. MapLibre's tile worker is served by `app/maplibre/[version]/[asset]/route.ts` because Turbopack breaks its module-worker URL — keep `setWorkerUrl` pointed there. Camera moves fall back to instant jumps until a style has loaded, because MapLibre runs no animation frames without one.

### Workspace packages (`packages/`)

- `packages/domain` (`@waste/domain`) — the pure planning logic of ADR-0002. `lib/route-schemes` moved here 2026-09-17 (Issue #45, slice 3) as `src/route-schemes/`, with `record-visibility`, `service-frequencies`, `business-filters`, `record-values` (`EMPTY_FACT`, `cleanFact`, `typedString`, `uniform` — one rule for facts and typed values, blank or the placeholder is absent; the readers Issue #58 enumerated moved here, and the ones with a different contract say so in the header) and `text` (`count`, one place to spell a count — the caller spells an irregular plural) beside it, and the thirteen pure `lib/map-planning` modules followed as `src/map-planning/` (slice 4); import them as `@waste/domain/route-schemes/<module>`, `@waste/domain/map-planning/<module>` and `@waste/domain/<helper>`. The package ships TypeScript source (`exports` maps `./*` to `./src/*.ts`; Turbopack and tsx read it directly, there is no build step) and depends on nothing. The purity gate from `@waste/tooling` keeps it that way (see below): `src/__tests__/purity.test.ts` is the one call that registers it, with no package allowed in shipping code and only `@waste/tooling` allowed in tests. `src/prototype-record.ts` holds the transitional `BusinessRecord` type, which `lib/data/business-modules` re-exports so web imports did not change; do not grow it into a registry. `route-schemes/scope.ts` is the scheme's service type vocabulary (Issue #42, 2026-09-24): `SCHEME_SERVICE_TYPES` — the prototype's Container, Underground and Kerbside collection, then Crane collection (Igloo · 2,500 L and Underground · 5,000 L, the Glass crane's work) and Tank emptying (Wastewater tank · 3,000 L, the vacuum tanker's) — and `SERVICE_TYPE_CONTAINER_TYPES`, the one mapping the group editor offers from and `checkCollectionGroups` refuses outside; a container type may sit in several (240 L, Underground · 5,000 L), and `scope.test.ts` holds every type in `CONTAINER_TYPE_VOCABULARY` to at least one service type, so a new container type fails a test until a service type collects it. `route-schemes/quick-create.ts` is the quick form's side of the two create paths (Issue #43, 2026-09-24): the `route-studio.schemes` schema picks one Waste fraction and a required Service type on its first section, as Guided Setup does on step 1, and the container types it offers follow the service type through `allowedContainerTypes` (the schema's `optionsBy`, the dialog's one dependent-options mechanism); `quickSchemeDraftFromValues` makes that fraction the rule's one fraction, `seedSchemeEditValues` seeds it from the stored scheme-level value or the one fraction the stored rule or groups name (blank for a re-pick when they name several), and `applySchemeWasteFraction` is what an edit-save runs so the fraction lands under `matchFractions` or inside every explicit group, the keys the readers consume. `record-values.ts` gained `splitList`, the one reader of a stored comma list, which treats a comma between digit groups as a thousands separator, since "Igloo · 2,500 L" and "Four-wheel bin · 1,100 L" are one item each and used to split in two; `matching.ts` re-exports it and the web's `splitMultiValue` reads through it. `apps/web/lib/data/__tests__/quick-scheme-form.test.ts` holds the schema to the domain. `route-schemes/fleet-profiles.ts` reads the licence rule from typed fields (Issue #37, 2026-09-24): `LICENCE_CLASSES` is B, C, CE (CE covers C, C covers B), a driver record's `licenceClass` is the highest class held with an optional `licenceExpiry` calendar day, a vehicle record's `requiredLicenceClass` is the class a driver needs to take it out, and the free-text parse of the `Licence` fact and the derivation from capacity are gone — a record without a readable class is unknown, and unknown never passes: a driver is listed disabled with `NO_LICENCE_ON_RECORD`, and a vehicle without a class disables every driver with `NO_VEHICLE_LICENCE_CLASS`, so the missing value is corrected on the record rather than waved through. `quick-create.ts`'s `quickDriverOptions` and `quickDriverIssue` judge the quick form's `plannedDriverId` by the vehicle its `plannedVehicleId` names through that same rule (the select and the submit check in `business-workspace.tsx` read both through `lib/data/driver-form-options.ts`), and `apps/web/lib/data/__tests__/fleet-licence.test.ts` holds the fixture fleet and the two fleet forms — the driver form's `licenceClass` select, re-purposed from a master-data relation, and the vehicle form's new `requiredLicenceClass` — to the vocabulary. Issue #41 (2026-09-24) added `route-schemes/container-drift.ts`: a Stop Matching Rule re-resolves against the container base on every generation, so each run stamps what every rule group matched — `submittedValues.lastGenerationMatches` beside `previousGenerationMatches`, JSON of `{ [groupId]: { rule, containerIds } }` over rule groups only (ids and not a count, because a container swapped for another reshapes a route as much as one added; `rule` the signature of planning area, fractions, vehicle type and container types, so a rule edit starts the comparison over instead of reading as drift) — and `planSchemeGeneration` carries `matches` (that stamp) and `containerDrift` (the shift since the last stamp: containers that joined plus containers that left, over the previous set's size, a previous set of nothing counting as one; strictly above 10 % is a drift and exactly 10 % is not, compared as integers). `recordGenerationRun` in `lifecycle.ts` is what the manual confirm and Plan Ahead write after applying a plan — the first run's marker and promotion, else the matches stamp alone, and the history advances only when the run's matches differ from the last stamp, so the two stamps are the two most recent distinct sets and a run of the same set returns its input and writes no scheme — creation and edit pass the matches to `recordSchemeGeneration`, and `schemeLiveAssessment` reads the drift between the two stamps, never the live container base, so `schemeAttention` spells it as its last sentence (`containerDriftWarning`), the list badge and the detail header show it, the Routes tab lists it per group, `GenerationSummary.containerDrift` and `PlanAheadSummary.containerDrift` carry it for the run toasts, and it persists across identical runs until the set moves again (a move back within the threshold clears it, a rule edit restarts the comparison); `route-schemes/__tests__/container-drift.test.ts` pins the boundary on both sides and the persistence. Two set replacements here are siblings of `members.ts`'s `replaceSet` and not a fourth and fifth descriptor — a holiday is a day with a name and names no row where an entry there is a row named by id with a role, and a group's rule is two tables and a column where its list is positioned — and both keep the mechanism's steps: the record's own row stamped first — `shared.ts`'s `stamp()`, which `replaceSet` and `replaceGroupSet` share so a Registry set and a group's set stamp the same way, the calendar's PUT still spelling the same `updatedAt: now()` in its own update — so `updatedAt` moves and the PUT answers "no such record" the way every route does, then delete-then-insert inside the request's transaction, never a diff. `references.ts` gained `requirePlanningArea` ("Not a planning area of this project"), `requireContainer` ("Not a container of this project") and `requireServiceProvider` ("Not a service provider of this company") and nothing for a scheme, a group or a calendar, since a singular check is added when a body names the row and none does yet. Test helpers: `src/__tests__/unreachable.ts` gives `REFUSED_URL` (loopback port 1, which needs root to bind and nothing binds, so a dial is refused at once and no just-released port can be taken by a sibling process) and a silent server (accepts, never answers; `scheme-fixtures.ts` seeds what the two scheme suites need of Planning directly through `tx` the same way — a planning area per project, the projects' working weeks and holiday lists, and a Copenhagen calendar with the holidays the occurrence read is proved against (Cairo's Friday–Saturday weekend shifting a Thursday to Sunday, Harbor's calendar rows read by nobody for want of a list) — since those suites prove the scheme routes and not the area and calendar ones; `grantRole` beside it adds rows to a seeded role the way a company does when it edits the matrix, so a Registry suite grants the role it calls as exactly the actions that test needs and no charter has to grow for a test's sake; `calls.ts` `callingAs(app, keys, account, companyId)` is one account's way of calling the API, a fresh token per call, so a test can also call with a claim naming a company the account is not in; `read-problem.ts` asserts the problem media type and parses the body with the contracts' `Problem`; and `database.ts` adds `ownerUnderTest` beside `databaseUnderTest`. The eighteen route suites — `me`, `company`, `projects`, `service-providers`, `users`, `roles`, `catalogue`, `products`, `customers`, `properties`, `property-groups`, `shared-collection-points`, `agreements`, `containers`, `planning-areas`, `collection-calendars`, `route-schemes` and `collection-groups` — each mint their own tenant, and `projects.test.ts` holds the project's two Planning fields. ### Next.js configuration (`apps/web/next.config.mjs`, 2026-09-17)

- **React Compiler** is on through Turbopack's Rust port (`reactCompiler`, `experimental.turbopackRustReactCompiler`). Components that break the hooks rules are skipped by the compiler, so the `react-hooks/*` lint warnings mark code the compiler cannot optimise.
- **Cache Components and Partial Prefetching** are on (`cacheComponents`, `partialPrefetching`). Every `page.tsx` and the root layout export `instant = false` (added by the `cache-components-instant-false` codemod), so routes may still block on request data; removing an opt-out means making that route's dynamic parts stream behind Suspense.
