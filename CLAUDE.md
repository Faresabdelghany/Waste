# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The frontend of a new WasteHero operations platform (waste/recycling logistics), built with Next.js App Router, TypeScript, Tailwind CSS v4, and shadcn/ui. It started as a small portfolio "project dashboard" template (see README.md) and has grown into a full multi-workspace prototype. There is no database or real auth yet — today all data is fixture data in `lib/data/` plus client-side stores persisted to localStorage, and `apps/api` is a Hono scaffold that serves only its health and its OpenAPI document. The backend it will get is described in `docs/architecture/backend-architecture.md` and decided in `docs/adr/`.

## Commands

- `pnpm dev` — both servers through turbo: the web app at http://localhost:3000 and the API (`apps/api`, `tsx watch`) at http://127.0.0.1:3001. `pnpm --filter @waste/web dev` or `--filter @waste/api dev` runs one of them. The web script pins `-p 3000`, so a busy 3000 fails loudly instead of Next sliding onto 3001 (its fallback when no port is given) and colliding with the API. turbo runs tasks in strict env mode: `HOST` and `PORT` reach the API only because `turbo.json` lists them on `@waste/api#dev` (which restates `cache: false` and `persistent: true`, since a package task does not inherit them from the root `dev` task); any new variable the API reads has to be added there too.
- `pnpm build` — production build of the web app through turbo; `pnpm --filter @waste/web start` serves it. The API has no build step: it runs its TypeScript source through tsx (`pnpm --filter @waste/api start`), see Workspace packages below.
- `pnpm typecheck` — type check with TypeScript 7's native `tsc` (the `@typescript/native` alias). The `typescript` package itself is TypeScript 6 (`@typescript/typescript6`), kept because ESLint's TypeScript parser needs the JavaScript compiler API that 7 no longer ships; `tsc6` runs it for parity. Both aliases are declared at the root and in every workspace package (`apps/web`, `apps/api`, `packages/domain`, `packages/contracts`, `packages/tooling`). `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm build` does NOT catch type errors; run the type check explicitly.
- `pnpm lint` — ESLint 9 with the Next rule set, one flat config at the repository root (`eslint.config.mjs`), run per package through turbo. Errors fail CI; warnings do not in `apps/web`, but the shared packages and `apps/api` run `eslint . --max-warnings 0`, so there a warning fails too. Every rule that is switched off or downgraded there carries the reason in a comment.
- `pnpm test` — unit tests on Node's built-in runner through tsx, one suite per package via turbo: `apps/web` (`lib/**/__tests__/*.test.ts`, 10 files, 55 tests), `packages/domain` (`src/**/*.test.ts`, 26 files, 180 tests, 6 of them the purity gate), `packages/contracts` (6 files, 31 tests, 6 the purity gate), `packages/tooling` (1 file, 45 tests, the gate's own specimens) and `apps/api` (`src/**/*.test.ts`, 3 files, 17 tests; the listen tests bind real ports, and the script sets `--test-timeout` so a leaked server fails the run instead of hanging CI) as of 2026-09-17.
- `pnpm test:e2e` — Playwright against an already running dev server at http://localhost:3000 (no managed webServer; start `pnpm dev` yourself). `pnpm typecheck:e2e` type-checks the e2e folder, which the root tsconfig excludes.

pnpm is the package manager (pnpm-lock.yaml). If the volta pnpm shim fails ("Could not find executable"), `npm run <script>` works against the existing node_modules.

## Architecture

### Workspace shell — the core pattern

Nearly every top-level route in `app/` (`/operate`, `/plan`, `/fleet`, `/customers`, `/resources`, `/commercial`, `/improve`, `/configure`, `/control-center`, `/route-studio`, `/service-providers`, plus aliases like `/routes` and `/tickets`) is a thin server component that renders `WorkspacePageShell` (`components/wastehero/workspace-page-shell.tsx`) with a `workspaceId` and optional `initialModuleId`. Navigation inside a workspace is driven by `?module=` and `?record=` search params; some pages redirect specific module params to dedicated routes (e.g. `/?module=driver-app` → `/driver`).

The shell machinery lives in `components/wastehero/`:
- `business-workspace.tsx` — the generic module list/table/detail rendering used by every workspace
- `business-record-form-dialog.tsx` — create/edit dialogs generated from form schemas
- `restricted-workspace-shell.tsx` — separate restricted shells for the driver, portal, service provider, and control-center personas (`/driver`, `/portal`, `/service-provider-workspace`, `/control-center`)
- `map-planning/` — the Plan workspace's page since 2026-09-16 (`plan.map-planning`, the only Plan module): a MapLibre map of the container registry with clustering, a toolbar search (address, container id, planning area), filters, a collection window, rectangle/polygon selection that stays on the map and can be edited by dragging its handles, a Selected area panel (properties, collection points, containers, assumed/collected weight, volume, active agreements, containers by fraction from `@waste/domain/map-planning/statistics`; the Service Areas covering the selection from `@waste/domain/map-planning/coverage` — by planning area, or by a stored polygon; the dated Routes touching it by status, drawable stop-to-stop with "See on map", from `@waste/domain/map-planning/routes`; a Containers list by address), two-way hover highlight (a panel row highlights its markers or route line and a marker or line highlights its rows — one `Highlight` state in the view), named saved selections (shape + filters + window, browser-stored via `saved-selections.ts`), a Layers control (four keyless base maps; planning-area outlines derived as the convex hull of each area's located containers; a Routes layer drawing every drawable route in the collection window from `routesInWindow`, coloured by status bucket — awaiting amber, in progress blue, completed emerald — each line clickable for a route card; drawn Service Areas from `@waste/domain/map-planning/service-areas`; a Coverage gaps toggle from `@waste/domain/map-planning/coverage-gaps` — Available containers whose agreement is not ended/paused/future that no Validated/Scheduled/Effective scheme lists, red-ringed with cluster badges; a Route Schemes section where ticking two compares them via `@waste/domain/map-planning/scheme-compare` — A violet, B cyan, both rose, orphans inside the hull of both red-ringed, a strip at the top with the counts), and two hand-offs: the Guided Setup wizard and the Service Area create dialog (through BusinessWorkspace's `RelatedCreateTarget`, whose `extraValues` store the drawn polygon under `submittedValues.boundaryPolygon` — only map-created service areas carry one). No zoom floor. Routes follow the roads: `road-geometry.ts` asks the keyless public OSRM demo server (car profile, no SLA; prototype only — the target system uses self-hosted Valhalla, see ADR-0002 and `docs/architecture/backend-architecture.md`) for the road through a route's stops in overlapping chunks, splits it into one leg per pair of stops, simplifies it, and caches it in memory and under `wastehero-map-road-geometry-v1`; `use-road-geometries.ts` fetches a few at a time and remembers refusals for the session; the map draws the road as an SVG path in world pixels at zoom 16 inside one translate-and-scale group (so the map is north-up and flat — rotation and pitch are disabled and must stay so), with a pending or refused road drawn straight and dashed. Route stops are records (order, kind, label, planned clock from the Scheduled fact, actual from Completed-at) — a pickup at no container is placed by its address only when the street is in the gazetteer, never hashed; `playback.ts` drives the replay (playback bar, vehicle marker, travelled path bright). The planning questions asked of the records (what a selection contains, which service areas and routes touch it, coverage gaps, scheme comparison, positions derived from fixture addresses and never stored) are answered by `@waste/domain/map-planning/*` (see Workspace packages below); the map-view mechanics stay in `lib/map-planning/` (base maps, marker colours, clustering, number formatting, toolbar search, playback, road geometry, saved selections) and are pure too, just not domain. Fixture route days have a gazetteer stop or two, so the Routes layer lists them; E2E stubs OSRM per test and seeds a generated-shaped route through the record store. MapLibre's tile worker is served by `app/maplibre/[version]/[asset]/route.ts` because Turbopack breaks its module-worker URL — keep `setWorkerUrl` pointed there. Camera moves fall back to instant jumps until a style has loaded, because MapLibre runs no animation frames without one.

### Workspace packages (`packages/`)

- `packages/domain` (`@waste/domain`) — the pure planning logic of ADR-0002. `lib/route-schemes` moved here 2026-09-17 (Issue #45, slice 3) as `src/route-schemes/`, with `record-visibility`, `service-frequencies` and `business-filters` beside it, and the thirteen pure `lib/map-planning` modules followed as `src/map-planning/` (slice 4); import them as `@waste/domain/route-schemes/<module>`, `@waste/domain/map-planning/<module>` and `@waste/domain/<helper>`. The package ships TypeScript source (`exports` maps `./*` to `./src/*.ts`; Turbopack and tsx read it directly, there is no build step) and depends on nothing. The purity gate from `@waste/tooling` keeps it that way (see below): `src/__tests__/purity.test.ts` is the one call that registers it, with no package allowed in shipping code and only `@waste/tooling` allowed in tests. `src/prototype-record.ts` holds the transitional `BusinessRecord` type, which `lib/data/business-modules` re-exports so web imports did not change; do not grow it into a registry. The `__tests__` directories are hidden from consumers by `null` exports.
- `packages/contracts` (`@waste/contracts`) — the wire primitives shared by `apps/web` and `apps/api` (Issue #45, slice 5, 2026-09-17), on zod 4; `zod` is its only dependency, and `apps/web` dropped its unused zod 3 the same day, so the web app meets zod only through these schemas. Modules, imported as `@waste/contracts/<module>`: `ids` (`Id`, a UUID version 7 normalised to lowercase — minted by the server for web writes and by the driver's device for offline commands per ADR-0004; no generator here), `dates` (`IsoDate` calendar day, `IsoDateTime` RFC 3339 with seconds and a UTC offset; a wall-clock time without an offset is rejected), `geojson` (`Longitude`, `Latitude`, `Position` = `[lng, lat, alt?]`, `Point`, `LinearRing` of four or more positions closing on the first with three distinct, `Polygon` with an outer ring and holes; unknown members such as `bbox` are dropped on parse; the prototype's unclosed `{ lng, lat }[]` boundaries are not this shape yet — where they become a ring is a Data-step decision), `pagination` (`PageRequest` with `limit` a whole number or a string of decimal digits, 1..200, default 50, empty or null meaning not given, nothing else coerced, and an opaque optional `cursor`; `Page(item)` = `{ items, nextCursor }` with `null` on the last page), `health` (`HealthResponse`, the body of the API's `GET /healthz`: `status: "ok"` and the server's clock as an `IsoDateTime`; no dependency checks until the API has dependencies). Schemas are written `import * as z from "zod"` so a bundler can drop what a consumer does not use. Same source-shipping layout and `tsconfig.json`/`tsconfig.test.json` split as domain, same purity gate with `allowedImports: ["zod"]` (exact specifiers, so `zod/v3` and `zod/mini` are refused). No module schemas yet: those derive from the form schemas in the Data step. `apps/web/lib/map-planning/road-geometry.ts` types OSRM coordinates as the contracts `Position` through a type-only import and checks the shape structurally: a runtime zod import would land about 90 KB gzipped in the client bundle of every workspace route, so the web app has no runtime consumer of the schemas until a real one exists.
- `packages/tooling` (`@waste/tooling`) — development-only helpers, a `devDependency` of the packages it checks (its own `typescript` is a runtime dependency because the gate imports it when a consumer's suite runs); it is not gated itself because it reads files and drives the TypeScript API. `purity` exports `definePurityTests({ packageDir, allowedImports, allowedTestImports, allowances })`, which registers the purity gate as node:test suites for one package, every file read inside a test because a throw in a `describe` body exits 0 on Node 22: `src/` holds only `.ts` and contains `__tests__/purity.test.ts`; every import — read from the TypeScript AST by `purity-scan`, so comments and strings cannot fool it, a computed `import()` is a finding of its own, and `import("x").T` in a type position counts — is relative and stays inside `src/` or is an allowed exact specifier, and the packages of the allowed specifiers must be exactly the manifest's `dependencies`; tests may add Node built-ins and the allowed test specifiers, whose packages must be `devDependencies`; triple-slash reference directives and `declare global` / `declare module` are refused everywhere; `exports` maps `./*` to `./src/*.ts`, exposes `./package.json` and hides every `__tests__` directory with `null`; `tsconfig.json` covers every module and no test, `tsconfig.test.json` every test, and neither sees a file the gate's walker did not; and a specimen compiled against the shipping options proves that `lib: ["esnext"]` with `types: []` rejects `window`, `document`, `localStorage`, `fetch`, `process`, `globalThis.fetch`, `Buffer` and `navigator` while plain ECMAScript compiles. Allowances are the whole exception list and stay empty unless a reviewer accepted a reason. The tooling's own tests are specimens for the scanner, the walker and the manifest check.

### The API (`apps/api`)

`apps/api` (`@waste/api`) is the Hono API of ADR-0001, the only web boundary to domain data, scaffolded 2026-09-17 (Issue #45, slice 6). `GET /healthz` answers the contracts `HealthResponse`; `GET /openapi.json` is generated at request time by hono-openapi from the `describeRoute` description beside each route, so a described route is always in the published contract: the generator's static-file heuristic (drop a path whose last segment has a dot) is switched off, and only described routes appear, a described OPTIONS handler being the one thing it leaves out (a test validates the document against the OpenAPI 3.1 schema through `@seriousme/openapi-schema-validator`). The generator's own 400 envelope for validated routes is switched off too: the wire error shape, and the validator hook that emits it, are decided with the first validated route. `src/env.ts` reads the process environment once at startup through a zod schema: `HOST` (default `127.0.0.1`; a container sets `0.0.0.0`; an IP address or host name, no brackets, scheme or IPv6 zone id, because a zone id has no URL spelling) and `PORT` (default 3001), an empty variable counting as unset (applied once for every variable, so a new field is a plain schema with a default) and every other variable dropped; a bad value stops the process with the variable named. `src/app.ts` builds the app (`createApp({ now })`, the clock injected so tests pin it), `src/listen.ts` binds it on Node's own http server through node-server's request listener with the global `Request`/`Response` override off (`port: 0` gives an ephemeral port; the returned `close()` is idempotent, releases the port at once, drops idle keep-alive connections, waits up to `SHUTDOWN_GRACE_MS` (5 s) for requests in flight and then cuts the rest, so a stalled client cannot hold the process past its host's deadline), and `src/server.ts` is the composition root, the one file without tests: it shuts down on SIGINT and SIGTERM through `process.on`, so a signal delivered twice (a terminal Ctrl-C plus tsx's relay of it) joins the one shutdown instead of killing the process mid-drain. No database, no auth, and no error shape yet: Hono's text 404 stands until the first real endpoint decides what an error looks like on the wire. The package runs its TypeScript source through tsx (`dev` is `tsx watch`, `start` is `tsx`, so tsx is a runtime dependency) and has no build step: the workspace packages ship source, so a Node build would have to bundle them, and that is decided together with hosting. Runtime dependencies: `@waste/contracts`, `hono`, `@hono/node-server`, `hono-openapi`, `zod`, `tsx`.

### Data registries (`lib/data/`)

- `business-modules.ts` (~4200 lines) — the central registry: workspaces → modules → fixture records, plus the fixture company, project, and service provider IDs used for per-record scoping (`FIXTURE_COMPANY_ID`, `FIXTURE_PROJECT_IDS`, `FIXTURE_SERVICE_PROVIDER_IDS`).
- `business-domain.ts` — machine-readable map of every UI surface to canonical business modules M01–M24 (owners, personas, dependencies, boundaries). Consult it before moving features between workspaces — it defines canonical ownership and known boundary corrections. `settingsModuleDomains` lists the modules that keep real business records but are managed from Settings (registered under the `configure` workspace, e.g. `configure.areas` — Areas & Zones, moved from Plan 2026-09-03); the schema registry's lockstep gate counts their keys as expected, and `lib/data/planning-areas.ts` is the only place that knows where planning areas live.
- `business-form-types.ts` + `business-form-schemas*.ts` — form field schemas per module, split across files by domain area.
- `legacy-ids.ts` — old → new id maps and `migrateLegacy*` helpers from the 2026-09-02 terminology rename plus the 2026-09-03 Areas & Zones move (`plan.areas` → `configure.areas`; see Client-side state below). The only place the retired ids are defined; the stores import it and carry only their own `LEGACY_*` display-string maps and legacy shape guards (the full list of sanctioned exceptions is under Client-side state).
- `projects.ts`, `clients.ts`, `project-details.ts`, `sidebar.ts` — fixture data for the legacy dashboard surfaces.

### Client-side state

`app/layout.tsx` wires the global providers: `BusinessRecordStoreProvider` (merges fixture records with user-created records per `workspace.module`, persisted to localStorage under `wastehero-business-records-v1`), `OrganizationStoreProvider` and `AssetManagementStoreProvider` (settings state), plus theme providers. All persistence is browser-local.

**Terminology rename (2026-09-02): Contractor → Service provider, Contract area → Service area.** The rename changed the workspace id (`contractors` → `service-providers`), module ids (`contract-areas` → `service-areas`, `contractor-workspace` → `service-provider-workspace`, `contractor-prices` → `service-provider-prices`), record-id prefixes, enum literals, and routes (`/contractors` → `/service-providers`, `/contractor-workspace/*` → `/service-provider-workspace/*`). Fixtures and code use the new ids only, but browser-local state and bookmarks written before the rename still carry the old ones, so: stores that persist ids must run loaded state through `migrateLegacyState` (or `migrateLegacyRecordBuckets` for record buckets) from `lib/data/legacy-ids.ts`; `business-workspace.tsx` normalises `?module=`/`?record=` params through `migrateLegacyModuleId`/`migrateLegacyId`; and `next.config.mjs` redirects the old routes. Do not reintroduce the old terms anywhere else — the only sanctioned exceptions are: `lib/data/legacy-ids.ts` (the sole definition of the retired ids); the redirect sources in `next.config.mjs`; the store-local `LEGACY_*` maps and shape guards that feed the migrate helpers (`LEGACY_ROLE_NAMES`/`LEGACY_ROLE_SCOPES` in `components/settings/organization-store.tsx`, `LEGACY_SCOPE_KEYS` in `components/wastehero/active-routes-store.tsx`, `LEGACY_RECORD_KEY_RENAMES` in `components/wastehero/business-record-store.tsx`); the legacy `wastehero-contractor-active-routes-v1` storage key that `active-routes-store.tsx` keeps for backward-compatible reads; and explicit historical notes that say the term was renamed. Do not strip those maps — the stores need them to migrate persisted state.

**Collection Calendars move (2026-09-16): `plan.calendars` → `configure.calendars`.** When Plan became Map Planning, Collection Calendars re-homed to Settings → Operations → Collection calendars (pane `collection-calendars`, rendered by `components/settings/collection-calendars-settings.tsx`); record ids did not change and generation, the wizard, and Plan Ahead still read the records. Resolve the location through `COLLECTION_CALENDARS_MODULE` in `lib/data/collection-calendars.ts` — never hard-code the pair. Persisted state follows through `lib/data/legacy-ids.ts` exactly like the Areas move below (`LEGACY_MODULE_KEYS`, `migrateLegacyState`, `hasLegacyIds`, and `migrateLegacyHref` sending `/plan?module=calendars[&record=…]` to `/settings?pane=collection-calendars[&record=…]`).

**Areas & Zones move (2026-09-03): `plan.areas` → `configure.areas`.** The module left the Plan workspace for Settings → Operations → Areas & Zones; record ids did not change. Persisted state follows through the same `lib/data/legacy-ids.ts` seam: the `LEGACY_MODULE_KEYS` entry moves the record-store bucket and role-access keys, `migrateLegacyState` rewrites stored `relationRefs` whose `workspaceId`/`moduleId` pair names the old home, `hasLegacyIds` detects both shapes, and `migrateLegacyHref` sends `/plan?module=areas[&record=…]` to `/settings?pane=areas[&record=…]` (`app/plan/page.tsx` redirects server-side). Never hard-code the pair again — resolve it through `PLANNING_AREAS_MODULE` in `lib/data/planning-areas.ts`.

### Legacy vs canonical surfaces

The original portfolio dashboard still exists alongside the WasteHero prototype: `/projects/[id]`, `/clients`, `/tasks`, `/performance`, and components like `projects-content.tsx` and `project-timeline.tsx`. These are legacy — notably, the records under `/projects/:id` are Routes in domain terms, not Projects. In WasteHero language a "Project" is an operating scope (municipality, contract, region), never a route.

### Domain language

`CONTEXT.md` is the canonical glossary. Every term lists _Avoid_ synonyms — use the exact terms in UI copy and identifiers (e.g. Agreement vs Subscription, Route Scheme vs Route, Warehouse vs Depot, Ticket vs Alert).

### Next.js configuration (`apps/web/next.config.mjs`, 2026-09-17)

- **React Compiler** is on through Turbopack's Rust port (`reactCompiler`, `experimental.turbopackRustReactCompiler`). Components that break the hooks rules are skipped by the compiler, so the `react-hooks/*` lint warnings mark code the compiler cannot optimise.
- **Cache Components and Partial Prefetching** are on (`cacheComponents`, `partialPrefetching`). Every `page.tsx` and the root layout export `instant = false` (added by the `cache-components-instant-false` codemod), so routes may still block on request data; removing an opt-out means making that route's dynamic parts stream behind Suspense. Both workspace shells wrap `BusinessWorkspace` in `<Suspense>` because it reads `useSearchParams`, which is request data under this model. Routes stay mounted across client navigations (React `<Activity>`), so component state persists when the user navigates back.
- **`experimental.useOffline`** keeps failed navigations and Server Actions pending until the connection returns instead of throwing.
- `next dev` maintains `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` (managed block pointing at the bundled Next docs); they are committed on purpose.

### Docs

`docs/` holds exactly two kinds of document: Architecture Decision Records under `docs/adr/` (one decision per numbered file, status in frontmatter, superseded rather than rewritten) and the living target architecture in `docs/architecture/backend-architecture.md` for the backend being built around this frontend (a new system from scratch, decided 2026-09-17). Rules and the index live in `docs/README.md`. Agent work logs, harness reports, and per-feature specs were removed 2026-09-03 and stay out of `docs/`. The glossary remains `CONTEXT.md` at the root.

### UI conventions

- shadcn/ui primitives (new-york style) in `components/ui/`; config in `components.json`; path alias `@/*`.
- Tailwind CSS v4 — there is no tailwind.config; theme tokens live in `app/globals.css`, the only live global stylesheet (`styles/globals.css` is unused; `styles/tiptap.css` is imported by the project description editor).
- Icons: lucide-react primarily; @phosphor-icons/react in some components.
- Theming: next-themes class-based dark mode plus `AppThemeProvider`/`ThemeBootstrapScript` with named theme presets in `lib/app-themes.ts` (persisted to localStorage).
