# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The monorepo of a new waste and recycling operations platform, working name Waste (the `@waste/*` namespace): the web app in `apps/web` (Next.js App Router, TypeScript, Tailwind CSS v4, shadcn/ui) and the beginnings of its backend in `apps/api`. The web app started as a small portfolio "project dashboard" template (see README.md) and has grown into a full multi-workspace prototype. It still runs on fixture data in `lib/data/` plus client-side stores persisted to localStorage and has no sign-in of its own (the `/login` account picker is a fixture until Issue 5); `apps/api` verifies Supabase access tokens and answers the Organisation & Access resources — company, projects, service providers, users, roles and their grants (Issue #70) — and the Registry's — the catalogue, customers and their properties, agreements and subscriptions, containers and their effective-dated service placements (Issue #78) — beside its two probes and its OpenAPI document, over the twenty-three tables of those two contexts in `packages/db` on the database foundation of Issue #64. The backend it will get is described in `docs/architecture/backend-architecture.md` and decided in `docs/adr/`.

## Commands

- `pnpm dev` — both servers through turbo: the web app at http://localhost:3000 and the API (`apps/api`, `tsx watch`) at http://127.0.0.1:3001; the API needs `DATABASE_URL` (see `pnpm db:start`) and `SUPABASE_URL` (the Supabase project whose Auth signs the tokens it verifies) and refuses to start without either. `pnpm --filter @waste/web dev` or `--filter @waste/api dev` runs one of them. The web script pins `-p 3000`, so a busy 3000 fails loudly instead of Next sliding onto 3001 (its fallback when no port is given) and colliding with the API. turbo runs tasks in strict env mode: `HOST`, `PORT`, `DATABASE_URL` and `SUPABASE_URL` reach the API from the shell only because `turbo.json` lists them on `@waste/api#dev` (which restates `cache: false` and `persistent: true`, since a package task does not inherit them from the root `dev` task); any new variable the API reads has to be added there too. The root `.env` reaches it without turbo: the API's `dev`, `start` and `test` scripts pass `--env-file-if-exists=../../.env` (after `watch` in the dev script: before it, tsx takes `watch` for the script path), and a variable set in the shell wins over the file.
- `pnpm build` — production build of the web app through turbo; `pnpm --filter @waste/web start` serves it. The API has no build step: it runs its TypeScript source through tsx (`pnpm --filter @waste/api start`), see Workspace packages below.
- `pnpm typecheck` — type check with TypeScript 7's native `tsc` (the `@typescript/native` alias). The `typescript` package itself is TypeScript 6 (`@typescript/typescript6`), kept because ESLint's TypeScript parser needs the JavaScript compiler API that 7 no longer ships; `tsc6` runs it for parity. Both aliases are declared at the root and in every workspace package (`apps/web`, `apps/api`, `packages/domain`, `packages/contracts`, `packages/tooling`, `packages/db`). `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm build` does NOT catch type errors; run the type check explicitly.
- `pnpm lint` — ESLint 9 with the Next rule set, one flat config at the repository root (`eslint.config.mjs`), run per package through turbo. Errors fail CI; warnings do not in `apps/web`, but the shared packages and `apps/api` run `eslint . --max-warnings 0`, so there a warning fails too. Every rule that is switched off or downgraded there carries the reason in a comment.
- `pnpm test` — unit tests on Node's built-in runner through tsx, one suite per package via turbo: `apps/web` (`lib/**/__tests__/*.test.ts`, 14 files, 88 tests), `packages/domain` (`src/**/*.test.ts`, 34 files, 236 tests, 6 of them the purity gate), `packages/contracts` (17 files, 189 tests, 6 the purity gate), `packages/tooling` (3 files, 58 tests: the gate's own specimens, the database-under-test rule, and the web database-fence specimen, which drives ESLint's Node API with `apps/web` and `apps/api` as cwd) and `apps/api` (`src/**/*.test.ts`, 25 files, 440 tests; the listen tests bind real ports, and the script sets `--test-timeout` so a leaked server fails the run instead of hanging CI; the readiness tests that need a database and the fourteen route suites (`me`, `company`, `projects`, `service-providers`, `users`, `roles`, and the Registry's `catalogue`, `products`, `customers`, `properties`, `property-groups`, `shared-collection-points`, `agreements`, `containers`, each minting its own tenants so files isolate on the shared local database) use `DATABASE_URL`, the API's own role, and skip with a visible reason when it is unset or fail when `REQUIRE_DATABASE` is set — one proof in `me.test.ts` takes `DATABASE_ADMIN_URL` as well, since only a role that bypasses RLS can show the principal lookup binding the claim to the tenant by itself; the rule is `@waste/tooling/database-under-test`, spelled once for `packages/db` and the API, each wrapping it in its own `src/__tests__/database.ts`, the API's adding `ownerUnderTest` for that one URL, loopback only; `turbo.json` declares `DATABASE_ADMIN_URL`, `DATABASE_URL`, `SUPABASE_URL` and `REQUIRE_DATABASE` on `@waste/api#test` with `cache: false`, and CI sets `SUPABASE_URL` to a placeholder, since these tests sign their own tokens against a key set they generate and never fetch one) and `packages/db` (`src/**/*.test.ts`, 22 files, 165 tests; the journal, bootstrap-plan, database-guard, EWKB, geometry-rendering, column-sets-rendering, organisation-access-rendering, registry-rendering, statuses and hand-written tests need no database, the rest run against a real Postgres: they skip with a visible reason when `DATABASE_ADMIN_URL` is unset and fail instead when `REQUIRE_DATABASE` is set, which CI sets, so CI can never pass by skipping; the package's test, migrate, bootstrap and seed scripts pass `--env-file-if-exists=../../.env` (Node 22.9+, hence `engines` at the root), so the root `.env` reaches them without turbo, and `turbo.json` declares the three variables on `@waste/db#test` with `cache: false`, since a test against an external database has no cacheable inputs) as of 2026-09-24.
- `pnpm db:start` / `pnpm db:stop` — the local database: the Supabase CLI (a root devDependency, pinned; its binary arrives as a platform optional dependency, no install script) starts one Postgres 17 + PostGIS container, `supabase_db_waste`, on Docker, from `supabase/config.toml` (`project_id = "waste"`, `[db] major_version = 17`, the CLI's own migrations and `seed.sql` disabled: Drizzle owns both; `[auth] enable_signup = false` and `[auth.hook.custom_access_token]` naming `pg-functions://postgres/public/custom_access_token_hook`, neither of which `db start` reads: they are in the file because the decisions belong in the repository and `supabase config push` applies them to the hosted project). It is the database container only, no Auth or Studio; the same image as the hosted project. Port 54322; the URLs are in `.env.example`, copied to `.env` (gitignored; Node reads it through `--env-file-if-exists`). `pnpm db:migrate` applies `packages/db/migrations` through `packages/db/src/migrate.ts` (an advisory lock with a 60 s timeout serialises two migrators on one database; a transaction-pooler URL, port 6543, is refused because the lock needs one backend; its connections carry `search_path = wms, extensions` as a startup parameter, so an unqualified name in a generated migration resolves the way it does for the API role), `pnpm db:generate` runs `drizzle-kit generate` (never `push`: it would fight the hand-written statements), and `pnpm db:bootstrap` gives the API role `wms_api` (`API_ROLE` in `packages/db/src/roles.ts`) its local login with the password `DATABASE_URL` carries; the plan refuses a non-loopback admin host and a `DATABASE_URL` that logs in as anyone else, because on a hosted project that statement is run by hand with a real password. The database tests refuse non-loopback URLs too: they migrate, create and drop databases and reset the API role's password. `pnpm db:seed` writes the demo company through `packages/db/src/seed/demo.ts` as the owner (`DATABASE_ADMIN_URL`): Kystbyen Renovation, its three projects, the two service providers, the eleven system roles with their 540 grant rows, and the two invited accounts (Fares Abdelghany, the primary administrator with every project; Lars Mikkelsen with one Service Provider Access for NordRen), on ids spelled out as fixed UUIDv7 constants (a millisecond of 2026-09-24, the version and variant nibbles, then a digit per kind of record and an ordinal), so the local database and the hosted project hold the same tenant and a test can name a row without looking it up. It is idempotent — every upsert skips the write when the stored row already says what the run proposes, so a second run does not even move `updated_at` through the touch trigger — it runs against any host, loopback or hosted, unlike bootstrap, and it never touches an account's `auth_user_id` or `deactivated_at`, which belong to the access token hook and the API. CI runs it after `pnpm db:bootstrap`, which is also the step that would catch a seed that writes twice. `supabase stop` stops only this project's containers.
- `pnpm test:e2e` — Playwright against an already running dev server at http://localhost:3000 (no managed webServer; start `pnpm dev` yourself). `pnpm typecheck:e2e` type-checks the e2e folder, which the root tsconfig excludes.

pnpm is the package manager (pnpm-lock.yaml). If the volta pnpm shim fails ("Could not find executable"), `npm run <script>` works against the existing node_modules.

## Architecture

### Workspace shell — the core pattern

Nearly every top-level route in `app/` (`/operate`, `/plan`, `/fleet`, `/customers`, `/resources`, `/commercial`, `/improve`, `/configure`, `/control-center`, `/route-studio`, `/service-providers`, plus aliases like `/routes` and `/tickets`) is a thin server component that renders `WorkspacePageShell` (`components/waste/workspace-page-shell.tsx`) with a `workspaceId` and optional `initialModuleId`. Navigation inside a workspace is driven by `?module=` and `?record=` search params; some pages redirect specific module params to dedicated routes (e.g. `/?module=driver-app` → `/driver`).

The shell machinery lives in `components/waste/`:
- `business-workspace.tsx` — the generic module list/table/detail rendering used by every workspace
- `business-record-form-dialog.tsx` — create/edit dialogs generated from form schemas
- `restricted-workspace-shell.tsx` — separate restricted shells for the driver, portal, service provider, and control-center personas (`/driver`, `/portal`, `/service-provider-workspace`, `/control-center`)
- `lib/data/project-scope.ts` — the workspace project scope (Issue #44, 2026-09-24). A `ProjectScope` is one `configure.organization` project record's id (`project-…`, the one rule the web reads a project record by) or `"all"`, never a name of its own: the hard-coded `"copenhagen" | "harbor"` union is gone, so a project the fixture list never knew — Cairo Operations (`project-cairo`) or one created in the browser — scopes exactly like the others. `BusinessWorkspace` derives `projectRecords` from the organisation module through `projectRecordsOf` (soft-deleted left out) and runs every scope question through the module: `isInProjectScope` filters the record list (a record of one project shows only in that project's scope and leaks into no other — Cairo's calendars used to leak into Copenhagen because the union did not know the id; a record with no project, or several, shows everywhere), `pinnedProjectId` drives the `projectId` relation options, the form's initial project and the "outside the current workspace scope" check, `selectedProjectIds` stamps a created record (the chosen project wins, else the pinned one, else every project record), and `projectScopeLabel` reads a scope's label from the project record's name, the id when no record names it. `DEFAULT_PROJECT_SCOPE` still pins the default (`FIXTURE_PROJECT_IDS.copenhagen`); the restricted shells pin theirs through `fixedProjectScope`; the header dropdown stays removed and the sidebar label and Settings "Default project" stay the entry points. `lib/data/__tests__/project-scope.test.ts` holds the rules and holds the fixture organisation records to `FIXTURE_PROJECT_IDS`.
- `map-planning/` — the Plan workspace's page since 2026-09-16 (`plan.map-planning`, the only Plan module): a MapLibre map of the container registry with clustering, a toolbar search (address, container id, planning area), filters, a collection window, rectangle/polygon selection that stays on the map and can be edited by dragging its handles, a Selected area panel (properties, collection points, containers, assumed/collected weight, volume, active agreements, containers by fraction from `@waste/domain/map-planning/statistics`; the Service Areas covering the selection from `@waste/domain/map-planning/coverage` — by planning area, or by a stored polygon; the dated Routes touching it by status, drawable stop-to-stop with "See on map", from `@waste/domain/map-planning/routes`; a Containers list by address), two-way hover highlight (a panel row highlights its markers or route line and a marker or line highlights its rows — one `Highlight` state in the view), named saved selections (shape + filters + window, browser-stored via `saved-selections.ts`), a Layers control (four keyless base maps; planning-area outlines derived as the convex hull of each area's located containers; a Routes layer drawing every drawable route in the collection window from `routesInWindow`, coloured by status bucket — awaiting amber, in progress blue, completed emerald — each line clickable for a route card; drawn Service Areas from `@waste/domain/map-planning/service-areas`; a Coverage gaps toggle from `@waste/domain/map-planning/coverage-gaps` — Available containers whose agreement is not ended/paused/future that no Validated/Scheduled/Effective scheme lists, red-ringed with cluster badges; a Route Schemes section where ticking two compares them via `@waste/domain/map-planning/scheme-compare` — A violet, B cyan, both rose, orphans inside the hull of both red-ringed, a strip at the top with the counts), and two hand-offs: the Guided Setup wizard and the Service Area create dialog (the domain's `serviceAreaSeedFromSelection` proposes a typed seed — project, planning-area ids, boundary line, polygon — and `serviceAreaFormValues` in `lib/data/service-areas.ts` maps it onto the form's field ids for BusinessWorkspace's `RelatedCreateTarget`, whose `extraValues` store the drawn polygon under `submittedValues.boundaryPolygon` — only map-created service areas carry one; the domain never writes a form id, since the schema is web-only and the dialog drops undeclared ids, and `lib/data/__tests__/service-area-seed.test.ts` holds the mapping against the schema). No zoom floor. Routes follow the roads: `road-geometry.ts` asks the keyless public OSRM demo server (car profile, no SLA; prototype only — the target system uses self-hosted Valhalla, see ADR-0002 and `docs/architecture/backend-architecture.md`) for the road through a route's stops in overlapping chunks, splits it into one leg per pair of stops, simplifies it, and caches it in memory and under `waste-map-road-geometry-v1`; `use-road-geometries.ts` fetches a few at a time and remembers refusals for the session; the map draws the road as an SVG path in world pixels at zoom 16 inside one translate-and-scale group (so the map is north-up and flat — rotation and pitch are disabled and must stay so), with a pending or refused road drawn straight and dashed. Route stops are records (order, kind, label, planned clock from the Scheduled fact, actual from Completed-at) — a pickup at no container is placed by its address only when the street is in the gazetteer, never hashed; the gazetteer is the web's (`FIXTURE_GAZETTEER` in `lib/data/street-gazetteer.ts`, mirroring the registry's seeded streets and explicit container fixtures) and is passed into every domain call that places a record — `containerLocation`, `containerPoints`, `planningAreaLayers`, `serviceAreasForSelection`, `routesInSelection`, `routesInWindow`, `compareSchemes` — because the domain cannot see the registry (Issue #58); `lib/data/__tests__/street-gazetteer.test.ts` holds table and registry together (no placed fixture container is hashed; the drawable fixture route days are exactly RC-1042, RC-1048, RC-1044); `playback.ts` drives the replay (playback bar, vehicle marker, travelled path bright). The planning questions asked of the records (what a selection contains, which service areas and routes touch it, coverage gaps, scheme comparison, positions derived from fixture addresses and never stored) are answered by `@waste/domain/map-planning/*` (see Workspace packages below); the map-view mechanics stay in `lib/map-planning/` (base maps, marker colours, clustering, number formatting, toolbar search, playback, road geometry, saved selections) and are pure too, just not domain. Fixture route days have a gazetteer stop or two, so the Routes layer lists them; E2E stubs OSRM per test and seeds a generated-shaped route through the record store. MapLibre's tile worker is served by `app/maplibre/[version]/[asset]/route.ts` because Turbopack breaks its module-worker URL — keep `setWorkerUrl` pointed there. Camera moves fall back to instant jumps until a style has loaded, because MapLibre runs no animation frames without one.

### Workspace packages (`packages/`)

- `packages/domain` (`@waste/domain`) — the pure planning logic of ADR-0002. `lib/route-schemes` moved here 2026-09-17 (Issue #45, slice 3) as `src/route-schemes/`, with `record-visibility`, `service-frequencies`, `business-filters`, `record-values` (`EMPTY_FACT`, `cleanFact`, `typedString`, `uniform` — one rule for facts and typed values, blank or the placeholder is absent; the readers Issue #58 enumerated moved here, and the ones with a different contract say so in the header) and `text` (`count`, one place to spell a count — the caller spells an irregular plural) beside it, and the thirteen pure `lib/map-planning` modules followed as `src/map-planning/` (slice 4); import them as `@waste/domain/route-schemes/<module>`, `@waste/domain/map-planning/<module>` and `@waste/domain/<helper>`. The package ships TypeScript source (`exports` maps `./*` to `./src/*.ts`; Turbopack and tsx read it directly, there is no build step) and depends on nothing. The purity gate from `@waste/tooling` keeps it that way (see below): `src/__tests__/purity.test.ts` is the one call that registers it, with no package allowed in shipping code and only `@waste/tooling` allowed in tests. `src/prototype-record.ts` holds the transitional `BusinessRecord` type, which `lib/data/business-modules` re-exports so web imports did not change; do not grow it into a registry. `route-schemes/scope.ts` is the scheme's service type vocabulary (Issue #42, 2026-09-24): `SCHEME_SERVICE_TYPES` — the prototype's Container, Underground and Kerbside collection, then Crane collection (Igloo · 2,500 L and Underground · 5,000 L, the Glass crane's work) and Tank emptying (Wastewater tank · 3,000 L, the vacuum tanker's) — and `SERVICE_TYPE_CONTAINER_TYPES`, the one mapping the group editor offers from and `checkCollectionGroups` refuses outside; a container type may sit in several (240 L, Underground · 5,000 L), and `scope.test.ts` holds every type in `CONTAINER_TYPE_VOCABULARY` to at least one service type, so a new container type fails a test until a service type collects it. `route-schemes/quick-create.ts` is the quick form's side of the two create paths (Issue #43, 2026-09-24): the `route-studio.schemes` schema picks one Waste fraction and a required Service type on its first section, as Guided Setup does on step 1, and the container types it offers follow the service type through `allowedContainerTypes` (the schema's `optionsBy`, the dialog's one dependent-options mechanism); `quickSchemeDraftFromValues` makes that fraction the rule's one fraction, `seedSchemeEditValues` seeds it from the stored scheme-level value or the one fraction the stored rule or groups name (blank for a re-pick when they name several), and `applySchemeWasteFraction` is what an edit-save runs so the fraction lands under `matchFractions` or inside every explicit group, the keys the readers consume. `record-values.ts` gained `splitList`, the one reader of a stored comma list, which treats a comma between digit groups as a thousands separator, since "Igloo · 2,500 L" and "Four-wheel bin · 1,100 L" are one item each and used to split in two; `matching.ts` re-exports it and the web's `splitMultiValue` reads through it. `apps/web/lib/data/__tests__/quick-scheme-form.test.ts` holds the schema to the domain. Issue #70 (2026-09-24) added `src/access/` and `src/ids.ts`, pure like everything else here. `access/modules.ts` is the permission vocabulary: `MODULE_KEYS`, the fifty `workspace.module` keys of the prototype's permission matrix in sidebar order (the standalone Control Center workspace is left out, since Configure already carries `configure.control-center`), `WORKSPACE_KEYS` and `modulesOf` derived from them, and `ACTIONS` (`view`, `edit`, `create`, `delete`); the list lives here and not in the database, where `role_grant.module_key` is text, so adding a module is a code change and never a migration. `access/grants.ts` holds `Grant` and the one spelling of the rule that edit, create and delete imply view: `normaliseGrants`, which the seed, the API's request path and `PUT /roles/:id/grants` all write through, so a grant set is the same whichever door it came through; `mergeGrants` beside it only tidies (one entry per module, actions in `ACTIONS` order, sorted, an empty grant dropped), so a charter can be read as written and a test can hold every charter already normalised. `access/system-roles.ts` is `SYSTEM_ROLE_KEYS` and `SYSTEM_ROLES`, the eleven seeded roles with their copy and 540 default grant rows between them, moved out of `apps/web/lib/data/role-permissions.ts`. `src/ids.ts` is `mintId(unixMillis, randomBytes)` and `nextId(previous, unixMillis, randomBytes)`, UUIDv7 laid out as RFC 9562 §5.7 says with §6.2's monotonic-random rule — two ids minted in the same millisecond count up over the 74 random bits, carrying past the variant and version bits and into the clock when the field is full — written lowercase, so the string order is the mint order and a cursor over `id` is a cursor over time; `apps/api/src/ids.ts` is the only place that supplies `Date.now` and `crypto.getRandomValues`. Issue #78 (2026-09-24) added `src/registry/vocabulary.ts`, the Registry's closed lists: twenty `as const` tuples of the kinds, statuses, roles, purposes, modes and units its rows may carry (`CUSTOMER_KINDS`, `PROPERTY_PARTY_ROLES`, `SHARED_COLLECTION_POINT_BILLING_MODES`, `PRODUCT_UNITS`, `BILLING_CADENCES`, `CONTAINER_OWNERSHIPS` and the rest), with `REGISTRY_VOCABULARIES` naming them all so a test can walk them. The database reads each list into its `CHECK ... in (...)` and the contracts read the same list into a `z.enum`, so the check at the API boundary and the check in the column cannot drift and there is no lockstep test to write — unlike the Organisation & Access statuses, which came first and keep their two spellings. A value is a kebab-case token because it goes into a migration as a SQL literal and onto the wire as an enum member and those are the same string; `registry/__tests__/vocabulary.test.ts` holds every list to that, to being non-empty, to naming nothing twice, and to being named in `REGISTRY_VOCABULARIES`, which it finds by reading the module as a namespace and picking the lists out by shape. The `__tests__` directories are hidden from consumers by `null` exports.
- `packages/contracts` (`@waste/contracts`) — the wire primitives shared by `apps/web` and `apps/api` (Issue #45, slice 5, 2026-09-17), on zod 4; `zod` was its only dependency until `permissions.ts` reached for the domain's vocabulary (Issue #70), and `apps/web` dropped its unused zod 3 the same day, so the web app meets zod only through these schemas. Modules, imported as `@waste/contracts/<module>`: `ids` (`Id`, a UUID version 7 normalised to lowercase — minted by the server for web writes and by the driver's device for offline commands per ADR-0004; no generator here), `dates` (`IsoDate` calendar day, `IsoDateTime` RFC 3339 with seconds and a UTC offset; a wall-clock time without an offset is rejected), `geojson` (`Longitude`, `Latitude`, `Position` = `[lng, lat, alt?]`, `Point`, `LinearRing` of four or more positions closing on the first with three distinct, `Polygon` with an outer ring and holes; unknown members such as `bbox` are dropped on parse; the prototype's unclosed `{ lng, lat }[]` boundaries are not this shape yet — where they become a ring is decided with the first table that stores a polygon, as `docs/architecture/backend-architecture.md` says; the Registry stored the system's first points and no polygon), `pagination` (`PageRequest` with `limit` a whole number or a string of decimal digits, 1..200, default 50, empty or null meaning not given, nothing else coerced, and an opaque optional `cursor`; `Page(item)` = `{ items, nextCursor }` with `null` on the last page), `health` (`HealthResponse`, the body of the API's `GET /healthz`: `status: "ok"` and the server's clock as an `IsoDateTime`; `ReadyResponse`, `UnavailableResponse` and the discriminated union `ReadinessResponse` over them, the two bodies of `GET /readyz`). Issue #70 added six more: `permissions` (`ModuleKey = z.enum(MODULE_KEYS)`, `Action = z.enum(ACTIONS)` and `Grant = { moduleKey, actions }` — the domain's vocabulary turned into the check the API boundary runs, so an unknown key never reaches `role_grant`), `problem` (`Problem`, RFC 9457 `{ type, title, status, detail?, errors? }` with `errors` a list of `{ path, message }`, plus `ProblemFieldError`, `PROBLEM_MEDIA_TYPE` = `application/problem+json` and `BLANK_PROBLEM_TYPE` = `about:blank`, every problem being the generic one for its status until a client needs to tell two apart), `me` (`Me`: the caller's `user` with a `status` of literally `active`, `company`, `role` with its normalised `grants`, `projects` and `serviceProvider` or null), `organisation` (`CompanyStatus`, `ProjectStatus`, `Company`, `CompanyPatch`, `Project`, `ProjectCreate`, `ProjectPatch`, `ServiceProvider`, `ServiceProviderCreate`, `ServiceProviderPatch`), `access` (`UserStatus` — `invited`, `active`, `deactivated`, derived and never stored — `User`, `UserInvite`, `UserPatch`, `Role`, `RoleCreate`, `RolePatch`, `RoleGrants`) and `text` (`Label`, the one spelling of a piece of text a person typed — present, not whitespace only, at most 200 characters, and stored exactly as it arrived, since trimming would answer something the body did not say; `organisation`, `access` and `me` all take it from there, so a resource and the summary of it in `Me` cannot drift apart). Issue #78 (2026-09-24) added seven more modules: `validity`, `resource` and `queries` beside the Registry's four. `validity` is the half-open period of ADR-0005: `Validity` (`validFrom` the first day in force, `validTo` the first day out of it or null while it runs), `ValidityCreate` the same as a create body spreads it (an absent end is the open one the column stores as null), `validityOrdered` the rule that an end comes after its start, and `ENDS_AFTER_IT_STARTS` that rule's one sentence — a constant of its own, because zod normalises the params object a `.refine` is handed and `message` is not there to read back afterwards. An end equal to its start is refused, since an empty period is an empty range the database's exclusion constraint would not even see as a conflict; comparing two `YYYY-MM-DD` strings compares the days, so nothing is parsed. `resource` is `stamped` (`id` and the two `IsoDateTime` stamps) beside `changesSomething` and `somethingToChange`, the "give at least one field to change" pair that `organisation` and `access` each carried before and now import, since a rule in six places is six chances for one of them to say something else. `queries` is `ProjectScopedListQuery`, `PageRequest` plus an optional `projectId` — new here and not a move: three of the Registry's modules extend it and four list routes validate against it as it stands, so eight project-scoped lists do not spell the filter eight ways. ### The API (`apps/api`)

`apps/api` (`@waste/api`) is the Hono API of ADR-0001, the only web boundary to domain data, scaffolded 2026-09-17 (Issue #45, slice 6), connected to the database 2026-09-24 (Issue #64, slice 4), and given its authentication, its error shape and the Organisation & Access resources the same day (Issue #70, slices 3 to 5). `GET /healthz` answers the contracts `HealthResponse` (liveness: the process answers, with its clock); `GET /readyz` answers `ReadinessResponse` (readiness: `checkDatabase` in `src/readiness.ts` runs `select 1` through a pool's raw `sql` face bounded by `DATABASE_CHECK_TIMEOUT_MS`, 2 s, under every common balancer's probe timeout; a probe the bound overtook is left to settle, never cancelled, because postgres.js's cancel strands a connection whose startup query it was and, for a sent query, dials a cancel connection whose dropped promise would be an unhandled rejection when the stalled database refuses it, killing the process; instead the probe runs on its own pool, `probePoolOptions(timeoutMs)` = `{ max: 1, connectTimeoutSeconds: timeoutMs / 1000, backoffSeconds: 1 }`, so probes never take a request's connection, a hung dial ends with the bound rather than after 30 s, and a database that comes back is seen within a second where postgres.js's own backoff would grow towards 20 s; 200 `ReadyResponse` `{ status: "ok", checks: { database: "ok" } }` or 503 `UnavailableResponse` `{ status: "unavailable", checks: { database: "unreachable" } }`, the two members of the contracts' discriminated union, so a body whose status disagrees with its check does not parse; a refused connection answers in milliseconds, a hung one at the bound, and `/healthz` keeps answering either way); `GET /openapi.json` is generated at request time by hono-openapi from the `describeRoute` description beside each route, so a described route is always in the published contract: the generator's static-file heuristic (drop a path whose last segment has a dot) is switched off, and only described routes appear, a described OPTIONS handler being the one thing it leaves out (a test validates the document against the OpenAPI 3.1 schema through `@seriousme/openapi-schema-validator`). The generator's own 400 envelope for validated routes is switched off too, because a 400 is a problem like every other error and the route that validates describes it. The document carries `components.securitySchemes.bearerAuth` (`type: http`, `scheme: bearer`, `bearerFormat: JWT`) and every route but the probes declares it: a test walks the document and counts 74 secured operations over its 44 paths, `/healthz` and `/readyz` the only open ones (`/openapi.json` is undescribed, so it is not a path of its own document). `src/env.ts` reads the process environment once at startup through a zod schema: `HOST` (default `127.0.0.1`; a container sets `0.0.0.0`; an IP address or host name, no brackets, scheme or IPv6 zone id, because a zone id has no URL spelling), `PORT` (default 3001), `DATABASE_URL` (required, no default: a `postgresql://` or `postgres://` URL with a host, the `wms_api` role's connection string, checked for shape only, since whether it answers is `/readyz`'s question on every probe; the transaction pooler is not refused here, unlike in the migrator, because `prepare: false` keeps the client valid behind it) and `SUPABASE_URL` (required, no default: the origin of the Supabase project whose Auth signs the tokens — `http` or `https`, a host, and nothing else, a trailing slash refused rather than stripped so the one spelling in `.env` is the one the issuer is compared against, and a path, query, fragment or credentials refused too), an empty variable counting as unset (applied once for every variable, so a new field is a plain schema with a default, or without one when the process cannot run without it) and every other variable dropped; a bad or missing value stops the process with the variable named. `src/app.ts` builds the app (`createApp({ probe, pool, verifier, now, databaseTimeoutMs, log })`: `probe` and `pool` are both a `Database` from `@waste/db/client`, the first what `/readyz` probes and the second what every authenticated request opens its transaction on, and the app connects on neither by itself, so a test hands a route that asks nothing of the database pools that go nowhere; `verifier` is injected too, so a test verifies against a key set it generated and the app never reads `SUPABASE_URL`; the clock is injected so tests pin it, the bound is interpolated into `/readyz`'s OpenAPI description so the document states the one in force, and `log` is where a 500's cause goes, `console.error` unless a test wants to look), `src/listen.ts` binds it on Node's own http server through node-server's request listener with the global `Request`/`Response` override off (`port: 0` gives an ephemeral port; the returned `close()` is idempotent, releases the port at once, drops idle keep-alive connections, waits up to `SHUTDOWN_GRACE_MS` (5 s) for requests in flight and then cuts the rest, so a stalled client cannot hold the process past its host's deadline), and `src/server.ts` is the composition root, the one file without tests: it opens the probe pool with `createDb(env.DATABASE_URL, probePoolOptions(DATABASE_CHECK_TIMEOUT_MS))` and the request pool with `createDb(env.DATABASE_URL)` before binding (postgres.js dials on the first query, so the process starts with the database down and `/readyz` says so) and builds the verifier over `createRemoteJWKSet` of the project's key set, and it shuts down on SIGINT and SIGTERM through `process.on`, so a signal delivered twice (a terminal Ctrl-C plus tsx's relay of it) joins the one shutdown instead of killing the process mid-drain: the listener drains and the probe pool closes together (a probe is not a request, and 503 is the right answer to one arriving mid-shutdown, so the two 5 s ceilings overlap instead of adding up), the request pool closes after the listener, so a request in flight keeps the connection its transaction runs on until it has answered; every failure is printed and any failure exits 1. Authentication and the request path (slice 3). A route takes `Authorization: Bearer <Supabase access token>`; `src/auth/verify.ts` verifies it with `jose` — `jwtVerify` against the project's key set, `issuer` `${SUPABASE_URL}/auth/v1`, `audience` `authenticated`, algorithms `ES256`, `RS256` and `EdDSA` only, so a token signed with a shared secret is refused before any key is looked up. `server.ts` builds the key set with `createRemoteJWKSet` (jose caches it, refetches on a `kid` it has not seen and rate-limits that refetch, which is what Supabase's edge cache and rotation guidance need, where Hono's own `jwk` middleware refetches per request) and a test with `createLocalJWKSet`, both behind the injected `Verifier`, which answers verified claims or a refusal with a reason and a sentence for the problem body, never the token itself; a key set that cannot be fetched is thrown, since it says nothing about the token, and becomes the server's 500. `src/auth/principal.ts` is the guard each authenticated route puts before its handler, never on a wildcard, so the probes and the document need no token and an unknown path stays a 404: it reads `sub` and `app_metadata.company_id`, opens `withCompany(companyId)` on the request pool, and `resolvePrincipal` looks the account (active, bound to that login), its role and normalised grants, its projects (all of the company's when `all_projects`, else its Project Access rows) and its Service Provider up inside it — every lookup carrying an explicit `company_id = companyId`, so the API binds the claim to the tenant itself and the fence is the second stop, not the only one (ADR-0001). The handler receives that same transaction as `tx` on the context and opens none of its own; after `next()` the middleware discards it (a private `Discard` thrown out of `withCompany`) when the context carries an error or the response is 400 or worse, so a failed request leaves nothing behind whether the handler threw a problem or returned one. Nothing is cached, so a revoked grant or a deactivated account is refused on the very next call. `src/auth/require.ts` `requireGrant(moduleKey, action)` reads the resolved grant set and nothing else; its arguments are the domain's literal types, so a typo in a route is a compile error rather than a route nobody can reach. `src/problem.ts` is the error shape the #45 and #64 scaffolds deferred: RFC 9457 Problem Details in the contracts' `Problem`. A handler throws `problem(status, { detail, errors, headers })`; `errorHandler` turns a `ProblemError` into its own response, one of Hono's `HTTPException`s into a problem of its status, SQLSTATE 23505 (a key already taken) and 23P01 (a period that overlaps one already there, the Registry's effective-dated tables) into a 409 naming the constraint, and anything else into a 500 with no detail and a projection of the error logged (`loggable`: name, message, SQLSTATE, constraint and stack, and the same of its cause — never postgres.js's statement or the `parameters` it bound, which on a failed `POST /users` would be the invitee's address and name). `notFound` answers an unknown path as a problem too; `validate(target, schema)` is hono-openapi's validator with `validationHook`, which turns zod's issues into a 400 listing `errors: [{ path, message }]`, the path dotted into the target (`projectIds.1`) and empty for the target as a whole; `describeProblem` is the OpenAPI response object for one. `invalidRequest(target, errors)` builds that same 400 wherever something other than a schema noticed — the validator's hook, a cursor that is not one of ours, a project the caller does not work in, an id naming a row that is not there — so a client reads one shape whatever refused. A 401 carries `WWW-Authenticate` in RFC 6750's three spellings — `Bearer` when no header was sent, `Bearer error="invalid_request"` when the header is not one Bearer token, `Bearer error="invalid_token"` when a token was presented and refused — while a valid token with no company claim is a 403 saying the token names no company, and an unknown `sub`, a `sub` that is not a UUID at all, a deactivated account and a company the account is not in are the one other 403, "No active account in this company is bound to this login" — same status either way, since a better token would not help. The routes. `GET /me` (slice 3) answers the contracts' `Me`, the Principal on the wire, and needs no grant. The organisation half (slice 4), ten routes: `GET`/`PATCH /company`, `GET`/`POST /projects`, `GET`/`PATCH /projects/:id`, `GET`/`POST /service-providers`, `GET`/`PATCH /service-providers/:id`, under `configure.organization` except the providers, which are `service-providers.service-providers`, `view` to read and `edit`/`create` to write. The access half (slice 5), twelve routes, all under `configure.access`: `GET`/`POST /users`, `GET`/`PATCH /users/:id`, `POST /users/:id/deactivate`, `POST /users/:id/reactivate`, `POST /users/:id/make-primary-administrator` (Issue #73, 2026-09-24), `GET`/`POST /roles`, `GET`/`PATCH /roles/:id` and `PUT /roles/:id/grants`. Their rules, each stated in the route's OpenAPI description and answered with a sentence: an invite names exactly one of `allProjects: true`, `projectIds` and `serviceProviderId`, and a patch that changes the access replaces the whole shape inside the request's transaction; the primary administrator cannot be deactivated, moved to another role or narrowed (409, each refusal stating the rule and nothing more); the flag itself moves through `POST /users/:id/make-primary-administrator`, to an account that is active — signed in as at least once and not deactivated — and reaches every project, a deactivated, never-signed-in, service-provider or projects-scoped target each refused with a 409 sentence of its own (the last is `PATCH`'s narrowing rule read from the other side: a transfer must not produce the account a patch refuses to make), off the old holder and then onto the new one as two statements, because the partial unique index checks each row as it is written; the command runs under the company's row lock, so two transfers take turns and the index never fires, and then the target's, which `PATCH /users/:id` and `POST /users/:id/deactivate` now take before they read, so a deactivation or a narrowing sent into the middle of a transfer waits for it and is then refused as the primary administrator the account has become; its grant is `edit` on `configure.access` and not the holder's alone, stated in its description, because the flag usually moves once its holder has left and another administrator must be able to move it before deactivating them; deactivate, reactivate and the transfer are idempotent, so an account already in that state answers 200 without a write and the instant it was switched off does not move; `PUT /roles/:id/grants` replaces the whole matrix and moves the role's `updatedAt`, since the matrix is part of the `Role` on the wire, while a system role's `key` and `system` flag stay immutable and its copy and matrix do not. Every grant set stored or answered goes through `normalisedGrants` in `src/access-shape.ts`, which also derives a user's status (deactivated before invited, so an account switched off never reads as a pending invitation). A single-row read or update always carries `company_id` beside the id, so another tenant's id is a 404 with the same sentence as an id nobody minted, and a duplicate is a 409 with the route's own sentence through `refuseDuplicate` — `routes/shared.ts`, beside `IdParam`, `describeJson`, `stampsOf`, and, since the Registry, `refuseOverlap` for 23P01 (two doors and not one taking a SQLSTATE, because a table's name key and its `no_overlap` constraint say different things to a person and a sentence written for one must not answer the other), `requireRow` for an id a body names, and `lockRow` for a rule the API holds rather than the database — so no constraint name reaches a client and a leaked one means a sentence is missing. Ids for web writes are minted by the server: `src/ids.ts` is the impure half of `@waste/domain/ids`, holding the last id so a burst inside one millisecond counts up instead of scattering, and a route writes `id: newId()` into the insert. Lists answer the contracts' `Page(item)` through `src/pagination.ts`: rows ordered by `id` ascending, which for a UUIDv7 is the order they were made in, the cursor base64url of the last item's id, a cursor that is not one of ours a 400 naming `cursor`, and `fetchLimit`/`pageOf` asking for one row more than the page to learn whether there is a next one — no offsets, which drift under inserts, and no total, which a list view does not need. The Registry (Issue #78, slices 3 to 5, 2026-09-24), fifty-one routes over ten families, and the second fence every one of them carries. A Registry row belongs to a Project, which Organisation & Access never had to know: `src/auth/projects.ts` is `projectIdsOf(principal)`, `inProjects(column, principal)` — the `where` fragment that bounds a project-scoped statement to the projects the caller works in, a SQL `false` when there are none rather than an `in ()` Postgres will not parse or a condition left out, which would widen the statement to the whole company — and `requireProject(principal, projectId)`. The two answers differ on purpose: a row outside the scope is a row that is not there, so a list leaves it out and a single-row read is the family's own 404, because telling an account which projects exist that it may not see tells it something about the company it was not given; a body or a query naming one is a 400 on that field, because the caller chose the project and can choose another, where a 404 on a row nobody made would say nothing about what to fix. An account that works in no project at all — a Service Provider's — reaches nothing project-scoped whatever its role grants. The families and their grants: `/waste-fractions`, `/container-types` and `/service-frequencies` under `configure.master`, `/products` under `commercial.products`, `/customers` under `customers.contacts`, `/properties` (with `PUT /properties/:id/parties`) under `customers.properties`, `/property-groups` (with `PUT /property-groups/:id/members`) under `customers.groups`, `/shared-collection-points` (with `PUT /shared-collection-points/:id/members`) under `customers.shared`, `/agreements` with `/agreements/:id/subscriptions` and `/subscriptions/:id` under `customers.agreements`, and `/containers` with `/containers/:id/placements`, `/placements` and `/placements/:id` under `resources.containers`; `view` to read, `create` to add, `edit` to change and to replace a set. No delete anywhere: an agreement is terminated by giving it a `validTo`, a container is taken out of service by ending its placement, and a record standing behind pickups and tickets is not removed. Three mechanisms are the Registry's own. A set that travels with a record — a Property's parties, a Group's members, a Point's members — is read with the record and replaced whole, since "add one, remove one" over a list the client already holds is two requests that can disagree; `routes/members.ts` is that mechanism once: delete-then-insert inside the request's transaction and never a diff (a diff is three statements and a tie-break rule where this is two and none, and the rows carry no id a client was given and no stamp anyone reads), a page loading every parent's entries in one query and grouping them, a body's entries held to what their key allows in one query too, so a set body of two hundred is one statement and not two hundred round trips behind the lock the record's own stamp has just taken, with `replaceSet` spelling the touch-then-replace step and each family handing in one descriptor. A create may carry the set it starts with; a patch never touches it, because a patch is a field-by-field change and a membership is a set. `routes/references.ts` is every singular "is that row really there" check, one function per family, each spelling its sentence once and defaulting the path to the field a body carries it in — a container type is named by a Product and by a Container, a waste fraction by a Product and by a Placement — and `members.ts` reads those same sentences, so one bad id and one among two hundred are told the same thing; underneath, `requireRow` is the statement, always with `company_id` and whatever else the key demands, checked before the write so a bad reference is a 400 naming the field and not a 23503 a client cannot read. And `routes/periods.ts` is containment: a Subscription runs inside its Agreement and a Placement inside its Subscription, which Postgres cannot say across rows without a trigger. It is two rules and not one — a child moved outside its parent is a 400 naming the bound, since the caller chose it, and a parent shortened under its children is a 409 counting them, since the rows in the way are not in the body and have to be ended first (`refuseStranded` beside `strayCount` in `agreements.ts` is that count once, for an agreement's subscriptions and a subscription's placements alike). A patch carries one bound and the stored row the other, so `periodAfter` composes the period the write leaves behind and `requireWithin` holds it to the ordering rule before it holds it to the parent's, in the contracts' own words (`ENDS_AFTER_IT_STARTS`), since a patch naming only the end would otherwise reach the table's `validPeriod` check and come back as a 500 saying nothing. The rule is held under the parent's row lock — `lockRow`'s `select … for update`, taken before the read, because two transactions that each read and then write would otherwise both pass — in five places, and a route that takes two takes them from the top down, the Agreement before the Subscription, so no two requests hold half of each other's pair. `?validOn=` is how "running", "expired" and "what stands there today" are asked for, through `validOn` from `@waste/db/query/valid-on`: none of those is a column, and no day is implied, since a default would need a timezone nobody stated. The cadence in force is read and never written: every placement statement joins the subscription and the product and selects `coalesce(placement.service_frequency_id, product.service_frequency_id)` as `effectiveServiceFrequencyId`, and a create answers by reading its row back through that same select rather than from its own `returning`, so what a write says is what the next read says and a product whose cadence changes carries every placement that inherited it with it, which a stored copy could not do. `GET /properties?customerId=` is the citizen portal's side of the resource — the properties a `property_party` row names that customer on, in any role, as one `exists`, so two roles at one property is one item and not two — a read model over Registry rows and not an account. Test helpers: `src/__tests__/unreachable.ts` gives `REFUSED_URL` (loopback port 1, which needs root to bind and nothing binds, so a dial is refused at once and no just-released port can be taken by a sibling process) and a silent server (accepts, never answers; a test ends such a pool with `sql.end({ timeout: 0 })` before closing the server, since `close()` would wait out its 5 s grace on a connection that is hung by construction and a socket dropped first would make postgres.js reconnect); `tokens.ts` mints an ES256 key pair and signs Supabase-shaped tokens against it (`signingKeys`, `signToken`, and `neverVerifies` for an app whose routes under test present none); `tenant.ts` seeds a whole company under `withCompany` as `wms_api` — three projects, two providers, three roles and five accounts, every e-mail on a random `.example` domain — and drops it again, the Registry's fifteen tables before Organisation & Access's, so files isolate by tenant on the shared database; `grantRole` beside it adds rows to a seeded role the way a company does when it edits the matrix, so a Registry suite grants the role it calls as exactly the actions that test needs and no charter has to grow for a test's sake; `calls.ts` `callingAs(app, keys, account, companyId)` is one account's way of calling the API, a fresh token per call, so a test can also call with a claim naming a company the account is not in; `read-problem.ts` asserts the problem media type and parses the body with the contracts' `Problem`; and `database.ts` adds `ownerUnderTest` beside `databaseUnderTest`. The package runs its TypeScript source through tsx (`dev` is `tsx watch`, `start` is `tsx`, so tsx is a runtime dependency) and has no build step: the workspace packages ship source, so a Node build would have to bundle them, and that is decided together with hosting. Runtime dependencies: `@waste/contracts`, `@waste/db`, `@waste/domain` (the vocabulary and the grant rule), `drizzle-orm` (the API writes its own queries; pinned to `packages/db`'s range so one instance resolves), `hono`, `@hono/node-server`, `hono-openapi`, `jose`, `zod`, `tsx`.

**Storage-key and fixture-id rename (2026-09-24): `wastehero…` → `waste…`.** The product's working name is Waste (the `@waste/*` namespace, the repository), so `components/wastehero/` became `components/waste/` and every browser-storage key dropped the old prefix (`wastehero-business-records-v1` → `waste-business-records-v1`, `wastehero.organization.v1` → `waste.organization.v1`, and so on). ### Legacy vs canonical surfaces

The original portfolio dashboard still exists alongside the Waste prototype: `/projects/[id]`, `/clients`, `/tasks`, `/performance`, and components like `projects-content.tsx` and `project-timeline.tsx`. These are legacy — notably, the records under `/projects/:id` are Routes in domain terms, not Projects. In Waste language a "Project" is an operating scope (municipality, contract, region), never a route.

### Domain language

`CONTEXT.md` is the canonical glossary. Every term lists _Avoid_ synonyms — use the exact terms in UI copy and identifiers (e.g. Agreement vs Subscription, Route Scheme vs Route, Warehouse vs Depot, Ticket vs Alert).

### Next.js configuration (`apps/web/next.config.mjs`, 2026-09-17)

- **React Compiler** is on through Turbopack's Rust port (`reactCompiler`, `experimental.turbopackRustReactCompiler`). Components that break the hooks rules are skipped by the compiler, so the `react-hooks/*` lint warnings mark code the compiler cannot optimise.
- **Cache Components and Partial Prefetching** are on (`cacheComponents`, `partialPrefetching`). Every `page.tsx` and the root layout export `instant = false` (added by the `cache-components-instant-false` codemod), so routes may still block on request data; removing an opt-out means making that route's dynamic parts stream behind Suspense. Both workspace shells wrap `BusinessWorkspace` in `<Suspense>` because it reads `useSearchParams`, which is request data under this model. Routes stay mounted across client navigations (React `<Activity>`), so component state persists when the user navigates back.
- **`experimental.useOffline`** keeps failed navigations and Server Actions pending until the connection returns instead of throwing.
- `next dev` maintains `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` (managed block pointing at the bundled Next docs); they are committed on purpose.
