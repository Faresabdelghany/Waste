# Backend architecture

Status: agreed 2026-09-17. This repository is the monorepo of a new system built from scratch: it began as the system's frontend, now `apps/web`, and the backend described here is built beside it, `apps/api` first. This document describes that backend. The five invariants and the optimiser choice are recorded as ADRs under `../adr/`; stack choices and their rejected alternatives live in the table below. This document is the readable whole and is updated when an ADR changes it. Terms follow `CONTEXT.md`.

## Bounded contexts

Derived from the glossary. Each context owns its tables and exposes commands and read models; other contexts reference its records by id only.

| Context | Owns | Defining trait |
|---|---|---|
| Organisation & Access | Company, Project, User account, Role and its grants, Project Access, Service Provider (the external organisation itself: legal name, registration number, country, contact), Service Provider Access, Company Administrator | The tenant is the Company. A Service Provider's users belong to another organisation and see only their currently assigned Service Areas. |
| Registry | Customer, Property, Property Group, Shared Collection Point, Agreement, Subscription, Service frequency, Product / Service, Container Service Placement | Effective-dated entitlements. Service frequency is inherited by query, never copied. |
| Resources | Vehicle (with compartments), Driver, Vehicle Allocation, Warehouse, Depot, Unloading Station, Stock Movement, Container Asset State | Two append-only ledgers: Stock Movements and Vehicle Allocations. Asset State is a projection. |
| Planning | Collection Calendar, Route Scheme, Collection Group, Stop Matching Rule, Planning Area, Scenario, Plan | Stores rules and immutable optimisation results (Plans), never generated work. Generation is a job. A Route in Execution references at most one active Plan. |
| Execution | Route, Planned and Actual Assignment, Pickup, Session, Proof of Service, Unload | Connectivity can disappear at any point in a shift. Pickup is one record from planning through execution; proof and unloads are appended. |
| Resolution | Ticket, Alert | Created from execution events. |
| Finance & Contracting | Billable Event, Billing Run, Invoice, Settlement, Price List, Service Area, Service Area Assignment | A pipeline from Pickup to Invoice. Everything effective-dated. A Service Provider's areas, assignments, prices and settlements are here; the organisation record itself is Organisation & Access's, because an access grant needs the organisation it grants for. |

Intelligence (Insight, Suggestion, Approval) and Promotion / Go-live are glossary terms with no schema in the first version. Activating a Plan on a Route (ADR-0002) is not Promotion; Promotion is the larger process of turning an approved plan into production configuration.

## Invariants

These are architectural constraints, not implementation preferences. Each has an ADR.

1. **Single domain data path.** Domain tables are not reachable from the browser. The Hono API is the web boundary; authorisation and business rules live behind it. Row-level security is a backstop, never the place the model is implemented. ADR-0001.
2. **Generation is not optimisation.** Generation deterministically establishes what work exists on a service date. Optimisation produces a Plan over that work and never rewrites the generated baseline. ADR-0002.
3. **Container lifecycle consistency.** One Container identity, a Service Placement in Registry, an Asset State projected from the Stock Movement ledger, and lifecycle commands that update both contexts atomically. ADR-0003.
4. **Offline execution.** Every driver action is an idempotent, client-identified command that survives hours without connectivity and is applied server-authoritatively later. ADR-0004.
5. **Effective dating.** Every effective-dated concept uses validity periods with database-enforced non-overlap, evaluated as of a date at query time. ADR-0005.

## Stack

| Layer | Choice | Why this and not the obvious alternative |
|---|---|---|
| Web | Next.js 16, React 19, TypeScript, shadcn/ui, Tailwind v4 | Already built. |
| API | Hono with hono-openapi and zod 4 | Zod schemas shared with the web forms. OpenAPI 3.1 is the contract for the driver app and third parties. tRPC has no first-party OpenAPI. ts-rest is unmaintained. Server Actions are Next-only. |
| Database | Supabase Postgres 17 with PostGIS, Stockholm (`eu-north-1`) | PostGIS for container points, planning-area and service-area polygons, route geometry. Supabase chosen as platform; Neon was the alternative. |
| Auth | Supabase Auth, tokens verified with jose | Its JWT is consumed natively by PowerSync and RLS. It has no organisation model, so Company, Project Access, Service Provider Access, and roles are our tables. The only claim of ours on the JWT is the home company id, which the custom access token hook adds; the user id is Auth's own subject, and grants are looked up per request. The API verifies an access token against the project's published JWKS (asymmetric keys, ES256 on `waste-dev`) through jose's cached remote key set, so it holds no shared secret and key rotation needs no restart; Hono's own JWK middleware refetches the key set on every request. Better Auth was the alternative and is the fallback if the platform changes. |
| ORM | Drizzle 0.45 | Typed SQL, transactions for multi-table commands. Geometry as GeoJSON through a custom type that drizzle-kit renders as written (`geometry(Point, 4326)`; Drizzle's own geometry column is not used, since drizzle-kit rewrites its polygon form to point). Hand-written SQL only for what Drizzle has no builder for: extensions, functions, roles, exclusion constraints, policies. Prisma rejected: PostGIS columns are unsupported in its client. |
| Jobs | pg-boss 12 | Same Postgres, same transaction as the rows it produces, cron built in. Needs the direct connection or session pooler, never the transaction pooler. Worker hosted outside Supabase (Railway or Fly). |
| Cross-context events | Outbox table relayed by the worker | No message broker. |
| Driver app | Expo with PowerSync | The only sync engine with offline writes, server-authoritative conflict handling, and an attachment queue on any Postgres. Zero rejects offline writes; Replicache is in maintenance mode. PowerSync's service is source-available under FSL: self-host or EU cloud. Fallback: plain Expo SQLite outbox. |
| Road routing | Valhalla, self-hosted | Truck costing, distance matrices, map-matching, MIT. Denmark extract is about 470 MB. The public OSRM demo server is non-commercial, one request per second, no uptime guarantee: prototype only. |
| Optimisation | PyVRP 0.14 as a Python sidecar behind one HTTP contract (ADR-0006) | Multi-dimensional capacity plus reloads in one model, verified by spike. Its reload empties every compartment, which matches Danish and Swedish practice. The only non-TypeScript component; OR-Tools replaces it behind the same contract if partial unloading is ever required. ADR-0006. |
| Map data | GeoJSON with client clustering; Martin vector tiles above roughly 50k features | Martin is maintained by the MapLibre organisation. pg_tileserv has stalled. |
| Danish addresses and basemap | Adressevælger (autocomplete), Datafordeleren (reverse geocoding, DAR, DAGI polygons), Dataforsyningen Skærmkort vector tiles | DAWA shuts down 2026-10-01. Every provider URL sits behind one config seam. |
| Monorepo | pnpm 12 workspaces with Turborepo | Web, api, worker, driver apps; domain, contracts, db packages; a development-only tooling package for the purity gate. |
| Tests | Node's built-in runner through tsx, Playwright | The unit suite already ran on it when this was decided. No migration to Vitest. |

## Data model rules

- Domain tables live in schema `wms`, which is not in Supabase's exposed schemas. RLS policies on them are coarse tenant fences; the API sets request claims per transaction so the backstop is real.
- The API connects as `wms_api`, which owns nothing and bypasses nothing, so every policy and default privilege applies to it; migrations run as the owner.
- Every table carries `company_id`; project-scoped tables carry `project_id`. Service Provider visibility is resolved through Service Area Assignment validity, never denormalised onto rows.
- An intra-tenant reference is a composite foreign key that carries the tenant: `(company_id, project_id) → project (company_id, id)`, `(company_id, role_id) → role (company_id, id)`, and so on, so every table referenced this way carries `unique (company_id, id)` for the key to point at. Only `company_id → company (id)` itself is a plain key, and `company` is its own tenant (`company_id = id`). A row therefore cannot reference another tenant's record whatever the API does; the database refuses it.
- A project-scoped reference carries the project. Where both tables are project-scoped the key carries `project_id` as well: `(company_id, project_id, property_id) → property (company_id, project_id, id)`, so a subscription cannot name a property of another project any more than of another company, and a placement cannot name another project's container. The referenced table carries `unique (company_id, project_id, id)` for it. A reference from a project-scoped table to a company-wide one — an agreement's customer, a placement's waste fraction — stays the tenant's composite key, because the target has no project to agree on. The helpers are `projectReference` and `projectKey` beside `tenantReference` and `tenantKey`.
- A record that hangs off another names it once and reaches the rest through it. ADR-0003 has a Container Service Placement name the place, the agreement, the product and the waste fraction; it names the waste fraction directly and reaches the other three through its Subscription, one reference in place of three that could disagree with each other.
- Supabase Auth is the identity provider and sign-up is invitation-only. The custom access token hook adds the one custom claim, `app_metadata.company_id`, the caller's home company; the API verifies the token against the project's JWKS and looks the caller's account and grants up on every request inside `withCompany`, so a revocation takes effect on the next call and RLS stays the backstop.
- Effective-dated tables use `valid_from` and nullable `valid_to`, half-open, with a `btree_gist` exclusion constraint per key.
- A status is stored only where validity does not already say it. "Pending", "expiring", "expired" and "terminated" are readings of a period against the day the caller names, never columns; a record with no period — a Customer, a Property, a Product — carries a status instead, and an effective-dated one carries a status only for what its period cannot say, as `agreement.status` (draft, active, cancelled) does. A status gates a new reference and never an existing one: an agreement's customer and payer must be active, a subscription's product active and its place served (a property active, a point open or restricted), and a container is not placed at a property that has gone inactive or a point that has closed — each a 409 the API holds, spelled once per family — while the agreements, subscriptions and placements already made stand whatever their rows do afterwards, a row's own status never blocks a write to that row, and a project's, a group's and an agreement's status stay informational (an onboarding project is one being set up, a group is built while draft, an agreement's period says the stronger thing). A record's own key may be held by the exclusion constraint rather than by a unique one where the stronger thing is true: one Agreement of a number is valid at a time, so the number may name a later Agreement once the earlier has ended.
- One spelling of a vocabulary: a context's closed lists — its kinds, statuses, roles, purposes, modes and units — are spelled once in the domain package (`@waste/domain/registry/vocabulary` for the Registry, `@waste/domain/planning/vocabulary` for Planning) and read from there by the column's `CHECK ... in (...)` and by the wire's `z.enum`, so the check at the API boundary and the check in the table cannot drift and there is nothing to hold in lockstep. Adding a value is still a code change and a migration: the table's check names its values. (The Organisation & Access statuses came first and keep their two spellings and their lockstep test.)
- A closed vocabulary that a row holds several of — the days a Route Scheme serves, the days a Collection Group runs on, the days a Project rests on — is a `text[]` under a subset check, `CHECK (column <@ ARRAY['…']::text[])` over the same tuple, with a separate non-empty check where an empty set would mean a scheme that never runs; never a child table, since a weekday is a token and not a row anyone references. The database holds subset-ness and non-emptiness; distinctness and the size of the set are the contracts' rule, since the API is the only writer. Where a bound is the table's own rule — a project's weekend leaves it a working day — it is an inline check beside the subset check.
- A versioned geometry is two tables: an identity that other records name (`planning_area`, by its stable `code`) and an effective-dated version table that holds the polygon (`planning_area_boundary`), one version in force at a time under the exclusion constraint. A record that named a version would break the day a new one started, and the version chain is the identity plus non-overlapping periods, which the constraint holds where a `previous_version_id` could not.
- The ring rule: a polygon reaches the API as a closed flat ring — the contracts' `FlatPolygon`, an outer ring of four or more `[lng, lat]` positions closing on the first with three distinct, holes allowed, no winding rule and no altitude, since the column is flat — closed by the client and never repaired at the boundary, which refuses rather than repairs everywhere else. PostGIS's `st_isvalid` in the column's check is the second stop, and its refusal of a ring that crosses itself is answered as a 400 on the field (`refuseCheck`), because the row is alone and its own value will not do, which is what a schema says of a value it refuses; the only difference is who noticed.
- A set that travels with a record is read with the record and replaced whole, never diffed, the record's own row stamped first so `updatedAt` moves and the replacement delete-then-insert inside the request's transaction: a Property's parties and a Group's or Point's members through one mechanism with a descriptor per family (`routes/members.ts`), a Collection Calendar's holidays through a sibling spelled in its route, since an entry there is a row named by id with a role and a holiday is a day with a name and names no row, and a Collection Group's Stop Matching Rule and picked containers through a sibling of their own (`replaceGroupSet`), since the rule is three things over two tables and a column and the list is positioned, 1..n in the body's order. A create may carry the set it starts with; a patch never touches it, because a patch is a field-by-field change and a set is a set.
- Generated Routes are unique on route scheme, collection group, and service date. Generation is idempotent.
- Pickup is a current-state row. Proof of Service and Unload are append-only rows referencing the Route or Pickup.
- Stock Movement and Vehicle Allocation are append-only. Asset State is projected.
- Derived rows (list columns, KPI tiles, matched containers, a scheme's scheduled, effective and expired readings and its Attention, which boundary of an area is in force on a day) are computed, never persisted; `?validOn=` is how a period is read against a day, and no day is implied, since a default would need a timezone nobody stated.
- Ids are UUIDv7, generated by the client for anything a driver can create offline.

## Build order

1. **Now, in parallel with everything:** request the Adressevælger token from Klimadatastyrelsen and a Dataforsyningen token; snapshot municipality and postcode GeoJSON from DAWA before 2026-10-01. The snapshot was taken 2026-09-24 and lives in `packages/db/reference/dawa/` (municipalities and postcodes as GeoJSON in EPSG:4326, gzip-compressed, checksums in its README); the two tokens are still to be requested.
2. **Monorepo.** Done in the repository 2026-09-17; the deployment's root directory and an e2e run against the moved app are still open, and the API ships as a container image (`apps/api/Dockerfile`, built and smoke-tested on every CI run since 2026-09-25) whose host is chosen with the worker's. This app is `apps/web`. The domain logic of `lib/route-schemes` (all of it) and of `lib/map-planning` (the planning questions; the map-view mechanics stayed in `apps/web/lib/map-planning`), with the pure record helpers from `lib/data`, is `packages/domain`, kept free of every dependency and browser global by a mechanical purity gate in the development-only `packages/tooling`. `packages/contracts` holds the shared wire primitives on zod 4. `apps/api` was, at that point, a Hono scaffold serving its health and its OpenAPI 3.1 document; the root `CLAUDE.md` describes the layout. The module contracts derived from the form schemas were not built here: each context's arrive with its tables, from step 3 on.
3. **Organisation & Access and Registry schema.** The database foundation came first in the repository, 2026-09-18 to 2026-09-24: `packages/db` on Drizzle over Supabase Postgres 17 with PostGIS, one container from one command locally and on every CI run, where a database test may not skip. It holds schema `wms`, unexposed and revoked from `PUBLIC`; `wms.uuidv7()` as every id's default; the column sets a table spreads (`company_id` and `project_id`, `created_at` and `updated_at`, `valid_from` and `valid_to`); the three statements Drizzle has no builder for, each spelled by one helper and required of every table's own migration file by a test: the exclusion constraint over the key and the validity range, the tenant fence (row-level security forced, one policy for `wms_api` on the company a transaction sets, which is what `withCompany` does) and the `updated_at` trigger; geometry columns typed as the contracts' GeoJSON `Point` and `Polygon` in SRID 4326 and checked valid in the database; `validOn`, the query-side reading of a validity period as of a day; and `apps/api` connected as `wms_api`, answering `GET /readyz` for the database. The hosted project carries the same foundation. Organisation & Access landed on that foundation in the repository, 2026-09-24: eight tables in migration `0002_organisation_access` — `company` (its own tenant, `company_id = id`), `project`, `service_provider`, `role`, `role_grant`, `user_account`, `project_access` and `service_provider_access` — each with its tenant fence and `updated_at` trigger, keyed by the composite rule above, statuses as text with a check rather than an enum, and nothing effective-dated, so the exclusion helper waited for the Registry; `public.custom_access_token_hook`, in the same migration, which binds an invited account to its login by e-mail on first sign-in, refuses a deactivated one, and puts `app_metadata.company_id` into every token Auth issues, refresh included — Auth's own role may execute it and nobody else, `service_role` included, which migration `0003_revoke_hook_from_service_role` settles, since `public` is the schema the Data API exposes and the owner's default privileges there had granted it; a seed (`pnpm db:seed`, idempotent, fixed UUIDv7 ids) that writes the demo company, its projects and providers, the eleven system roles with their grants and the two demo accounts — and, since 2026-09-25, the Registry's fifteen tables derived from the prototype's fixtures, the first of step 4's "fixtures become seed data" — so the local database and the hosted project hold the same tenant; the API's request path — the bearer token verified against the project's JWKS, then the caller's account, role, grants, projects and provider resolved inside `withCompany` on a per-request transaction the handler runs in, the grant checked per route, and every error an RFC 9457 problem; and the routes themselves, `GET /me` beside the organisation resources (company, projects, service providers) and the access resources (users, roles and their grant matrix), ids minted by the server and lists paged by a cursor over them. The first module contracts came with them, into `packages/contracts`: `permissions`, `problem`, `me`, `organisation` and `access`. The Registry landed on the same foundation later the same day, 2026-09-24, and closes this step: fifteen tables in migration `0004_registry`, grouped as the context reads — the catalogue a service is described in (`waste_fraction`, `container_type`, `service_frequency`, `product`), who is served and where (`customer`, `property`, `property_party`, `property_group`, `property_group_member`, `shared_collection_point`, `shared_collection_point_member`), what they are entitled to (`agreement`, `subscription`) and the one Container identity with the placement that says where it serves (`container`, `container_service_placement`) — each with its tenant fence and `updated_at` trigger, twelve of them project-scoped and keyed by the project rule above, three of them — a waste fraction, a container type and a Customer — the company's, since the same housing administrator is a customer of every project. Three are effective-dated, the first in the system, so the foundation's `validity` set, `validPeriod` check, `excludeOverlapping` constraint and `validOn` reading get their first real use: `agreement_no_overlap` over the agreement number, `subscription_no_overlap` over the agreement, the product and the place, and `container_service_placement_no_overlap` over the container. A subscription's place is a Property or a Shared Collection Point, exactly one of the two, and `location_id` is the generated `coalesce` of them, because an exclusion constraint's key column may not be nullable and a null never equals anything. `property.location` and `shared_collection_point.location` are the first points the system stores rather than derives from address text. The citizen portal's customer-side identity is here as a Registry read model and not an account: the `property_party` rows a person is named on, answered by `GET /properties?customerId=`. The module contracts came with the tables — `validity`, `catalogue`, `customers`, `agreements` and `containers` in `packages/contracts`, on a shared `resource` module the earlier two now import from as well and a new `queries` for the project filter these lists share — and the API answers fifty-one routes over ten families, under `configure.master` (waste fractions, container types, service frequencies), `commercial.products`, `customers.contacts`, `customers.properties`, `customers.groups`, `customers.shared`, `customers.agreements` (agreements and their subscriptions) and `resources.containers` (containers and their placements), with every project-scoped statement bounded by the projects the caller works in as well as by the tenant, so a Service Provider account, which works in none, reaches nothing here. Containment — a subscription inside its agreement's period, a placement inside its subscription's — is a rule no constraint can state across rows, so the API states it under the parent's row lock: a child moved outside its parent is a 400 naming the bound the caller chose, a parent shortened under its children a 409 counting the rows in the way. What moves to later steps: the project's working week and holiday list, which the prototype keeps on its project record, arrived as columns on `project` with Planning (step 5, migration `0006_planning`, 2026-09-25); the Stock Movement ledger, the projected Container Asset State and the ledger half of the "issue into service" command — `POST /containers/:id/placements` is its seam — arrive with Resources, and a ledger's `REVOKE UPDATE, DELETE` with them; Price Lists, and the invoice name, code and VAT of a Product, arrive with Finance & Contracting; the portal login bound to a Customer is its own issue. Line strings arrive with the first stored route leg, and where the prototype's unclosed `{ lng, lat }[]` boundaries become rings was decided with the first table that stores a polygon, `planning_area_boundary`, in step 5: they are closed in the web adapter, and the API takes a closed ring and nothing else.
4. **Frontend adapter.** A server-backed implementation behind the record store's `getRecords` and `upsertRecord`, switched module by module. Fixtures become seed data.
5. **Planning and the generation worker.** Part A, the rules, landed in the repository 2026-09-25 (Issue #97): nine tables in migration `0006_planning`, grouped as the context reads them. Where work happens: `planning_area`, the identity a Route Scheme and, in step 7, a Service Area name by its stable `code`, and `planning_area_boundary`, its effective-dated versions, each the system's first stored polygon — one boundary of an area in force at a time under `planning_area_boundary_no_overlap`, a new version starting when the old ends, so the prototype's `previousVersionId` is gone and the area's "active", "upcoming" and "expired" are readings of the versions against a day; the ring rule was decided with that first polygon and is a data model rule below. When work may not happen: `weekend` and `holiday_list` on `project`, the first `ALTER TABLE` to a table already applied, and `collection_calendar` with its `collection_calendar_holiday` rows — one calendar of a project in force at a time under `collection_calendar_no_overlap` over the project alone, so the per-year calendars tile the project's timeline and a scheme reads its project's calendars and never picks one. What recurs: `route_scheme`, effective-dated with one scheme of a name in force at a time under `route_scheme_no_overlap`, so "Create new version" is a new row of the same name starting when the old ends and the prototype's Version fact is the row count; `collection_group`, and the Stop Matching Rule as rows a key can refuse and generation can join, never JSON — `collection_group_fraction` (one or more, what the rule matches), `collection_group_container_type` (none or more, a restriction) and `rule_vehicle_type` on the group, with `collection_group_container` in stop order the manual alternative and `stop_source` saying which the group is. The implicit group of a scheme without explicit groups is materialised as a row by the server (a create carries at least one group, the quick form's one rule becoming it), so every generated Route will carry a group and the route key of ADR-0002 has no nullable column. Every one of the nine is project-scoped, fenced and triggered, keyed by the rules above; the days a scheme serves, a group runs on and a project rests on are `text[]` columns under a subset check, and `route_scheme.status` stores only the half of the lifecycle a person decides, `draft` or `validated`. The module contracts came with the tables — `planning` (the enums read off `@waste/domain/planning/vocabulary`), `planning-areas`, `collection-calendars` and `route-schemes` in `packages/contracts`, `IsoTime` in `dates` for a planned start on the project's clock, and the two fields on `Project` in `organisation` — and the API answers twenty-five routes over four families: planning areas and their boundary versions under `configure.areas` (nine), collection calendars and their holidays under `configure.calendars` (five), route schemes with the occurrence read under `route-studio.schemes` (five) and collection groups with their two set replacements under that same grant (six), every statement bounded by the tenant and by the projects the caller works in, no delete anywhere. Their rules are sentences: a holiday lies inside its calendar's period — a day put outside is a 400 naming the entry, a calendar shortened under its holidays a 409 counting them, the two-sided containment the Registry states for a subscription in its agreement, held under the calendar's row lock; a `validated` scheme holds together — every service day has a collection group, a rule group names a waste fraction, a manual group picks a container, a rule group has a planning area to match inside — refused as one 409 listing every sentence that fails, on the write that makes it validated and on every write to it or its groups while it is, where a `draft` accepts partial configuration; no container is picked by two collection groups that run on a shared day, held with every other rule across a scheme's groups under the scheme's row lock; and a check only the database can run, `st_isvalid` on a polygon, reaches the client through `refuseCheck`, the third door beside the duplicate's and the overlap's, as a 400 on the field rather than a 500 naming nothing. The occurrence read, `GET /route-schemes/:id/occurrences`, is the pure preview: the scheme's recurrence and holiday policy through the domain's `generateOccurrences` — the one implementation the guided setup's preview and the generation job will both call, so a preview row and a generated route agree by construction — against the project's weekend and the holidays of its collection calendars, read only when the project names a holiday list and none otherwise; `?validOn=` is how the boundary or the calendar in force on a day is picked. Derived and never stored: a scheme's scheduled, effective and expired readings and its Attention, its `lastGeneratedAt`, which boundary of an area is in force on a day, and the area's own readings. Part B owes the rest and waits for a host outside Supabase (Railway or Fly): `apps/worker` on pg-boss; migration `0007_generation` with `generation_run` and `generation_match` (the drift stamps of #41, an ordinary table) and the minimal Execution tables generation writes into, `route` and `pickup`, unique on route scheme, collection group and service date, which step 6 extends and never renames; generation itself — stops resolved by containment in the boundary in force on the service date and by the validity of placement, subscription and agreement on that day, idempotent by that identity, a shifted collection keeping it and moving its operating date; the nightly `planning.plan-ahead` cron; a second role, `wms_worker`, with `BYPASSRLS` for the one sweep that reads across tenants, every write still fenced as `wms_api`; and, last and separable, the Valhalla legs with the system's first stored line string.
6. **Execution.** Proof of Service and Unload, outbox, Expo driver app on PowerSync, live dashboard.
7. **Resolution and Finance** from the outbox, then the e-conomic export.
8. **Optimisation and import tooling** once real routes exist.
