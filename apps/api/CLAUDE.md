# apps/api

The Hono API (ADR-0001), run from TypeScript source through tsx. `src/app.ts` builds the app from injected pools, a token verifier and a clock; `src/server.ts` is the composition root. `GET /openapi.json` is generated from each route's `describeRoute`, so a route without one is missing from the published contract.

## A route

- Each authenticated route puts the principal guard (`src/auth/principal.ts`) and `requireGrant(moduleKey, action)` (`src/auth/require.ts`) before its handler, route by route rather than on a wildcard, so the probes stay open and an unknown path stays a 404.
- The handler works inside the request's transaction, `c.get("tx")`, which the guard opened under `withCompany`; it opens none of its own. The guard discards the transaction on an error or any status of 400 or above.
- The routes that call another service are the exception, since no transaction is held across such a call (#124 §4): on the Pilot's small pool a connection idle through one starves the requests behind it. They are `POST /routing/preview` (#173), which calls the routing provider, the proof objects' `POST /driver/uploads` and `GET /pickups/:id/proof-objects` (O1), which call Storage, and the address lookup's `GET /addresses` and `GET /addresses/:id` (#291 C13), which call the address register. Their guard is `identify`, the same checks through the same function as `authenticate`, with the transaction ended before the handler, which opens short `withCompany` transactions of its own outside the call. A property's create and patch keep their transaction and read a body's `addressId` from the register before their guard opens it (`addressLookup`, `routes/addresses.ts`).
- A public route (`/public/:slug/…`, ADR-0010) puts `publicDoor` before its validators and handler, takes no token, and reads as `wms_public` inside `c.get("tx")`. It may read only `PUBLIC_DOOR_TABLES` (`packages/db/src/sql/public-door.ts`): a column a public answer needs is added there, with its grant and policy, in the slice's migration.
- Every statement carries two fences: an explicit `company_id` (the API's own check, with RLS behind it) and the project fence, `inProjects(column, principal)` from `src/auth/projects.ts`. A row outside the caller's projects is the family's 404; a body or query naming a project the caller does not work in is a 400 on that field. The driver door fences by assignment (`src/auth/driver.ts`), and the pick lists of `GET /driver/me` by the driver profile's project or the company alone; a Service Provider's account reaches rows through `src/auth/provider.ts`: the reads of the routes and pickups families carry `routeReach` / `pickupReach` (`servesRoute` for a provider), their commands the office's `routeScope` alone, so a provider's command is the family's 404.
- A token names its company in `app_metadata.company_id`, which the access token hook sets from the account bound to the login. Sign-up is invitation-only (`supabase/config.toml`).

## Answers

- Every error is an RFC 9457 problem (`src/problem.ts`): throw `problem(status, { detail, errors })`, and validate with `validate(target, schema)` over the contracts' schemas.
- A problem's type is `about:blank`, except the principal's two account refusals, `kind: NO_ACTIVE_ACCOUNT`, and the proof-object routes' 503 on a deployment whose Storage is absent or refuses, `kind: NO_PROOF_STORAGE` (both `@waste/contracts/problem`), which the Driver App answers as the action's rejection rather than an outage. The web ends the session on the first alone, so give neither to any other refusal, a driver door's or a grant's 403 included.
- A body value that will not do is a 400 naming its field (`invalidRequest`). A row whose state refuses the command is a 409 with one sentence saying why. Judge in this order: the path's own row (404), its state (409), the body's fields (400), then the 409s that need the body.
- A database refusal goes through the doors in `src/routes/shared.ts`, each with the route's own sentence: `refuseDuplicate` (23505), `refuseOverlap` (23P01), `refuseCheck` (23514, as a 400) and `replayed` (an idempotent retry meeting a primary key). A client sees the sentence and never the constraint's name; an unmapped 23514 is a 500, which means a sentence is missing.
- A create answers 201 with `Location` through `created()` and declares it with `describeCreated`. An append to a ledger — a stock movement, a comment, a weight review — answers 201 without one. `src/__tests__/app.test.ts` counts the secured operations and the 201s; update it with each new route.
- A list answers `Page(item)` through `src/pagination.ts`: ordered by `id` (a UUIDv7, so creation order; newest first only where the route says so), with a cursor over `id`, no offsets and no total.
- The server mints the ids of web writes (`newId()`, `src/ids.ts`); a driver's command carries the id its device minted.

## Rules the API holds

- Take `lockRow` before reading a row whose rule the API holds, parent before child, and `lockRows` for a set (in id order). A command that may change a key column of the row it locks (a name or a code unique in its scope) passes `strengthFor(table, patch)` as `lockRow`'s strength. `wms_api` cannot row-lock a ledger row, since a row lock needs the UPDATE privilege it was denied, so lock the parent instead.
- A status gates a new reference, never an existing one (`src/routes/statuses.ts`).
- A child's period sits inside its parent's (`src/routes/periods.ts`): a child placed outside is a 400 at the bound, and a parent shortened under its children is a 409 counting them.
- Routes take the app's injected `now`. An instant becomes a day in the project's timezone through `src/routes/days.ts`, and a body's instant may run ahead of the clock by `OCCURRED_AT_SKEW_MS` at most.
- News for another context goes into the outbox through `emit()` (`src/outbox.ts`), in the request's transaction, after the rows it describes, with the wire resource as the route answers it for its payload.
- Every write is audited by the database's trigger under the Principal (`authenticate` → `writtenBy`, `src/auth/audit.ts`); a route writes no history itself. The office's reason is the `Waste-Change-Reason` header, percent-encoded and bounded, and `GET /audit-events` reads a row's history under its table's module (`AUDITED`).
- A statement the worker runs too lives in `@waste/db/commands` and throws `Refused`, which the error handler answers as the 409 or 400 it names.
- Work for the worker is a pg-boss job sent in the request's transaction through `@waste/db/jobs` (`sendGenerateRoutes`, `sendInTransaction`), so it commits with the rows that asked for it. The API runs no pg-boss: `createApp` builds one sender over the probe pool, never the request pool, and never starts it (`jobs`). The worker creates every queue when it starts; the API creates none, and answers 503 on a database whose worker has not (`QueueMissing`). The generation trigger takes no lock on the scheme, since the worker holds it for a whole run; pg-boss's singleton key is the serialisation, and the run it answers is the one whose job pg-boss still holds (`jobHeld`).
- A new environment variable goes into `src/env.ts` and onto the API's tasks in `turbo.json`.
- A route is generated (#97 B) or the office's ad-hoc one (#111, `POST /routes`, no scheme and no group, numbered with `nextNumber`); a stop is generation's or the office's (`pickup.origin`). Generation never reads an ad-hoc route and never skips, moves or re-plans an office stop, so neither is held. A stop's `service` is an emptying, generation's only, or a work order the office books (O3 of #290); the office may repeat a container on a route, but not book the same work twice while it is planned.
- A stop never changes its route: its proofs and a ticket's booking carry the route in their keys. Moving, splitting and merging (`routes/stop-moves.ts`, O23 of #290) take the stop off (`removed-by-dispatcher`, the note naming where it went) and add the office's stop of the same work on the other route through `addOfficeStop`, naming the stop it was moved from (`moved_from_pickup_id`), which is what keeps a move standing through the next generation run without a hold; Finance reads a moved stop with the origin of the first stop of its chain, so a scheduled collection moved is still billed as one.
- A command over many rows (`POST /routes/dispatch`, O5 of #290) judges each row as its own command does, each in a savepoint under its own row lock, the rows locked in id order, and answers one result per row in the body's order: a refusal (`ProblemError`, 404 or 409) is that row's result, anything else fails the request.
- A scheme is never deleted: its archive (`routes/scheme-lifecycle.ts`, O21 of #290) cuts the period, turns Plan Ahead off and ends its routes from the day as generation would, in the request's transaction, never through a queued run. A new write to a scheme or its groups calls `requireNotArchived` after its 404.
- A reschedule onto a day the project rests on is judged by `@waste/domain/execution/operating-day` and taken only with `acceptNonWorkingDay`; a cancel carries one of `OFFICE_CANCEL_REASON_CODES`, and `regeneration` is the run's own code, written with `cancelled_by_generation`.
- Where the deployment holds Storage's key, the API's boot makes or keeps the `proofs` bucket (`src/proof-bucket.ts`), best-effort; the migration and the boot are the two writers of its settings.
- A reply to a customer, a customer-visible ticket comment, is written through `recordCustomerReply` (`routes/ticket-evidence.ts`) alone, the one place its sending is added.
- A report (`src/routes/reports.ts`) counts rows and stores nothing, under two grants: the Improve module it is read in and the module whose rows it counts. It counts by day and folds the days into intervals through `@waste/domain/insight/intervals`, never a `date_trunc`, and an instant's day on its project's clock carries a coarse instant bound beside it, so the instant's index still prunes.
- A Property's parties are dated (#374): a read answers those in force on the project's today and later (`heldFromToday`), a question of who a customer is to a property now asks `partyInForce`, and `PUT …/parties` edits today's set, never deleting history but a same-day correction. A move (`routes/moves.ts`) ends the outgoing customer's roles and subscriptions there and writes the incoming agreement through the agreements' own writers; it reprices nothing and answers the charges past its day as `chargesToCredit`.
- A tank (M11 of #293, `routes/tanks.ts`) is a Container at its Property; its last emptying is read only through `lastEmptyings` (`@waste/db/query/tank-emptyings`) and its due date through `tankDueOn`, the reading generation plans from, so the office's date and the run's agree.
- A registry family's create and patch live outside its handlers (`routes/customer-writes.ts`, `property-writes.ts`, `container-writes.ts`, and the four exported functions of `agreements.ts`), because the CSV import (`routes/import-rows.ts`) runs them too: a new rule on a create goes there, never into the handler alone. An import row is one savepoint of the request's transaction, and a request carries at most `IMPORT_BATCH_MAX` rows (`@waste/domain/imports/vocabulary`), below the 64 subtransactions Postgres caches per transaction.

## Tests

- `src/**/*.test.ts`. A suite on the shared local database mints its own tenant (`src/__tests__/tenant.ts`) and removes it with `dropTenant`; a suite that writes a ledger hands `dropTenant` the owner's pool (`DATABASE_ADMIN_URL`), since `wms_api` cannot delete ledger rows. Tokens are signed against a key set each test generates (`src/__tests__/tokens.ts`), and calls go through `callingAs` (`src/__tests__/calls.ts`).
