# apps/web

The Next.js App Router prototype (TypeScript, Tailwind CSS v4, shadcn/ui). Records are fixtures from `lib/data/` merged with browser storage, except in the modules switched onto the API.

## The workspace shell

- Most top-level routes in `app/` are thin server components that render `WorkspacePageShell` (`components/waste/workspace-page-shell.tsx`) with a `workspaceId`. Navigation inside a workspace is the `?module=` and `?record=` search params.
- `components/waste/business-workspace.tsx` renders every workspace's modules generically, and `business-record-form-dialog.tsx` builds the create and edit dialogs from the schemas in `lib/data/business-form-schemas*.ts`. The citizen portal and the service-provider persona have restricted shells (`restricted-workspace-shell.tsx`); the driver's surface is the Driver App, below. On the Pilot the provider's shell is `/me`'s (`lib/data/provider-workspace.ts`, `components/waste/provider-account.ts`): its provider, actor and grants, no pinned project, and no provider filter over a switched module, which the API fences itself (`fencedByApi`); a surface offers a provider's account only the commands the API gives it, through `useCommandOffered` (`commandOffered`, `PROVIDER_COMMANDS`), never a branch of its own; its team is `service-providers.service-provider-workspace` over `/users`, read for a provider's account alone (`providersOnly`), since the office's accounts are `configure.access`'s.
- `lib/data/business-modules.ts` is the registry of workspaces, modules and fixture records. `lib/data/business-domain.ts` maps every surface to its canonical business module; consult it before moving a feature between workspaces.
- A `ProjectScope` is a project record's id or `"all"`; every scope question goes through `lib/data/project-scope.ts`.

## The record store and the API

- `components/waste/business-record-store.tsx` answers `getRecords` and `upsertRecord`. A module in `SERVER_MODULES` (`lib/api/records/modules.ts`) reads the API while a person is signed in against one; every other module reads fixtures plus the browser's bucket. To switch a module, add it there, with a mapping under `lib/api/records/` wherever the wire and the prototype's form disagree.
- A switched module shows the server's rows, or its fixtures until they arrive or when the load failed — never a mix with records made in the browser. A module read that fails on the way — a 5xx or no answer — is asked again at `READ_RETRY_DELAYS_MS` before it is failed; a refusal the API answered is not (`readModuleInto`).
- `lib/api/client.ts` is the one way the web calls the API. The prototype's ids stay the web's handles; the server's id is kept beside the record in the module's `serverIds`. A module read again keeps the web id the store holds each server row under (`mapModule`), so a row made this session keeps its minted id across reads and the adapter's id is the next session's. Name a row by server id through the resolver (`byServerId`, `webIdVia`), never by rebuilding `<prefix>-<uuid>`.
- A row's command (`POST /users/:id/deactivate`) is an entry in its adapter's `commands`, sent through the store's `sendCommand`, whose optional input the command's `toBody` maps to the body (web ids through the resolver, a `LocalRefusal` before the API). A command's or an action's refusal that names its row by server id is told with the row's name (`namingRow`). A command that changes another module's rows too names that module in `touches`; the store reads it again after the command. A module whose records are read through others names them in `derivedFrom` (`ServerModule`), and one whose records are read on the project's day says `readsTheDay`: the store stamps each read of a derived module with their rows as the read began (`mappedAgainst`) and reads it again once one has new rows since, and reads a day-bound one again once its projects' day turns (the provider's watcher; `derivedFromChanged`, `dayTurnRereads` in `server-records.ts`) — the containers, through the organisation and their places' modules, the planning areas' boundary in force, the provider prices' periods and Apply index, the settlements' offers, and the access credentials' statuses (#393). The generic workspace offers a switched module's commands, and a primary action other than its create form, only through `components/waste/commands/command-surfaces.ts`, consulted with the adapter configured: a slice adds an entry there, not a branch in business-workspace.tsx; an entry's `whileShown` is mounted beside the module's table while the module is shown, for what a module does on its own while a person watches it (the Live board's re-read through the store's `refreshModule`, the command re-read exposed). A request about a row that answers another resource (a scheme's generate answers its run) is an entry in the adapter's `actions`, sent through `sendAction` by the adapter's typed wrapper (`generateScheme`), never by name; `refreshRecord` reads one row back through the adapter's `read` when the server changed it on its own account. `upsertRecord` answers a switched module's write outcome, so a dialog can stay open on a refusal. The status dialog (`ActionDecisionDialog`) asks and promises per `actionDecisionShape` (`lib/data/action-decision.ts`): on a switched module the status and an optional reason, which the write gives in the change-reason header (`ApiClient.reason`, `upsertRecord`'s `reason`), no date and no audit row of the browser's; a record's History (`components/waste/record-history.tsx`) is the API's audit log of the row, read by its adapter's `auditTable`, and a kind with none shows no section. On the Pilot the sidebar shows the API's alone: Active Routes resolves a starred route from the routes module's rows (`resolveActiveRouteSummaries`, `onApi`), and a nav badge is `navBadgeOf` (`lib/data/sidebar.ts`) — the open tickets once read, no other number. A write the API took whose answer the adapter cannot map is `landed`: told as saved, its row kept with its server id and its module read again, never a refusal. A write to a switched module the API has not read is refused by the store itself (`writeRouteOf`), never kept in the browser. A write or a command of several requests that fails after a mutation of it landed is told apart by the store, not the adapter (`trackingClient`): with no mutation failing it is `landed` — a command's row read again and answered done — and with a later one failing a `partial` refusal, the row kept as typed and its module read again; never the row put back. An adapter does its reads after its writes. A surface reads a write's outcome only inside `whenSaved`'s `done`, which is handed it; `savedRow` is the row a saved write left. Settings › Users & roles reads the organisation store in fixture mode only; on the Pilot it reads `configure.access` alone (`lib/data/users-roles.ts`) and, through `useServerModuleState`, shows nothing rather than the fixtures until the module is ready; its Roles tab creates a custom role through `NewRoleDialog`, which may start from any role's matrix, saves a custom role's matrix whole through `REPLACE_ROLE_GRANTS` (`PilotRolePermissionsPanel`), and shows a system role's read-only in `systemRoleKept`'s sentence (`roleMatrixOf`); `useModuleRecords` is that rule for a pane's own module, which Areas & Zones, Collection calendars, Holiday lists and Master data read through, and `whenSaved` is the one way a pane waits on a write's outcome. Master data (`configure.master`) is four adapters in one module (`lib/api/records/master-data.ts`); which kind a record is — its id prefix, then its typed `kind` — is `masterDataKindOf` (`lib/data/master-data.ts`), the rule the adapters own by and the pickers pointing at the module filter by; the pane's forms are its own, the registry's schema for the module stays disabled, and the pane is reached through `masterDataSettingsHref`. A planning area record carries the boundary version in force on the project's day as GeoJSON under `PLANNING_AREA_GEOMETRY_KEY` (`@waste/domain/map-planning/areas`), which the map draws over its container-derived outline; an upcoming or ended version lends the record its dates and id, not its geometry (`lib/api/records/planning.ts`). The fleet and the places (`lib/api/records/fleet.ts`, `places.ts`) write through the generic forms as they stand: a vehicle's "Asset reference" is its callsign on the wire, its fractions multiselect is one compartment (a vehicle of several is read whole and its fractions not re-cut from the form; the compartments one by one are its details' editor, `SET_COMPARTMENTS`, O7 of #290), a location's kind is the form's `locationType`, and a station's fractions and a vehicle's compartments are replaced whole through their `PUT` routes; `enhanceField` turns a single fraction select at the master module into static keys and leaves a multiselect on the module. Agreements (`customers.agreements`) is two adapters in one module (`lib/api/records/agreements.ts`), the subscriptions after the agreements they name; which kind a record is — its id prefix, then its `recordKind` — is `isAgreementRecord`/`isSubscriptionRecord` (`lib/data/agreements.ts`), the rule the pickers pointing at the module filter by. The products and the price lists load before it. An agreement's price list is one of its project's lists in its currency, `PROJECT_DEFAULT_LIST` standing for the wire's null (`agreementPriceListOptions`). A subscription's product is one of its agreement's project's (`subscriptionProductOptions`), a typed id only for a role that reads no products (`subscriptionFormSchemaFor`). Both are read through `useModuleRecords`, never fixtures. A field that names an unswitched module's row carries an id chip (`referencedId`), and every effective-dated form spells its end as the last day in force where the wire's `validTo` is the first day out (`lastDayIn`/`firstDayOut` in `planning.ts`). Properties, property groups and shared points (`lib/api/records/properties.ts`) are operated through their command surfaces with forms of their own (`lib/data/properties.ts`): a set goes out whole as its `PUT`, a property's parties as one multiselect per role, a group's or a point's members as one multiselect plus the role new members join as, the roles already held riding on the record under `MEMBER_ROLES_KEY`. A server container stands where its placement serving today is delivered at, read through its subscription (`lib/api/records/container-places.ts`): its serving under `SERVING_KEY` (`@waste/domain/route-schemes/matching`) — for each placement not ended, the period it serves in under its subscription and agreement and the planning areas its place lies in — which the rule preview judges on the scheme's first day where that is ahead instead of its asset state, naming its fraction and type by its facts; the point and the facts are today's placement's, and the map reads where a container lies and whether it serves today through `containerAreaRefs` and `containerInService` (`@waste/domain/route-schemes/matching`), the shown placement's period marked `shown`; the Route scheme filter of a container naming no scheme is built from the routes that stop at it (`mapFilterReaders`, `routeSchemeIndex`); the worker's matcher decides at generation.
- Route schemes (`route-studio.schemes`, `lib/api/records/route-schemes.ts`) are `scheme-<uuid>` from the start. The record keeps the prototype's group shape — the legacy keys for one group running every service day, the `collectionGroups` JSON otherwise — with each group's server id under `SERVER_GROUP_IDS_KEY`; a rule names its fractions, container types and vehicle type by the master data's names (`Resolver.find`), and the lifecycle and drift readings come from the resource's `generation`. An edit is one `PATCH` (#205): the scheme's moved fields and, where any group moved, `collectionGroups` whole — a group restated under its server id, an added one without, one left out parked — the legacy shape's one group under the name the server holds (`SERVER_GROUP_NAMES_KEY`) and an untouched rule by the ids it was read with (`RULE_MASTER_IDS_KEY`). On the Pilot the web never generates itself — Generate asks the API for a run and the scheme page watches it (`components/waste/scheme-generation.tsx`, the rule in `lib/api/records/generation.ts`); a run that succeeds has the routes, then the pickups, read again (`modulesAfterRun`), the routes first since a stop takes its scheme and dates from its route as the store holds it, no Plan Ahead run on load, a create or an edit writes the scheme alone — and a scheme's pickers offer no rows of a module still on fixtures (`components/waste/pickable-records.ts`). The guided setup reads the same way (`scheme-wizard/use-wizard-records.ts`: the master data's fractions and container types, no browser catalogue); a draft changes through `patchGuidedDraft` (`@waste/domain/route-schemes/draft`), which clips the groups to the service days a patch leaves, and a picker under a picked project offers `recordsForProject` (`lib/data/project-scope.ts`); the preview's zero-match sentence blocks as in fixture mode once the API's containers are placed — the containers and the modules their records are read through (`CONTAINER_PLACE_MODULES`) ready — and is a notice until then, or while the store's read of them is behind a change (`useContainersPlaced`, `validationWhenUnplaced`).
- Routes, stops and the Live board (`route-studio.routes`, `.pickups`, `.live`; `lib/api/records/routes.ts`, `pickups.ts`, `live.ts`) are `route-<uuid>` and `pickup-<uuid>` from the start, a live row being its route under the route's web id, and move by command alone: the adapters list no `statuses` and refuse every patch, and a module with a row surface offers no generic Edit. The routes and the stops are read over a window from 35 days back with no end (`ROUTES_WINDOW_DAYS`, named once in `routes.ts`), the Live board's short read ahead of them, and the board is read again every 30 s while shown (`whileWatched`); a live row's details read its track and its estimates from the route itself (`routeTrack`, `routeEtas`, O8 of #290), never from the board's row. A time a person reads is on the project's clock — `shownOn`, `dayAndTimeOn`, `timeOn` (`lib/api/records/clock.ts`) — never the browser's. On the Pilot a route opens the generic details with its command surface (`commands/route-surfaces.tsx`); `RouteDetailsPage` is fixture mode's. A read's `activePlan` rides on the route record as JSON under `ROUTE_ACTIVE_PLAN_KEY` (`lib/data/routes.ts`, #173 reads it), and a stop names its container by id and by its `Container ID` label, the two keys the map links a stop by (`linkRoutes`, `routeStopIndex`). A running scheme's edit asks over the API's planned future routes (`schemeEditOnApi`, `lib/data/route-schemes.ts`), comparing values only in one JSON key order, and refuses a shaping edit while the routes are not read; its "This collection only" moves the next collection's routes by their own `reschedule`/`assign`, which the API holds against later runs (`heldAt`) — the planned start, the depot, the unloading station and a group's vehicle or driver, anything else disabled with the reason (`schemeOneOffOnApi`) — and an assign or a reschedule leaves a field its input does not name as the route stands. Since #111 the office makes routes and stops of its own. New route is the routes module's command-surface primary (`ROUTE_CREATE_FORM`, `POST /routes`), its minted id `routes-route-<now>`, never `route-studio-…`, which would read as a route's handle; an ad-hoc route's `Origin` is `Made by the office` where a generated one names its scheme, and its note is `Note`, not `Deviation`. Add stop (`ROUTE_COMMANDS["add-stop"]`) is a route command on a planned or ready route, at a container or at a property or a shared point with its fraction, whose `run` reads the route back, since the API answers the stop; an address-only stop is named and addressed by its place. A ticket's re-collection stop is picked from its route's stops through `recollectionStopOptions` (`lib/data/tickets.ts`), and the Driver App says what a stop collects through `stopCollects`. Dispatch day stands beside New route (`RoutesPrimarySurface`): it lists a project's planned routes of a day (`dispatchDayRows`), sends the ticked ones through `dispatchRoutes`, then re-reads the routes and the Live board (`refreshModule`). A route's details offer Optimise (`OPTIMISE_ROUTE`) and list its Plans (`routePlans`); the active Plan's measure is the route's Distance and Duration. Cancel takes a reason code, and Reschedule's checkbox is the API's `acceptNonWorkingDay`.
- The Price Engine's customer-money chain (`commercial.products`, `.price-rows`, `.events`, `.billing`, `.invoices`; `lib/api/records/pricing.ts`, `billing.ts`, forms in `lib/data/commercial-forms.ts`) is `<prefix>-<uuid>` throughout. The price lists are the first kind of `commercial.price-rows`, the API's grant key for `/price-lists`, and the rows are read list by list and flattened; the module's list `shows` the rows alone (it scopes the module's rows, `listShows`), and Settings › Commercial › Price lists reads the lists — on the Pilot from that module, in fixture mode from the browser bucket `commercial.price-lists` (`FIXTURE_PRICE_LISTS`), one source by mode. Money is minor units on the wire, converted once each way and shown in the row's currency (`lib/commercial/money.ts`). A credit note is a create in `commercial.invoices` posted under the invoice it corrects; Explain price and Run billing's preview are reads the surface asks through the client; Explain price opens on a price row's conditions, a product's default list, or, where the event's price is a list's (`eventPricedByList`), a billable event's own question (`eventQuestion`). An event names its agreement's customer and payer each under its own fact. An event's details offer only the commands its status moves it by (`eventCommandsOffered`): reprice on a blocked event, cancel on a blocked or a ready one, never on a reversal, and a run, a credit note and a price row re-read the modules they change (`refreshModule`).
- The provider-money chain (`service-providers.service-areas`, `commercial.service-provider-prices`, `.settlements`, `route-studio.weights`; `lib/api/records/service-areas.ts`, `provider-money.ts`, `weights.ts`, forms in `lib/data/provider-money-forms.ts`) is `<prefix>-<uuid>` throughout. An award is the planning areas it covers, never a drawn polygon: on the Pilot the map's Create service area opens the API's form on the selection's planning areas and drops the polygon, and the map draws an award as its planning areas' stored boundaries. The assignments are the second kind of `service-providers.service-areas` — which kind a record is, is `serviceAreaKindOf` (`lib/data/provider-money.ts`), the rule the pickers filter by — listed in an award's details, never its table. Apply index is a create of the chain's next row, and Apply index over many prices (#291 C8) — a list's in Settings › Commercial › Price lists, a provider's or an award's from the prices' header and an award's assignments — is one dialog (`commands/apply-index-dialog.tsx`) previewed with `dryRun` and applied through the client, never the store, the module read again once it lands; an unload's details offer only the reviews its status moves by; a price's details offer Apply index only while it has not ended on the project's day it was read on (`providerPriceIndexOffered`), and an ended one says why in the domain's `priceEnded`, its end named by its last day in, and a settlement's only the commands its status moves by on the project's day it was read on (`SETTLEMENT_DAY_KEY`; the module `readsTheDay`): no Calculate before its period has begun, no Close settlement, which asks before it is sent, before the period has ended. Where the day holds a command back, the details say why in the machine's sentence (`settlementHeldBack`). A command surface's own primary stands with the create grant alone, whatever the fixture form (`primaryOf`).
- Service Providers › Activities (`service-providers.activities`, `lib/api/records/provider-activities.ts`, forms in `lib/data/provider-activities.ts`, #474) is `provider-activity-<uuid>`, read after the routes. The provider's shell has it as its Activities page.
- The Sorting Guide (`configure.sorting-guide`, `lib/api/records/sorting-guide.ts`) is `guide-item-<uuid>`, read after the projects and the fractions it names. - On the Pilot the Dashboard (`/performance`) is `components/insight/dashboard-on-api.tsx`, Improve's Performance and Analytics as its two tabs, over the API's reports (`lib/api/reports.ts`, read through `use-report.ts`, never the store). Each card is read under its report's grants, and a change is told against the period before through `lib/insight/dashboard.ts`; fixture mode's control room is the prototype's. The workspace's Export is `exportShownRows` (`lib/data/workspace-export.ts`): the rows the table shows, every page, by the columns it draws, so a column added to the table is added there too, and its test spells it.
- The browser calls `/waste-api/*` on its own origin, and `next.config.mjs` proxies it to `WASTE_API_ORIGIN`, since the API has no CORS yet. `NEXT_PUBLIC_WASTE_API_URL` turns the adapter on, and with it the Pilot's sign-in: every page but `/login` and the public pages under `/p/` (`isPublicPath`) needs a session (`components/auth/sign-in-gate.tsx`), `/login` offers the password form alone (the two `NEXT_PUBLIC_SUPABASE_*` variables, see `.env.example`), a person lands where `GET /me` says (`landingOf`: a driver on `/driver`, a provider on its workspace, a Site attendant on `/check-in`, else `/operate`) and the sidebar's identity is `/me`'s, and so is Settings › Account & appearance's Profile, read and never set there (`profileOf`, `lib/data/account-profile.ts`). Without it the fixture picker, local development and e2e are as before.
- `lib/api/session.ts` holds the session's rules. Only the API's `urn:waste:problem:no-active-account` or a refresh Auth refuses ends a session; a 403 of `about:blank` is a permission refusal and leaves it alive.
- The store reads only the switched modules the person's `/me` role grants `view` on (`viewableModules`); the rest are never requested and are `not-granted`, never `failed`: fixtures to `getRecords` as for `idle`, and to `useModuleRecords` `notGranted`, not pending, whose pane says "The <noun> are not shown to your role." with the store's sentence beneath rather than a failed read, never toasted.

## The Driver App

- `/driver` and `/driver/routes/[id]` are a surface of their own on the driver door, never a `SERVER_MODULES` entry: the screens in `components/waste/driver/`, the rules in `lib/driver/` — `driver-app.ts` is the controller (reads, taps, the drain), `command-queue.ts` the IndexedDB Command Queue, `route-view.ts` what a screen offers. Nothing is shown that the server has not answered: no local `decide`, no display cache.
- A photo's or a signature's bytes ride in the queue's row, and the drain puts them to Storage before the command naming them is sent (`driver-app.ts`); a refusal on the way is the action's rejection.
- Positions (O8 of #290) are recorded only while a route's screen shows this driver's open, unpaused session (`position-recorder.ts`, `sessionRecords`). The open batch is the queue's one `collecting` row, which the drain passes over and a reload closes into a command; a batch is minted as a `record-positions` command when it closes, and is neither counted among the actions waiting nor shown when refused.
- A stop shows its place's `driverInstructions`, never a property's `notes`, which are the office's own.
- It imports the contracts as types only; a value it needs from them is spelled again and held equal by a test (`BATCH_LIMIT`).

## Persisted state and renames

- Every storage key is a constant in `lib/storage-keys.ts`, read through `readPersisted`, which carries a value over from a retired key.
- Persisted ids and hrefs go through `lib/data/legacy-ids.ts` (`migrateLegacyState`, `migrateLegacyId`, `migrateLegacyHref`). Retired names — Contractor, Contract area, the `wastehero` keys and ids — live only there, in `lib/storage-keys.ts`, in the redirects of `next.config.mjs` and in the stores' `LEGACY_*` maps. Keep those maps: they migrate state that browsers still hold.
- Two modules moved into Settings; resolve them through `PLANNING_AREAS_MODULE` (`lib/data/planning-areas.ts`) and `COLLECTION_CALENDARS_MODULE` (`lib/data/collection-calendars.ts`) rather than spelling the workspace and module.

## Map planning

- MapLibre's tile worker is served by `app/maplibre/[version]/[asset]/route.ts`, because Turbopack breaks its module-worker URL; keep `setWorkerUrl` pointed there. Camera moves jump instantly until a style has loaded.
- Maps are north-up and flat: the road overlay's transform assumes it, so rotation and pitch stay disabled.
- Roads come through the API alone; the provider's key never reaches the browser (#173). Step 4 of the guided setup asks `POST /routing/preview` (`use-road-geometries.ts` over `lib/map-planning/road-geometry-cache.ts`). A dated route's line is its active Plan's legs (`use-plan-legs.ts`, `GET /plans/:id` only for a route the map draws), asked for four at a time, the map's day first, then the days ahead, the past window last (`planFetchOrder`), and drawn together every `REDRAW_MS`, never one render per Plan, and every per-route reading comes from the record's `activePlan` (`ROUTE_ACTIVE_PLAN_KEY`, `lib/map-planning/plan-readings.ts`). Without the API no road is asked for and every line is the dashed estimate. A map drawing provider geometry shows `RoutingAttribution`. Route Studio and step 4 show the routing banner from `GET /routing/quota`. The sentences live in `lib/routing/readings.ts`.
- The planning questions — what a selection holds, coverage, routes, scheme comparison — are answered by `@waste/domain/map-planning/*`. They cannot see the records, so every call that places a record takes the gazetteer as an argument: `FIXTURE_GAZETTEER`, which `@waste/domain/fixtures/gazetteer` holds beside the seeded registry's generator and `lib/data/street-gazetteer.ts` re-exports.

## Next.js
